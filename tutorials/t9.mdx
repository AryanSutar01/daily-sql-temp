## What is a Transaction?

A transaction is a group of SQL statements that are executed as a single unit. Either **all** of them succeed, or **none** of them do.

### Classic Example: Bank Transfer

```sql
-- Transfer $500 from Alice to Bob
-- Both operations must succeed or both must fail

BEGIN;

UPDATE accounts SET balance = balance - 500 WHERE user_id = 1;  -- Debit Alice
UPDATE accounts SET balance = balance + 500 WHERE user_id = 2;  -- Credit Bob

COMMIT;  -- Save both changes permanently
```

If the server crashes after debiting Alice but before crediting Bob — without a transaction, Alice loses $500. With a transaction, the database rolls back both changes.

## Transaction Commands

```sql
BEGIN;          -- Start a transaction (also: START TRANSACTION)
COMMIT;         -- Save all changes permanently
ROLLBACK;       -- Undo all changes since BEGIN
SAVEPOINT name; -- Create a checkpoint within a transaction
ROLLBACK TO name; -- Roll back to a savepoint
```

## COMMIT and ROLLBACK

```sql
BEGIN;

INSERT INTO orders (customer_id, amount) VALUES (101, 500);
INSERT INTO order_items (order_id, product_id) VALUES (LASTVAL(), 5);

-- If everything looks good:
COMMIT;

-- If something went wrong:
ROLLBACK;
```

## SAVEPOINT

```sql
BEGIN;

INSERT INTO orders (customer_id, amount) VALUES (101, 500);
SAVEPOINT after_order;  -- checkpoint

INSERT INTO order_items (order_id, product_id) VALUES (999, 5);  -- error!

ROLLBACK TO after_order;  -- undo only back to savepoint

INSERT INTO order_items (order_id, product_id) VALUES (LASTVAL(), 5);  -- try again

COMMIT;
```

## ACID Properties

ACID is an acronym for the four properties that guarantee reliable database transactions.

### A — Atomicity
All operations in a transaction succeed completely, or none of them do. There is no partial state.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
-- If this next line fails, the previous line is also undone
UPDATE accounts SET balance = balance + 500 WHERE id = 2;
COMMIT;
```

> "All or nothing"

### C — Consistency
A transaction brings the database from one valid state to another. All data rules (constraints, foreign keys, triggers) are enforced.

```sql
-- This will fail if balance has a CHECK constraint (balance >= 0)
-- and Alice only has $200
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
-- ERROR: new row violates check constraint "balance >= 0"
-- Transaction is rolled back, consistency maintained
```

> "The database is always valid before and after"

### I — Isolation
Concurrent transactions do not interfere with each other. Each transaction executes as if it's the only one running.

```sql
-- Session 1
BEGIN;
UPDATE products SET stock = stock - 1 WHERE id = 5;
-- Not committed yet...

-- Session 2 (at the same time)
SELECT stock FROM products WHERE id = 5;
-- Isolation determines whether Session 2 sees Session 1's change
```

> "Transactions don't see each other's intermediate states"

### D — Durability
Once a transaction is committed, changes are permanent — even if the server crashes immediately after.

> "Committed data survives failures"

## Isolation Levels

Isolation levels define how much one transaction can see of another's uncommitted work. Higher isolation = more safety, less concurrency.

| Level | Dirty Read | Non-Repeatable Read | Phantom Read |
|-------|-----------|---------------------|--------------|
| READ UNCOMMITTED | ✅ Possible | ✅ Possible | ✅ Possible |
| READ COMMITTED | ❌ Prevented | ✅ Possible | ✅ Possible |
| REPEATABLE READ | ❌ Prevented | ❌ Prevented | ✅ Possible |
| SERIALIZABLE | ❌ Prevented | ❌ Prevented | ❌ Prevented |

### Problems Explained

**Dirty Read** — Reading uncommitted data from another transaction.
```
T1: UPDATE balance = 0  (not committed)
T2: SELECT balance → sees 0  ← dirty read!
T1: ROLLBACK  → balance is back to original
T2 made a decision based on wrong data
```

**Non-Repeatable Read** — Same query returns different results within the same transaction.
```
T1: SELECT balance → 500
T2: UPDATE balance = 200; COMMIT
T1: SELECT balance → 200  ← different result!
```

**Phantom Read** — New rows appear in a repeated query within the same transaction.
```
T1: SELECT COUNT(*) FROM orders WHERE amount > 100 → 5
T2: INSERT INTO orders (amount) VALUES (150); COMMIT
T1: SELECT COUNT(*) FROM orders WHERE amount > 100 → 6  ← phantom row!
```

### Setting Isolation Level

```sql
-- PostgreSQL
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN;
...
COMMIT;

-- MySQL
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

## Locking

Transactions use locks to enforce isolation.

```sql
-- Explicit row lock: lock the row for update
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;

-- Share lock: others can read but not modify
SELECT * FROM accounts WHERE id = 1 FOR SHARE;
```

### Deadlock

Two transactions waiting for each other's locks.

```
T1 locks Row A, waits for Row B
T2 locks Row B, waits for Row A
→ Deadlock! Database kills one transaction.
```

Avoid deadlocks by always locking resources in the same order.

## Autocommit

In most databases, every SQL statement is automatically wrapped in a transaction (autocommit mode).

```sql
-- In autocommit mode, this is immediately committed:
UPDATE users SET name = 'Bob' WHERE id = 1;

-- To group statements, explicitly use BEGIN/COMMIT
BEGIN;
UPDATE users SET name = 'Bob' WHERE id = 1;
UPDATE users SET email = 'bob@new.com' WHERE id = 1;
COMMIT;
```

## Real World Example

```sql
-- E-commerce order placement
BEGIN;

-- 1. Create the order
INSERT INTO orders (customer_id, total_amount, status)
VALUES (101, 1500, 'pending')
RETURNING id INTO order_id;

-- 2. Deduct from inventory
UPDATE products SET stock = stock - 2 WHERE id = 5;

-- 3. Charge the customer
INSERT INTO payments (order_id, amount, status)
VALUES (order_id, 1500, 'completed');

-- 4. Update order status
UPDATE orders SET status = 'confirmed' WHERE id = order_id;

COMMIT;

-- If ANY step fails, all changes are rolled back
-- No partial orders, no inventory deducted without payment
```

## Summary

- A transaction groups SQL statements into an all-or-nothing unit
- `BEGIN` starts, `COMMIT` saves, `ROLLBACK` undoes
- `SAVEPOINT` creates checkpoints within a transaction
- **ACID**: Atomicity, Consistency, Isolation, Durability
- Isolation levels control visibility between concurrent transactions
- Higher isolation = more data safety, lower concurrency
- Deadlocks occur when transactions wait for each other's locks
