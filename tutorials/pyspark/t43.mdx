# Catalyst Optimizer & Tungsten Engine

## Tungsten's Physical Execution Model: Eliminating the Volcano Iterator

Tungsten (Spark's physical execution engine) solves two fundamental performance problems that plagued earlier Spark versions: **JVM GC pressure** and the **Volcano iterator model overhead**.

### The Volcano Iterator Model (Pre-Tungsten)

Traditional database execution used the "Volcano" or "iterator" model — each operator exposes a `next()` method and operators chain together:

```
// Volcano model (conceptual):
while (filter.hasNext()) {
    Row row = filter.next();          // virtual function call
    // filter internally calls scan.next()  → another virtual call
    // scan reads bytes from disk
    Row result = aggregate.process(row);  // creates new Row OBJECT
    // ... materializes result as JVM heap object
}
```

Problems:
1. **Virtual function calls**: Every `next()` call is a JVM interface dispatch — the CPU cannot predict the target → cache misses, branch mispredictions
2. **Object creation per row**: Each `Row` is a heap-allocated JVM object → millions of objects per second → GC pressure, GC pauses stop all computation

### Tungsten's Off-Heap UnsafeRow

Tungsten replaces JVM Row objects with `UnsafeRow` — a **compact binary format** stored directly in native off-heap memory (allocated via `sun.misc.Unsafe`):

```
UnsafeRow binary layout for [id=1, name="Alice", salary=95000]:

Byte offset:
[0-7]   : null bit vector (1 bit per field: 0=not null, 1=null)
[8-15]  : id = 1L           (8 bytes, fixed-width Long)
[16-23] : name offset = 24, name length = 5  (8 bytes, points to variable section)
[24-23+5]: name = "Alice"   (5 bytes, variable-length data)
[29-36] : salary = 95000L   (8 bytes, fixed-width Long)

Total: 37 bytes vs ~200 bytes for equivalent JVM object (with headers, padding, references)
```

**Key properties**:
- Lives in **off-heap memory** (not JVM heap) → zero GC pressure for data
- Accessed via `unsafe.getLong(baseObj, offset)` → direct memory read, no boxing
- Can be passed directly to sort algorithms and hash maps without deserialization

### Whole-Stage Code Generation: Eliminating Virtual Calls

Tungsten compiles multiple chained operators into **one JVM method** (whole-stage codegen), eliminating all virtual function calls:

```java
// Traditional: 3 separate operators with virtual calls
// filter.next() → scan.next() → materialise Row object

// Tungsten generates ONE fused method for:
// filter("amount > 100").groupBy("country").sum("amount")

void processPartition(Iterator<UnsafeRow> inputRows,
                      HashMap<Long, Long> aggregateMap) {
    while (inputRows.hasNext()) {                    // tight loop, no virtuals
        UnsafeRow row = inputRows.next();
        long amount = row.getLong(2);                // direct memory read
        if (amount > 100L) {                         // inline predicate
            long hash = country_hash(row);           // inline hash
            aggregateMap.merge(hash, amount, Long::sum);  // inline aggregate
        }
        // No object creation, no virtual calls, no GC
    }
}
```

The JVM JIT compiler can then:
- **Inline** all operations into one loop body
- **Unroll** the loop for SIMD vectorization
- **Cache** all accessed memory in CPU registers

This is why Tungsten achieves near-native C performance — the bottleneck becomes memory bandwidth, not JVM overhead.

## Overview

PySpark's performance is built on two pillars inside Spark SQL:

1. **Catalyst Optimizer** - A query optimizer that rewrites your logical query plan into a more efficient form before execution
2. **Tungsten Engine** - A low-level execution engine that makes the physical execution as fast as possible using memory management and code generation tricks

Together, they are why PySpark is often faster than hand-optimized code - you just write what you want, and these engines figure out the best way to do it.

---

## Part 1: Catalyst Optimizer

### What is it?

Catalyst is Spark's **rule-based and cost-based query optimizer**. It sits between your PySpark code and the actual execution engine. When you write a DataFrame transformation, Catalyst:

1. Parses it into a logical plan
2. Validates and resolves it (checks column names, data types)
3. Applies optimization rules to produce a better logical plan
4. Converts the optimized logical plan into a physical plan

### Catalyst's 4-Phase Pipeline

```
User's PySpark Code
        ↓
┌─────────────────────────────────────────┐
│          Catalyst Optimizer             │
│                                         │
│  Phase 1: Analysis                      │
│  - Resolve column names & types         │
│  - Validate schema                      │
│                                         │
│  Phase 2: Logical Optimization          │
│  - Apply optimization rules             │
│  - Predicate pushdown                   │
│  - Column pruning                       │
│  - Constant folding                     │
│                                         │
│  Phase 3: Physical Planning             │
│  - Generate multiple physical plans     │
│  - Choose the cheapest one (cost model) │
│  - Select join strategy                 │
│                                         │
│  Phase 4: Code Generation               │
│  - Generate bytecode for execution      │
│  - Whole-stage code generation          │
└─────────────────────────────────────────┘
        ↓
    Tungsten Execution Engine
```

---

### Key Optimization Rules in Catalyst

#### 1. Predicate Pushdown
Moves filter conditions as close to the data source as possible to reduce the amount of data read.

```python
# What you write:
df.join(other, "id").filter("country = 'IN'")

# What Catalyst executes:
# Filter is pushed BEFORE the join - reads less data, joins less rows
df.filter("country = 'IN'").join(other, "id")
```

#### 2. Column Pruning (Projection Pushdown)
Reads only the columns that are actually needed, not the entire row.

```python
# What you write:
df.select("name", "age").filter("age > 25")

# What Catalyst does:
# Only reads "name" and "age" columns from disk, ignores all others
# Especially powerful with columnar formats (Parquet, ORC)
```

#### 3. Constant Folding
Evaluates constant expressions at compile time rather than for every row.

```python
# What you write:
df.filter(col("price") > 10 * 5 + 20)

# What Catalyst computes:
# 10 * 5 + 20 = 70 - computed once, not for every row
df.filter(col("price") > 70)
```

#### 4. Join Reordering
Reorders joins to minimize intermediate data size (cost-based optimization).

#### 5. Broadcast Join Detection
Automatically detects when one side of a join is small enough to broadcast, converting a costly SortMergeJoin into a cheap BroadcastHashJoin.

---

### Cost-Based Optimizer (CBO)

Catalyst also has a **Cost-Based Optimizer** that uses table statistics to make smarter decisions:

```python
# Enable CBO
spark.conf.set("spark.sql.cbo.enabled", True)

# Collect statistics on your tables for CBO to use
spark.sql("ANALYZE TABLE my_table COMPUTE STATISTICS")
spark.sql("ANALYZE TABLE my_table COMPUTE STATISTICS FOR COLUMNS col1, col2")
```

With statistics, Catalyst can:
- Estimate join output sizes
- Choose better join order
- Decide between broadcast vs sort-merge join more accurately

---

### Adaptive Query Execution (AQE) - Spark 3.0+

AQE takes Catalyst a step further - it re-optimizes the plan **at runtime** based on actual data statistics collected during execution:

```python
# AQE is enabled by default in Spark 3.2+
spark.conf.set("spark.sql.adaptive.enabled", True)
```

AQE automatically:
- **Coalesces shuffle partitions**: merges small shuffle partitions into fewer, larger ones
- **Switches join strategies**: converts a SortMergeJoin to BroadcastHashJoin if one side turns out to be small at runtime
- **Handles data skew**: detects skewed partitions and splits them

## Part 2: Tungsten Engine

### What is it?

Tungsten is Spark's **physical execution engine**, introduced in Spark 1.4. It improves performance through three key techniques:

1. **Off-heap memory management** - avoids JVM garbage collection overhead
2. **Cache-aware data structures** - uses CPU cache efficiently
3. **Whole-stage code generation** - generates optimized JVM bytecode at runtime

---

### 1. Off-Heap Memory Management

Traditional Spark stored objects as JVM objects on the heap. This caused massive garbage collection pauses on large datasets.

Tungsten manages **binary data directly in memory** (off-heap), bypassing JVM GC:

```
Traditional JVM Object Storage:
  Java Object Header (16 bytes) + Field padding + GC overhead

Tungsten Binary Format:
  Compact binary representation - no object overhead, no GC pressure
```

This reduces memory usage by 2-5x and eliminates GC pauses.

---

### 2. Cache-Aware Computation

Tungsten uses data structures designed to maximize **CPU L1/L2 cache hits**. Modern CPUs are much faster when data is in cache vs. main memory.

- Uses **sort algorithms** that operate on binary data in cache-friendly access patterns
- Minimizes random memory access
- Exploits SIMD (Single Instruction, Multiple Data) CPU instructions where possible

---

### 3. Whole-Stage Code Generation (WSCG)

This is Tungsten's biggest performance win. Instead of interpreting the query plan row-by-row using a general interpreter, Tungsten **generates custom JVM bytecode** for each specific query.

```python
df.filter("amount > 100").select("user_id", "amount").agg({"amount": "sum"})
```

Without code generation (traditional interpreter):
```
For each row:
  → Call filter function → Check result → Call project function → Call sum function
  → Virtual function call overhead on every row, every operation
```

With Whole-Stage Code Generation:
```
Generated custom function (compiled JVM bytecode):
  For each row:
    if (amount > 100) { sum += amount; output(user_id, amount); }
  → Single tight loop, no virtual calls, JIT-compiled by JVM
```

This can be **10-100x faster** for CPU-bound operations.

You can see code generation in action:
```python
df.explain("codegen")  # Shows the generated Java code
```

---

### Tungsten in the Physical Plan

When you run `explain()`, you see `*` (asterisk) markers next to operators - these indicate **Tungsten whole-stage code generation** is active:

```
== Physical Plan ==
*(2) HashAggregate(...)     ← * means code gen active
+- Exchange hashpartitioning(...)
   +- *(1) Filter (amount > 100)    ← * means code gen active
      +- *(1) FileScan parquet
```

Operations without `*` (like Exchange/shuffle) fall outside whole-stage code gen because they involve data movement.

## How Catalyst and Tungsten Work Together

```python
# You write this simple query:
result = (
    spark.read.parquet("data/sales")
    .filter("year = 2024")
    .select("product_id", "revenue", "country")
    .filter("country = 'IN'")
    .groupBy("product_id")
    .agg({"revenue": "sum"})
)
result.show()
```

**Catalyst optimizes:**
- Combines both filters into one: `year = 2024 AND country = 'IN'`
- Pushes combined filter to data source (reads less)
- Prunes columns: only reads `product_id`, `revenue`, `country`, `year` from Parquet
- Detects best physical plan for groupBy

**Tungsten executes:**
- Manages memory without GC pressure
- Generates tight JVM bytecode for the filter + aggregation
- Uses cache-friendly sort for the aggregation

## Interview Tips 🎯

> **Q: What is the Catalyst optimizer in Spark?**

**Answer:** Catalyst is Spark SQL's query optimizer. It takes your logical query plan and applies a series of rules - like predicate pushdown, column pruning, constant folding, and join reordering - to produce an optimized logical plan. It then generates multiple physical plans and picks the cheapest one based on a cost model. The result is that Spark can often run queries faster than hand-optimized code.

> **Q: What is Tungsten and what problem does it solve?**

**Answer:** Tungsten is Spark's low-level execution engine that addresses two bottlenecks in JVM-based processing: **GC overhead** and **interpreter overhead**. It manages memory off-heap to reduce garbage collection pauses, and uses **whole-stage code generation** to compile query plans into optimized JVM bytecode instead of interpreting them row-by-row. This makes CPU-bound operations significantly faster.

> **Q: What is whole-stage code generation?**

**Answer:** Instead of interpreting each operation step-by-step for every row (which has virtual function call overhead), Tungsten generates a single custom JVM function for all operations in a stage and compiles it at runtime. This tight loop eliminates interpreter overhead and allows the JVM's JIT compiler to further optimize the hot code path. You can see it in the physical plan - operators marked with `*` are part of whole-stage code gen.

> **Q: What is Adaptive Query Execution (AQE)?**

**Answer:** AQE (Spark 3.0+) re-optimizes the query plan at runtime using statistics collected during execution. It can automatically merge small shuffle partitions, switch a SortMergeJoin to a BroadcastHashJoin if one side turns out small, and handle data skew by splitting large partitions. It's enabled by default in Spark 3.2+ and requires no code changes.

## Summary

- **Catalyst Optimizer** rewrites your query plan to be more efficient - applying predicate pushdown, column pruning, constant folding, and smart join selection
- **Tungsten Engine** executes the physical plan efficiently using off-heap memory, cache-aware algorithms, and whole-stage code generation
- Together they let you write simple, readable PySpark code while Spark handles the low-level performance optimization
- **AQE** (Spark 3.0+) extends Catalyst with runtime re-optimization based on actual data
- Use `explain()` to see what Catalyst and Tungsten are doing, and `explain("codegen")` to see generated code
