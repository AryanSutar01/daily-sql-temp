# Structured Streaming Basics

## How Structured Streaming Executes: The Micro-Batch Engine

Structured Streaming does not process data as individual events — it batches incoming data into small time intervals and runs a Spark batch job on each interval. Understanding this model clarifies latency characteristics, fault tolerance, and stateful operation semantics.

### The Micro-Batch Execution Cycle

```
Trigger interval: every 5 seconds (default: as fast as possible)

Cycle 1:
  1. Source query: "what new data arrived since last batch?"
     → Kafka: read offsets [partition0: 100→150, partition1: 200→260]
  2. Construct logical plan for this batch's data
  3. Run Spark batch job on the new data slice
  4. Write output to sink (console, Parquet, Delta, etc.)
  5. Commit new offsets to checkpoint WAL:
     → Write {"partition0": 150, "partition1": 260} to checkpoint dir
  
Cycle 2 (5 seconds later):
  1. Source query: read from committed offsets (partition0:150, partition1:260)
     → Get only the NEW records since last cycle
  2. Run batch job on new slice
  ...
```

The **WAL (Write-Ahead Log)** in the checkpoint directory ensures exactly-at-most-once delivery: if the job crashes mid-cycle, the uncommitted offsets mean the next restart will re-read from the last committed position.

### Stateful Operations and the State Store

Window aggregations (`window("timestamp", "5 minutes")`) and `groupBy` in streaming require **state** — partial aggregation results that accumulate across micro-batches:

```
Micro-batch 1:  events [10:00, 10:01, 10:03]
  State store after batch 1: {window "10:00-10:05": count=3}

Micro-batch 2:  events [10:02, 10:04, 10:06]
  State store after batch 2: {window "10:00-10:05": count=5,
                               window "10:05-10:10": count=1}
  
Output: count for "10:00-10:05" window is now 5 (merged across batches)
```

The State Store is stored on **HDFS/S3** (via the checkpoint directory), not in executor memory — it persists across restarts and cluster failures. It uses RocksDB (Spark 3.2+) for high-throughput key-value operations.

### Watermarking: Handling Late-Arriving Data

Events often arrive **out of order** due to network delays. Without watermarking, Spark would keep all historical state forever (OOM risk). Watermarking defines how long to wait for late data:

```python
df.withWatermark("event_time", "10 minutes") \
  .groupBy(window("event_time", "5 minutes")).count()

Effect:
  At processing time T:
    Watermark threshold = max(event_time seen) - 10 minutes
    Windows older than threshold are CLOSED and emitted
    Windows newer than threshold are still open (waiting for late data)
    
Example:
  Current max event_time = 10:30
  Watermark = 10:30 - 10 min = 10:20
  Window [10:00-10:05]: older than 10:20 → EMIT FINAL RESULT + drop state
  Window [10:20-10:25]: within watermark → keep open (late data expected)
```

Without a watermark, state for all windows accumulates forever → OOM. With watermark, the State Store periodically purges old windows, keeping memory bounded.

### Continuous Processing Mode (Experimental)

The default micro-batch mode has a minimum latency equal to the trigger interval. For sub-second latency requirements, Spark 2.3+ offers **continuous processing**:

```python
# Micro-batch: 1-minute latency minimum
query = df.writeStream.trigger(processingTime="1 minute").start()

# Continuous: ~1ms latency (experimental, limited operations)
query = df.writeStream.trigger(continuous="1 second").start()
# Note: only supports map/filter operations (no aggregations)
```

Continuous mode runs persistent tasks that poll the source continuously, rather than starting new batch jobs on each trigger. The trade-off: only stateless operations (map, filter) are supported.

## What is Structured Streaming?

**Structured Streaming** is Spark's built-in stream processing engine. It lets you write the same DataFrame/SQL code you use for batch processing, and run it on **continuously arriving data** - treating a live data stream as an unbounded table that keeps growing.

The key insight: instead of writing two separate pipelines (one for batch, one for streaming), you write one query and Spark handles the execution incrementally as new data arrives.

---

## Core Concept: Streaming as a Table

```
Streaming Input (e.g., Kafka topic):

  Time ──────────────────────────────────────────────────→
       [row1] [row2] [row3]        [row4] [row5]   [row6] ...
         t=1    t=2    t=3           t=10   t=11     t=15

Structured Streaming treats this as an unbounded table:

  ┌────────────────────────────────────────┐
  │       Unbounded Input Table            │
  │  row1                                  │
  │  row2                                  │
  │  row3          ← New rows keep coming  │
  │  row4                                  │
  │  ...                                   │
  └────────────────────────────────────────┘

Your query runs continuously on this growing table
and writes results to an output sink.
```

## Reading a Stream

### From Socket (for testing/learning)

```python
from pyspark.sql import SparkSession

spark = SparkSession.builder.appName("StreamingDemo").getOrCreate()

# Read from a socket (good for local testing)
# In terminal: nc -lk 9999   then type text
df_stream = spark.readStream \
    .format("socket") \
    .option("host", "localhost") \
    .option("port", 9999) \
    .load()

df_stream.printSchema()
# root
#  |-- value: string (nullable = true)
```

### From Kafka

```python
df_kafka = spark.readStream \
    .format("kafka") \
    .option("kafka.bootstrap.servers", "kafka-broker:9092") \
    .option("subscribe", "orders_topic") \
    .option("startingOffsets", "latest") \
    .load()

# Kafka gives you raw bytes - parse the JSON value
from pyspark.sql.functions import from_json, col
from pyspark.sql.types import StructType, StringType, IntegerType, DoubleType

schema = StructType() \
    .add("order_id", StringType()) \
    .add("customer_id", StringType()) \
    .add("amount", DoubleType()) \
    .add("timestamp", StringType())

df_parsed = df_kafka \
    .select(from_json(col("value").cast("string"), schema).alias("data")) \
    .select("data.*")
```

### From File Source (Auto-ingest new files)

```python
df_files = spark.readStream \
    .format("parquet") \
    .schema(my_schema) \
    .load("s3://my-bucket/incoming-data/")
# Spark monitors this directory and processes new files as they arrive
```

## Transformations on Streams

All standard DataFrame transformations work on streams:

```python
# Filter and select
df_result = df_parsed \
    .filter("amount > 100") \
    .select("order_id", "customer_id", "amount")

# Aggregations (with or without watermark)
from pyspark.sql.functions import count, sum

df_aggregated = df_parsed \
    .groupBy("customer_id") \
    .agg(
        count("order_id").alias("order_count"),
        sum("amount").alias("total_amount")
    )
```

## Writing a Stream (Output Sinks)

### Write to Console (for debugging)

query = df_result.writeStream \

query = df_result.writeStream \

query = df_aggregated.writeStream \

## Output Modes

Output mode defines **what data is written** to the sink after each trigger:

| Mode | Description | Use case |
|---|---|---|
| `append` | Only new rows added since last trigger | Row-level operations (filter, select) |
| `complete` | Full result table each trigger | Aggregations (whole result replaces previous) |
| `update` | Only changed rows since last trigger | Aggregations (only updated rows) |

```python
# Append: only new matching rows
df_filtered.writeStream.outputMode("append")...

# Complete: all aggregated results (for running totals, counts)
df_grouped.writeStream.outputMode("complete")...

# Update: only rows that changed (efficient for large aggregation tables)
df_grouped.writeStream.outputMode("update")...
```

## Triggers

Trigger controls how often the streaming query processes new data:

```python
# Process new data every 30 seconds
.trigger(processingTime="30 seconds")

# Process as fast as possible (default - runs mini-batches continuously)
.trigger(processingTime="0 seconds")

# Once: process all available data once, then stop (batch + stream hybrid)
.trigger(once=True)

# Available in Spark 3.3+: process one micro-batch and stop
.trigger(availableNow=True)
```

## Watermarks - Handling Late Data

In real streams, data can arrive late (network delays, retries). **Watermarks** tell Spark how long to wait for late data before closing a time window.

```python
from pyspark.sql.functions import window, col, to_timestamp

df_with_ts = df_parsed.withColumn("event_time", to_timestamp("timestamp"))

# Watermark: wait up to 10 minutes for late data
df_windowed = df_with_ts \
    .withWatermark("event_time", "10 minutes") \
    .groupBy(
        window(col("event_time"), "5 minutes"),   # 5-minute tumbling window
        col("customer_id")
    ) \
    .agg(sum("amount").alias("revenue"))

query = df_windowed.writeStream \
    .format("delta") \
    .option("checkpointLocation", "s3://checkpoints/windowed/") \
    .outputMode("append") \
    .start()
```

### Window types:
```python
# Tumbling window: non-overlapping fixed windows
window(col("event_time"), "5 minutes")

# Sliding window: overlapping windows
window(col("event_time"), "10 minutes", "5 minutes")  # 10-min window, slide every 5 min

# Session window (Spark 3.2+): gaps determine window boundaries
session_window(col("event_time"), "10 minutes")  # New window after 10 min of inactivity
```

## Checkpointing in Streaming (Required)

Unlike batch checkpointing, streaming checkpointing is **mandatory for recovery**. It stores:
- The current offset in the source (e.g., Kafka partition offset)
- State for stateful operations (counts, aggregations)

```python
query = df_aggregated.writeStream \
    .format("delta") \
    .option("checkpointLocation", "s3://my-bucket/checkpoints/my-stream/") \
    .start()
# If the query fails and restarts, it resumes from exactly where it left off
```

## Complete End-to-End Example

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import from_json, col, sum, window, to_timestamp
from pyspark.sql.types import StructType, StringType, DoubleType

spark = SparkSession.builder \
    .appName("OrderRevenueStream") \
    .config("spark.sql.extensions", "io.delta.sql.DeltaSparkSessionExtension") \
    .getOrCreate()

# Schema for incoming Kafka messages
schema = StructType() \
    .add("order_id", StringType()) \
    .add("region", StringType()) \
    .add("amount", DoubleType()) \
    .add("event_time", StringType())

# Read from Kafka
raw_stream = spark.readStream \
    .format("kafka") \
    .option("kafka.bootstrap.servers", "kafka:9092") \
    .option("subscribe", "orders") \
    .load()

# Parse JSON
orders = raw_stream \
    .select(from_json(col("value").cast("string"), schema).alias("d")) \
    .select("d.*") \
    .withColumn("event_time", to_timestamp("event_time"))

# Aggregate: revenue by region per 5-minute window, watermark 10 min
revenue_stream = orders \
    .withWatermark("event_time", "10 minutes") \
    .groupBy(
        window("event_time", "5 minutes"),
        col("region")
    ) \
    .agg(sum("amount").alias("total_revenue"))

# Write to Delta Lake every 1 minute
query = revenue_stream.writeStream \
    .format("delta") \
    .option("path", "s3://bucket/delta/revenue_by_region/") \
    .option("checkpointLocation", "s3://bucket/checkpoints/revenue-stream/") \
    .outputMode("append") \
    .trigger(processingTime="1 minute") \
    .start()

query.awaitTermination()
```

## Interview Tips 🎯

> **Q: What is Structured Streaming in PySpark?**

**Answer:** Structured Streaming is Spark's stream processing framework that treats a live data stream as an unbounded table. You write the same DataFrame transformations you'd use for batch processing, and Spark executes them incrementally as new data arrives in micro-batches. It supports Kafka, file sources, Delta Lake, and more.

> **Q: What are output modes in Structured Streaming?**

**Answer:** Output mode controls what data is written to the sink after each trigger. `append` writes only new rows (used for stateless operations like filter/select). `complete` writes the entire result table (used for aggregations where you want the full current state). `update` writes only the rows that changed since the last trigger (efficient for aggregations when you don't need the full table each time).

> **Q: What is a watermark in Structured Streaming?**

**Answer:** A watermark defines how long Spark should wait for late-arriving data before closing a time window. For example, `withWatermark("event_time", "10 minutes")` tells Spark that data arriving more than 10 minutes late relative to the maximum observed event time will be dropped. This is needed when computing window aggregations - without a watermark, Spark would have to keep all state indefinitely to handle infinitely late data.

## Summary

- **Structured Streaming** treats streams as unbounded tables - use DataFrame API on live data
- **Sources**: Kafka, files (S3/HDFS), socket (testing)
- **Sinks**: console (debug), files, Kafka, Delta Lake
- **Output modes**: `append` (new rows), `complete` (full result), `update` (changed rows)
- **Triggers**: control micro-batch frequency (every N seconds, continuous, once)
- **Watermarks**: handle late data in windowed aggregations
- **Checkpointing** is mandatory for streaming - enables exactly-once recovery
