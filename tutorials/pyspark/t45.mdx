# Spark UI & DAG Visualization

## How the Spark UI Maps to Execution Internals

The Spark UI is not just a monitoring dashboard — every tab directly corresponds to a specific layer of Spark's execution model. Knowing which tab maps to which layer tells you exactly where to look for performance problems.

### The Execution Model → UI Mapping

```
Your PySpark code
      ↓
Action triggered (e.g., .count(), .write(), .show())
      ↓ creates a
Job  ← UI: Jobs tab (one row per .count()/.write() call)
      ↓ divided into
Stages  ← UI: Stages tab (one row per Exchange/shuffle boundary)
      ↓ each stage runs
Tasks  ← UI: Stage Detail → Task table (one row per partition)
         Running on
Executors  ← UI: Executors tab (one row per JVM process)
         Storing cached data in
Storage  ← UI: Storage tab (one row per cached DataFrame)
```

### Reading the Stage Detail: Identifying Bottlenecks

The **Stage Detail** page is the most powerful view. The task metric distribution reveals the root cause of slow stages:

```
Task metrics to inspect (for a 200-task stage):

Duration column:
  Min: 2s  Median: 5s  Max: 480s  ← MAX is 96x the median!
  → DATA SKEW: one partition has 96x more data than average
  → Solution: repartition by key, salting, or AQE skew join

GC Time column:
  Min: 0s  Median: 4s  Max: 8s  ← GC is 80% of median task time!
  → JVM GC PRESSURE: executor heap too small, too many objects
  → Solution: increase executor memory, use G1GC, reduce UDFs

Shuffle Read column:
  Min: 10MB  Median: 12MB  Max: 11MB  ← all ~equal
  → NO SKEW in shuffle read (uniform distribution, good)

Shuffle Write column:
  If Max >> Median → skew in pre-shuffle data (groupBy key is skewed)
```

### The Event Timeline: Understanding Parallelism Gaps

The Event Timeline in the Stage Detail shows each task's phases:
- **Scheduler delay** (blue): time between task submission and task start → too many tasks per executor, or slow TaskScheduler
- **Task deserialization** (red): unpacking task closure → large closure means large broadcast needed instead
- **Shuffle read** (orange): fetching shuffle data from other executors → long shuffle read means network bottleneck or skew
- **Executor computing** (green): actual computation → want this to be the dominant color
- **Result serialization** (purple): sending result back to driver → if large, avoid collect()-style actions on big data

An ideal timeline: **green dominates**. If you see large orange or blue gaps, that's your optimization target.

### Adaptive Query Execution (AQE) in the UI (Spark 3.0+)

When AQE is enabled, the SQL tab shows the query re-optimization:
```
SQL plan before AQE:
  SortMergeJoin (planned based on estimated statistics)

SQL plan after AQE (after seeing actual runtime stats):
  BroadcastHashJoin (AQE detected actual table size was < threshold)
  → Switched join strategy at runtime without restarting the job!
```

To see AQE re-optimizations: SQL tab → click query → look for orange "AQE" badges on plan nodes that were changed at runtime.

## What is the Spark UI?

The **Spark UI** is a web-based dashboard that Spark automatically starts when you run a Spark application. It gives you a real-time and historical view of everything happening in your Spark job - jobs, stages, tasks, executors, memory, and more.

It is your **primary tool for debugging and optimizing** PySpark applications in production.

**Default URL:** `http://<driver-host>:4040`
- On Databricks: available via the **Clusters → Spark UI** button
- On EMR: via the cluster's public DNS
- On local: `http://localhost:4040`

If you run multiple apps simultaneously, additional apps get ports 4041, 4042, etc.

## Navigating the Spark UI - Key Tabs

### 1. Jobs Tab
Shows all **Spark jobs** - one job is created per action (`.count()`, `.show()`, `.write()`).

- Each job shows: job ID, description, submission time, duration, stages, tasks
- Click a job to drill into its stages

```
Job 3  │ count at example.py:42  │  2 min 14 sec  │  Stages: 3/3  │  Tasks: 200/200
```

### 2. Stages Tab
Shows all **stages** within each job. A stage is a group of tasks that can run in parallel without a shuffle.

Key metrics per stage:
- **Duration** - total time for the stage
- **Input** - data read from disk
- **Shuffle Read / Write** - data shuffled (expensive if high)
- **Output** - data written to disk

**Red flags:**
- One stage taking much longer than others → likely skew
- Very high Shuffle Read/Write → too many shuffles, consider optimization

### 3. Tasks Tab (within a Stage)
Shows individual **tasks** - one task per partition.

Look for:
- **Task duration distribution** - if most tasks take 1s but one takes 5min → data skew
- **GC Time** - high GC time means memory pressure
- **Shuffle Spill (Memory/Disk)** - data too large to fit in memory during shuffle

### 4. Storage Tab
Shows **cached/persisted DataFrames and RDDs**:
- Storage level (memory, disk)
- How much memory is used
- % cached vs. not cached

### 5. Environment Tab
Shows all **Spark configuration properties** - useful to verify configs like shuffle partitions, memory settings, etc.

### 6. Executors Tab
Shows all **executor instances** and their resource usage:
- Memory used vs. available
- CPU cores active
- Tasks completed / failed
- GC time

Look for:
- One executor with much more data than others → skew
- High GC time → memory pressure, consider increasing executor memory
- Failed tasks → OOM errors or network issues

### 7. SQL Tab (Spark SQL queries)
Shows the **execution plan** with timing for each node in the plan tree - great for identifying bottlenecks in SQL/DataFrame queries.

## Understanding the DAG (Directed Acyclic Graph)

The **DAG** represents the execution plan of your Spark job as a graph where:
- **Nodes** = transformations (filter, join, groupBy, etc.)
- **Edges** = data flow between transformations
- **Acyclic** = no loops (data flows in one direction)

### How Spark builds the DAG

```python
df1 = spark.read.parquet("data/orders")         # Node: FileScan
df2 = df1.filter("status = 'completed'")         # Node: Filter
df3 = spark.read.parquet("data/customers")       # Node: FileScan
df4 = df2.join(df3, "customer_id")              # Node: Join (triggers shuffle)
df5 = df4.groupBy("region").count()             # Node: GroupBy (triggers shuffle)
df5.write.parquet("output/result")              # Action → builds & executes DAG
```

**The DAG for this job:**
```
FileScan(orders) ──→ Filter ──→ SortMergeJoin ──→ HashAggregate ──→ Write
                                      ↑
FileScan(customers) ──────────────────┘

Stage 1: FileScan(orders) → Filter → Shuffle Write
Stage 2: FileScan(customers) → Shuffle Write
Stage 3: Shuffle Read → SortMergeJoin → HashAggregate → Shuffle Write
Stage 4: Shuffle Read → HashAggregate → Write
```

### DAG Stages and Stage Boundaries

**Stage boundaries** are created wherever a **shuffle** occurs. Within a stage, tasks run fully in parallel.

```
                Stage 1              Stage 2              Stage 3
┌──────────────────────────┐  ┌─────────────────┐  ┌──────────────────┐
│  Read → Filter → Write   │  │  Read → Write   │  │  Join → GroupBy  │
│  (shuffle write)         │  │  (shuffle write) │  │  (shuffle read)  │
└──────────────────────────┘  └─────────────────┘  └──────────────────┘
        │                              │                     ↑
        └──────────────────────────────┘─────────────────────┘
                         [Shuffle / Network transfer]
```

## Viewing the DAG in the UI

1. Go to **Jobs tab** → click on a job
2. Click on a **Stage**
3. Click **"DAG Visualization"** button at the top

The DAG visualization shows:
- Blue boxes = RDD/DataFrame operations (nodes)
- Arrows = data flow
- Red boxes = cached data (shortcut in the lineage)
- Stage boundaries (where shuffles happen)

## Practical: Reading the Spark UI for Performance Issues

### Scenario 1: Job is slower than expected

**Check:** Stages tab → look at stage durations
**Find:** One stage takes 90% of total time
**Drill down:** Check that stage's task metrics
**Identify:** Most tasks: 2s, but 3 tasks: 10min → **data skew**
**Fix:** Salting, AQE skew join, or broadcast join

### Scenario 2: Out of Memory errors

**Check:** Executors tab → GC Time column
**Find:** GC time is 50%+ of task duration
**Identify:** Executors are running out of memory
**Fix:** Increase `spark.executor.memory`, reduce data per partition, add caching

### Scenario 3: Job is slower after adding more data

**Check:** Stages tab → Shuffle Read/Write size
**Find:** Shuffle data is huge (hundreds of GB)
**Identify:** Too many joins, or shuffle.partitions=200 but partitions are huge
**Fix:** Increase `spark.sql.shuffle.partitions`, filter early, use broadcast joins

## Key Spark UI Metrics Cheat Sheet

| Metric | Where | What to look for |
|---|---|---|
| Task duration | Stage detail | Outliers (skew) vs. median |
| GC Time | Stage / Executor | >10% of task time = memory pressure |
| Shuffle Read/Write | Stage list | Large values = expensive shuffle |
| Spill (Memory) | Stage detail | Any value = partition too large for memory |
| Spill (Disk) | Stage detail | Any value = serious memory issue |
| % Cache | Storage tab | < 100% = not enough memory to cache |
| Failed Tasks | Stage / Executor | OOM, network issues |

## Interview Tips 🎯

> **Q: What is the Spark UI and what can you use it for?**

**Answer:** The Spark UI is a web dashboard (default port 4040) that provides visibility into running and completed Spark jobs. It shows jobs, stages, tasks, executor usage, cached data, and SQL execution plans. It's the primary tool for diagnosing performance issues - you can identify data skew (uneven task durations), excessive shuffles (high shuffle read/write), memory pressure (high GC time), and spilling (data overflowing memory to disk).

> **Q: What is a DAG in Spark?**

**Answer:** A DAG (Directed Acyclic Graph) is the execution plan of a Spark job represented as a graph. Nodes are transformations (filter, join, groupBy), edges represent data flow, and it's acyclic meaning data flows in one direction without loops. Spark builds the DAG when you call an action, and then executes it stage by stage, where each stage boundary is a shuffle operation.

> **Q: How do you identify data skew in the Spark UI?**

**Answer:** Go to the Stages tab and click on the slow stage. In the task metrics, look at the distribution of task durations. If most tasks complete in seconds but a few take minutes, that indicates data skew - those slow tasks are processing much more data than others. You can also check the "Shuffle Read Size" per task to confirm one partition has significantly more data.

## Summary

- **Spark UI** (port 4040) is the primary debugging tool for Spark jobs - monitor jobs, stages, tasks, memory, and executors
- **Jobs Tab**: one job per action; **Stages Tab**: one stage per shuffle boundary; **Tasks Tab**: one task per partition
- **DAG Visualization** shows the execution plan as a graph with stage boundaries where shuffles occur
- Key metrics to monitor: **task duration distribution** (skew), **GC time** (memory), **shuffle size** (network cost), **disk spill** (OOM risk)
- In Databricks, the Spark UI is accessible from the Clusters page under each running cluster
