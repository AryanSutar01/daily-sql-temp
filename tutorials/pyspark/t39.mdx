# Shuffling & Its Performance Cost

## The Three-Phase Shuffle Lifecycle

A shuffle in Spark is not a single operation — it is a **three-phase distributed process** that crosses stage boundaries and involves both disk I/O and network transfer. Understanding each phase explains why shuffles dominate job latency.

### Phase 1: Shuffle Write (Map Side)

Each task in the preceding stage (the "map" stage) writes its output sorted by partition key:

```
Executor A, Task for Partition 0:
  Processes rows:
    {user=Alice,  country=IN,  amount=100}
    {user=Bob,    country=US,  amount=200}
    {user=Carol,  country=IN,  amount=150}

  groupBy("country") → hash("IN") % 200 = 42, hash("US") % 200 = 87

  Sort rows by destination partition:
    Dest partition 42: [{Alice, IN, 100}, {Carol, IN, 150}]
    Dest partition 87: [{Bob, US, 200}]

  Write to LOCAL DISK as shuffle files:
    /tmp/spark-shuffle/app_id/executor_0/
      shuffle_0_0_42.data   (42 = dest partition)
      shuffle_0_0_87.data
      shuffle_0_0_42.index  (byte offsets for fast seek)
```

**Key cost**: Every shuffle map task writes ALL its output to local disk before any reduce task can start. This is why shuffle disk I/O is a bottleneck.

### Phase 2: Network Transfer

Reduce-side tasks (in the next stage) **pull** their shuffle data from all map-side executors:

```
Executor B, Task for Partition 42 (country=IN):
  Needs shuffle data from ALL previous-stage executors
  
  Sends HTTP requests to Spark's shuffle service:
    GET executor_A/shuffle_0_0_42.data  → 2 rows (Alice, Carol)
    GET executor_B/shuffle_0_0_42.data  → 3 rows (Dave, Eve, Frank)
    GET executor_C/shuffle_0_0_42.data  → 0 rows (no IN users on executor C)
    ...
  
  This is a network fan-out: each reduce task reads from ALL map tasks
  200 partitions × 100 executors = 20,000 individual HTTP fetches per stage
```

### Phase 3: Shuffle Read (Reduce Side)

Received data is merged, sorted (for sort-merge join / orderBy), and processed:

```
Executor B receives:
  [Alice, IN, 100], [Carol, IN, 150], [Dave, IN, 80], [Eve, IN, 200]

If groupBy+sum: HashAggregate → sum(amount) = 530
If orderBy:    Sort → [Alice:100, Dave:80, Carol:150, Eve:200]
```

### Sort-Based vs Hash-Based Shuffle

Spark's default is **sort-based shuffle** (since Spark 1.6):

```
Sort-Based (default: SortShuffleManager):
  Map side: sort rows by partition key → write to ONE merged file per executor
  + Only 1 file per map task (less file system pressure)
  + Better for sequential disk I/O
  - Requires sorting cost on map side

Hash-Based (legacy, deprecated):
  Map side: write separate file per destination partition
  + No sorting cost
  - N_partitions files per map task → too many open files for large N
  - Causes "too many open files" errors with 200+ partitions
```

### Shuffle Spill-to-Disk

When the sort buffer on the map side exceeds `spark.shuffle.spill.compress` memory threshold:

```
Map side sort buffer: 64MB default
  Accumulates rows sorted by partition key...
  Buffer reaches 64MB → SPILL to disk:
    Write sorted partial buffer to spill file on local disk
    
  Continue accumulating...
  Buffer reaches 64MB again → SPILL again

  At end of task: merge all spill files + remaining buffer
  → Final sorted shuffle output file

Multiple spills = multiple disk read+writes per task!
```

Setting `spark.shuffle.sort.bypassMergeThreshold` (default 200) — if the number of output partitions is below this threshold, Spark bypasses sorting (no spill needed for small partition counts).

## What is a Shuffle?

A **shuffle** is the process of redistributing data across partitions - typically across different executors and machines in a cluster. It happens when Spark needs to bring together data that is spread across multiple nodes to complete an operation.

Shuffling is one of the **most expensive operations** in Spark because it involves:
- Reading data from disk
- Serializing and writing data to disk again (shuffle write)
- Sending data over the network between executors
- Deserializing and reading the data on the receiving end (shuffle read)

---

## What Triggers a Shuffle?

The following operations trigger a shuffle in PySpark:

| Operation | Why it shuffles |
|---|---|
| `groupBy()` + aggregation | Groups matching keys must be on the same partition |
| `join()` (unless broadcast) | Matching keys from both sides must co-locate |
| `distinct()` | Deduplication requires all copies of a value together |
| `repartition(n)` | Explicitly redistributes data |
| `orderBy()` / `sort()` | Global sort requires data movement |
| `reduceByKey()` / `aggregateByKey()` (RDD) | Key-based aggregation |

```python
# These operations all trigger a shuffle:
df.groupBy("country").count()                # shuffle to group by country
df1.join(df2, "user_id")                     # shuffle both sides on user_id
df.distinct()                                 # shuffle to find duplicates
df.orderBy("created_at")                      # shuffle for global sort
df.repartition(20)                            # explicit shuffle
```

## The Shuffle Lifecycle

When a shuffle happens, Spark splits the job into two stages:

```
Stage 1 (Map side / Shuffle Write)
  └── Each task reads its partition
  └── Partitions output into shuffle files (bucketed by key hash)
  └── Data written to local disk on executors

                [Network Transfer]

Stage 2 (Reduce side / Shuffle Read)
  └── Each task fetches relevant shuffle files from remote executors
  └── Data is sorted, merged, and processed
  └── Result passed to the next operation
```

This disk I/O + network transfer is what makes shuffles **slow and expensive**.

---

## Performance Cost of Shuffling

### 1. Network I/O
Data travels between executors over the network. On large datasets, this can be **gigabytes or terabytes** of data being transferred.

### 2. Disk I/O
Shuffle data is written to disk twice - once on the write side and once on the read side. This is slow compared to in-memory operations.

### 3. GC Pressure
Large shuffles increase garbage collection overhead in the JVM, causing pauses that slow down your job.

### 4. Out-of-Memory Errors
If a shuffle produces very large partition sizes (due to data skew), it can cause OOM errors on executors.

## How to Minimize Shuffle Cost

### 1. Use Broadcast Joins for Small Tables

When one table is small enough to fit in memory, broadcast it to all executors - eliminating the join shuffle entirely.

```python
from pyspark.sql.functions import broadcast

# Without broadcast: both tables shuffle
df_large.join(df_small, "product_id")

# With broadcast: no shuffle - df_small is sent to all executors
df_large.join(broadcast(df_small), "product_id")
```

Spark auto-broadcasts tables under `spark.sql.autoBroadcastJoinThreshold` (default: **10MB**).

```python
# Increase threshold if your "small" table is larger
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", 50 * 1024 * 1024)  # 50MB
```

### 2. Filter Early (Reduce Data Before Shuffle)

Push filters before joins or groupBys to reduce the amount of data being shuffled:

```python
# Bad: join first, then filter (shuffles all data)
df1.join(df2, "user_id").filter("country = 'IN'")

# Better: filter first, then join (shuffles less data)
df1.filter("country = 'IN'").join(df2, "user_id")
```

### 3. Tune spark.sql.shuffle.partitions

The number of shuffle partitions (default 200) controls how many tasks run in the reduce stage. Wrong values hurt performance:

```python
# Default: 200 (often too many for small datasets, too few for large ones)
spark.conf.set("spark.sql.shuffle.partitions", 50)   # for medium datasets
spark.conf.set("spark.sql.shuffle.partitions", 500)  # for large datasets
```

> Rule of thumb: shuffle partition size should be **100–200MB each**. Adjust based on your data size.

### 4. Use coalesce() Instead of repartition() When Reducing

`repartition()` always shuffles. `coalesce()` avoids shuffle when reducing partition count:

```python
# Avoid shuffle when just reducing partitions
df.coalesce(5).write.parquet("output/")
```

### 5. Avoid groupByKey() - Prefer reduceByKey() (RDD API)

In the RDD API, `groupByKey()` shuffles all values across the network before reducing. `reduceByKey()` pre-reduces on the map side first (combine step), drastically reducing shuffle size:

```python
# Bad: sends all values over the network
rdd.groupByKey().mapValues(sum)

# Better: combines locally first, then shuffles partial results
rdd.reduceByKey(lambda a, b: a + b)
```

In DataFrame API, Spark's Catalyst optimizer handles this automatically.

## Shuffle in the Spark UI

You can see shuffle cost clearly in the **Spark UI**:
- **Shuffle Write**: data written by map tasks (Stage N)
- **Shuffle Read**: data read by reduce tasks (Stage N+1)

If you see large shuffle read/write numbers, that's a signal to optimize.

## Practical Example: Measuring Shuffle Impact

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import broadcast

spark = SparkSession.builder.appName("ShuffleDemo").getOrCreate()

orders = spark.read.parquet("data/orders")          # 10GB table
products = spark.read.parquet("data/products")      # 5MB table

# Without broadcast: both tables shuffle on product_id
orders.join(products, "product_id").explain()
# PhysicalPlan: SortMergeJoin → both sides have Exchange (shuffle)

# With broadcast: no shuffle
orders.join(broadcast(products), "product_id").explain()
# PhysicalPlan: BroadcastHashJoin → no Exchange on products side
```

## Interview Tips 🎯

> **Q: What causes a shuffle in Spark and why is it expensive?**

**Answer:** A shuffle occurs when Spark needs to redistribute data across partitions - for operations like `groupBy`, `join`, `distinct`, and `orderBy`. It's expensive because it involves writing data to local disk (shuffle write), transferring it over the network, and reading it again (shuffle read). This disk I/O and network transfer makes shuffles the most costly part of many Spark jobs.

> **Q: How would you reduce shuffle in a join operation?**

**Answer:** Use a **broadcast join** if one side is small (under ~50MB). Broadcast the smaller DataFrame to all executors so each executor can do the join locally without any network shuffle. Also, filter data before the join to reduce the volume being shuffled.

> **Q: What is spark.sql.shuffle.partitions and what value should you use?**

**Answer:** It controls how many output partitions are created after a shuffle (default: 200). For small datasets, 200 is too many (creates tiny tasks). For large datasets, it may be too few (creates large partitions). Aim for ~100–200MB per partition and tune accordingly. In Spark 3+, Adaptive Query Execution (AQE) can auto-tune this at runtime.

---

## Summary

- A **shuffle** redistributes data across partitions via disk I/O and network transfer
- Operations like `groupBy`, `join`, `distinct`, `sort`, and `repartition` trigger shuffles
- Shuffles are expensive - they are often the **#1 bottleneck** in Spark jobs
- Minimize shuffles by: **broadcasting small tables**, **filtering early**, **tuning shuffle partitions**, and **using coalesce instead of repartition**
- Monitor shuffle read/write size in **Spark UI** to identify optimization opportunities
