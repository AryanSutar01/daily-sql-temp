## The Memory Cost of Python's Dynamic Attribute System

Python's flexibility — the ability to add any attribute to any object at any time — comes at a memory cost. When you create a Python object (an instance of a class), Python automatically gives it a **private dictionary called `__dict__`** to store all its instance attributes. This dictionary is a full Python `dict` object with its own hash table, overhead, and memory allocation.

For a simple class with 3 attributes, a single instance might consume:
- ~56 bytes for the object itself (type pointer + reference count + `__dict__` pointer)
- ~232 bytes for the `__dict__` dictionary (minimum dict size with its hash table)

Total: ~288 bytes per instance, just to hold 3 numbers.

When you're building a web server that holds 1 million user sessions in memory, or a data pipeline processing 10 million sensor readings, this per-instance overhead of 200+ bytes for the dictionary alone becomes hundreds of megabytes of wasted memory.

## The Default: `__dict__` Per Instance

Every Python object without `__slots__` stores its instance attributes in a dictionary called `__dict__`. Python creates this dictionary automatically — you never write it, but it's always there. Its existence gives you the flexibility to add, remove, and modify attributes dynamically at runtime.

```python
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

p = Point(1, 2)

# __dict__ is a real Python dict, inspectable at any time
print(p.__dict__)   # {'x': 1, 'y': 2}
print(type(p.__dict__))   # <class 'dict'>

# Python's dynamic attribute system lets you add attributes at runtime
p.z = 3
p.label = "origin"
p.description = "the point at origin"
print(p.__dict__)   # {'x': 1, 'y': 2, 'z': 3, 'label': 'origin', 'description': 'the point at origin'}
```

When you write `p.x`, Python first checks the class's attribute lookup chain (type's `__dict__`, then MRO), then falls back to `p.__dict__["x"]`. This dictionary lookup involves computing a hash of the string "x" and finding it in the hash table — it's fast but not free.

## `__slots__` — Fixed Attribute Storage

`__slots__` is a class-level declaration that tells Python: "this class will only ever have these specific attributes." Instead of giving each instance a `__dict__`, Python stores the declared attributes directly on the object at **fixed memory offsets** — like fields in a C struct.

```python
class SlottedPoint:
    __slots__ = ("x", "y")   # declare the only allowed attributes

    def __init__(self, x, y):
        self.x = x
        self.y = y

p = SlottedPoint(1, 2)
print(p.x)   # 1 — works normally, accessed via fixed offset, not dict lookup

# Attempting to add an undeclared attribute raises an error immediately
p.z = 3   # AttributeError: 'SlottedPoint' object has no attribute 'z'

# No __dict__ exists — the attribute storage IS the slots themselves
p.__dict__   # AttributeError: 'SlottedPoint' object has no attribute '__dict__'
```

The `AttributeError` on `p.z = 3` is not a bug — it's a feature. Slotted classes enforce their attribute contract. This makes the class's interface explicit and catches typos immediately (`p.nmae = "Alice"` raises an error rather than silently creating a misspelled attribute).

## Memory Comparison — The Savings Are Dramatic

The memory savings from `__slots__` are substantial and can be measured precisely:

```python
import sys

class Regular:
    def __init__(self, x, y, z):
        self.x = x
        self.y = y
        self.z = z

class Slotted:
    __slots__ = ("x", "y", "z")

    def __init__(self, x, y, z):
        self.x = x
        self.y = y
        self.z = z

r = Regular(1, 2, 3)
s = Slotted(1, 2, 3)

# For Regular, you must add __dict__ size separately — it's the main overhead
regular_size = sys.getsizeof(r) + sys.getsizeof(r.__dict__)
slotted_size = sys.getsizeof(s)

print(f"Regular: {regular_size} bytes")   # ~232 bytes (object + dict overhead)
print(f"Slotted: {slotted_size} bytes")   # ~56 bytes (object + 3 slot pointers)
print(f"Reduction: {regular_size / slotted_size:.1f}x smaller")   # ~4x smaller
```

The dictionary overhead is the main cost. An empty Python `dict` requires a minimum of ~232 bytes for its hash table. Even with only 3 entries, you're paying that full cost. With `__slots__`, there's no dict — just 3 pointers at fixed positions on the object, costing about 8 bytes each.

### At Scale — Why This Matters in Production

```python
import tracemalloc

class RegularSensor:
    def __init__(self, sid, ts, val):
        self.sensor_id = sid
        self.timestamp = ts
        self.value = val

class SlottedSensor:
    __slots__ = ("sensor_id", "timestamp", "value")
    def __init__(self, sid, ts, val):
        self.sensor_id = sid
        self.timestamp = ts
        self.value = val

n = 1_000_000

tracemalloc.start()
regular_list = [RegularSensor(i, float(i), i * 0.1) for i in range(n)]
size_regular = tracemalloc.get_traced_memory()[1]
tracemalloc.stop()

tracemalloc.start()
slotted_list = [SlottedSensor(i, float(i), i * 0.1) for i in range(n)]
size_slotted = tracemalloc.get_traced_memory()[1]
tracemalloc.stop()

print(f"Regular: {size_regular / 1e6:.1f} MB")   # ~320 MB
print(f"Slotted: {size_slotted / 1e6:.1f} MB")   # ~80 MB
# Saving: ~240 MB for 1 million objects — the difference between fitting in RAM or not
```

In a sensor data pipeline processing 1 million readings, using `__slots__` can save 200–300 MB of RAM. That's the difference between the process fitting in memory and triggering OS swapping (which can slow the pipeline by 100x or more).

## Performance — Faster Attribute Access

Beyond memory, `__slots__` also speeds up attribute access. With `__dict__`, accessing `p.x` involves:
1. Look up `"x"` in the class chain (check for descriptors, class attributes)
2. Fall back to `p.__dict__["x"]` — a hash table lookup

With `__slots__`, accessing `p.x` goes through a **descriptor** defined on the class that directly reads from a fixed memory offset on the object. It's closer to `*(object_ptr + offset)` in C.

```python
import timeit

class Regular:
    def __init__(self):
        self.x = 42

class Slotted:
    __slots__ = ("x",)
    def __init__(self):
        self.x = 42

r = Regular()
s = Slotted()

# Run each access 10 million times to measure reliably
t_regular = timeit.timeit(lambda: r.x, number=10_000_000)
t_slotted = timeit.timeit(lambda: s.x, number=10_000_000)

print(f"Regular: {t_regular:.3f}s")
print(f"Slotted: {t_slotted:.3f}s")
# Typical: slotted is 10–20% faster — modest but measurable in tight loops
```

The speed improvement is not dramatic for single attribute accesses, but in tight loops accessing many attributes millions of times, the cumulative effect matters.

## Inheritance with `__slots__`

Inheritance interacts with `__slots__` in ways that require care. The key rules:
1. A subclass should only declare **new** slots — not repeat the parent's slots
2. If a subclass does **not** declare `__slots__`, it automatically gets `__dict__` back, negating the parent's memory savings

```python
class Animal:
    __slots__ = ("name", "age")

    def __init__(self, name, age):
        self.name = name
        self.age = age

class Dog(Animal):
    __slots__ = ("breed",)   # only ADD new slots — "name" and "age" inherited

    def __init__(self, name, age, breed):
        super().__init__(name, age)
        self.breed = breed

d = Dog("Max", 3, "Labrador")
print(d.name)    # Max — inherited slot from Animal
print(d.breed)   # Labrador — Dog's own slot
# Dog has no __dict__, saves memory, despite being a subclass

# If a subclass forgets to declare __slots__, __dict__ comes back
class Cat(Animal):
    pass   # no __slots__ → Cat instances have __dict__ again

c = Cat("Whiskers", 2)
c.color = "orange"   # works — Cat got __dict__ back despite Animal having __slots__
```

This is why using `__slots__` in a class hierarchy requires discipline — every class in the hierarchy that needs the memory savings must declare `__slots__`.

## Adding `__dict__` Back Selectively

Sometimes you want most attributes to be slots for performance, but still allow dynamic attributes in exceptional cases. You can include `"__dict__"` in `__slots__` itself:

```python
class Flexible:
    __slots__ = ("x", "y", "__dict__")   # x, y are slots; __dict__ allows extras

    def __init__(self, x, y):
        self.x = x
        self.y = y

f = Flexible(1, 2)
f.z = 3          # works — stored in __dict__
f.x = 10         # works — stored in slot (faster)

print(f.x)       # 10 — from slot
print(f.z)       # 3  — from __dict__
```

This pattern gives you the speed benefit for your core attributes (accessed frequently via slots) while retaining flexibility for occasional dynamic attributes. The `__dict__` adds back some overhead but only for objects that actually use dynamic attributes.

## `__slots__` with `@dataclass`

Python 3.10 added `slots=True` to `@dataclass`, making it easy to create memory-efficient data classes without manually declaring `__slots__`:

```python
from dataclasses import dataclass

# Before Python 3.10 — manual approach (awkward)
@dataclass
class OldStylePoint:
    __slots__ = ("x", "y")   # had to be repeated outside fields
    x: float
    y: float

# Python 3.10+ — clean, idiomatic approach
@dataclass(slots=True)
class Point:
    x: float
    y: float

p = Point(1.0, 2.0)
print(p.x)             # 1.0
print(p.__slots__)      # ('x', 'y')
# p.__dict__           # AttributeError — no __dict__ ✓

# You still get all dataclass features: __init__, __repr__, __eq__, etc.
print(p)               # Point(x=1.0, y=2.0)
```

`@dataclass(slots=True)` is the recommended way to write memory-efficient data classes in modern Python. It's clean, explicit, and automatically handles the correct interaction between `__slots__` and dataclass-generated methods.

## When to Use `__slots__`

The decision is a trade-off. `__slots__` is not "always better" — it has real constraints that make it wrong in some situations.

```
USE __slots__ when:
  ✓ Creating thousands or millions of instances (sensors, records, coordinates, nodes)
  ✓ Memory is a constraint (embedded systems, large in-memory datasets)
  ✓ All attributes are known upfront and fixed
  ✓ Attribute access speed matters (data-intensive inner loops)

DO NOT USE __slots__ when:
  ✗ You need to add attributes dynamically at runtime (plugins, monkey-patching)
  ✗ Using frameworks that inspect __dict__ (some ORMs, some serializers, pickle without __getstate__)
  ✗ Writing a base class for unknown subclasses (forces them to use __slots__ too)
  ✗ The memory saving is irrelevant for your use case (< 1000 instances)
```

## Interview Questions

**Q: What is `__slots__` and what problem does it solve?**
`__slots__` is a class-level declaration of a fixed set of instance attributes. It replaces the automatic per-instance `__dict__` (a full hash table) with fixed-offset storage on the object — similar to C struct fields. The result is 3–4x less memory per instance and slightly faster attribute access. It's essential when creating millions of instances of a class.

**Q: Why does `__slots__` save memory?**
Without `__slots__`, every instance has a `__dict__` — a full Python dictionary with a minimum overhead of ~200 bytes regardless of how few attributes you store. With `__slots__`, attributes are stored at fixed offsets directly on the object — about 8 bytes per attribute pointer, with no hash table. For an object with 3 attributes, this reduces per-instance overhead from ~230 bytes to ~56 bytes (~4x).

**Q: What are the trade-offs of using `__slots__`?**
Benefits: 3–4x memory reduction per instance, 10–20% faster attribute access. Drawbacks: cannot add arbitrary attributes dynamically at runtime (no `__dict__`), breaks some frameworks that rely on `__dict__` inspection, subclasses must also declare `__slots__` to maintain the savings, and some introspection tools don't handle slotted classes correctly. Only use it when the memory savings are meaningful.

**Q: Does `__slots__` affect inheritance?**
Yes, carefully. A subclass must also declare `__slots__` to maintain memory savings — if it doesn't, Python gives it `__dict__` back. The subclass only declares **new** slots (not the parent's), which are inherited automatically. Mixing slotted and non-slotted classes in a hierarchy requires understanding which classes have `__dict__` and which don't.

**Q: How does Python 3.10's `@dataclass(slots=True)` work?**
It's a convenient shorthand for creating a dataclass with `__slots__`. Python 3.10 generates the slots from the field annotations automatically, creating an equivalent class to one where you manually defined `__slots__` with the same names. This avoids the awkward duplication of defining both `__slots__` and the dataclass fields separately.

## Summary

- Without `__slots__`, every instance has a `__dict__` — a Python dict with ~200 bytes minimum overhead
- `__slots__ = ("x", "y")` — replaces `__dict__` with fixed-offset attribute storage on the object
- **Memory savings**: ~3–4x per instance — critical when creating millions of objects
- **Speed**: attribute access slightly faster — fixed offset vs hash table lookup
- **Trade-off**: no dynamic attribute addition, no `__dict__`, more complex inheritance
- Subclasses must also declare `__slots__` — otherwise they get `__dict__` back
- Include `"__dict__"` in `__slots__` to allow dynamic attributes while keeping slot benefits for declared ones
- `@dataclass(slots=True)` — clean, idiomatic way to create slotted data classes in Python 3.10+
- Use when: millions of instances, fixed attributes, memory-constrained environments
- Don't use when: dynamic attributes needed, ORM/framework compatibility required, few instances
