## Python's Object Model — Everything Lives on the Heap

Python's memory model is fundamentally different from languages like C++ or Java. In C++, a local variable `int x = 42` stores the integer directly on the stack — it has no identity, no type information, and no overhead. In Python, `x = 42` creates a **full Python object on the heap** and binds the name `x` to it.

Every Python object, without exception, has three components:
```
+------------------+
|  ob_refcnt       |  Reference count (how many names point here)
|  ob_type         |  Pointer to the type object (int, list, str, etc.)
|  ob_val / data   |  The actual value
+------------------+
```

This means even a simple integer uses at minimum **28 bytes** of memory in CPython. A Python list of 1,000 integers is actually 1,000 separate heap objects plus the list's array of 1,000 pointers. This is why understanding Python's memory model is essential for writing memory-efficient code.

## Everything Is an Object

```python
# Every value is a heap object with an id, type, and value
x = 42
type(x)    # <class 'int'>
id(x)      # memory address, e.g. 9785600
isinstance(x, int)   # True

# Functions are objects
def greet(): return "hello"
type(greet)    # <class 'function'>
id(greet)      # has an address too
greet.custom_attr = "I can add attributes to functions!"  # because it's an object

# Classes are objects too (metaclasses)
type(int)      # <class 'type'>  — int is an instance of 'type'
type(list)     # <class 'type'>
```

## Names vs Objects — The Core Mental Model

Variables (names) in Python live in **namespace dictionaries** — every module, function, and class has its own `__dict__` that maps name strings to object references. When you write `x = 42`, Python stores `"x": <int object at 0x...>` in the current namespace's dictionary.

```python
a = [1, 2, 3]
b = a           # b references the same list object — just adds another entry to namespace dict

b.append(4)
print(a)   # [1, 2, 3, 4] — a sees the change because both point to the same object
print(b)   # [1, 2, 3, 4]

# Reassigning a name doesn't affect the object
a = [10, 20]   # a now points to a NEW list object
print(b)       # [1, 2, 3, 4] — b still points to the old list
```

**The key insight**: assignment (`=`) never copies an object. It just binds a name to an existing object. Only explicit copy operations create new objects.

## Reference Counting — Python's Primary Memory Management

Every Python object maintains a **reference count** — the number of names, containers, or other references pointing to it. When the reference count reaches **zero**, CPython immediately frees the object's memory. This is the primary garbage collection mechanism.

```python
import sys

a = [1, 2, 3]
sys.getrefcount(a)   # 2 — 'a' holds one reference, getrefcount's argument holds another

b = a
sys.getrefcount(a)   # 3 — 'a', 'b', and getrefcount argument

c = a
sys.getrefcount(a)   # 4 — 'a', 'b', 'c', getrefcount argument

del b
sys.getrefcount(a)   # 3 — b removed

del c
sys.getrefcount(a)   # 2 — only 'a' and getrefcount argument remain
```

**Why `getrefcount` reports N+1**: the function call itself holds a temporary reference to the argument while executing — that's the extra +1 you always see.

```python
# Reference count lifecycle
a = [1, 2, 3]   # refcount = 1
b = a            # refcount = 2
c = [a, a]       # refcount = 4 (list holds two references to same object)

del a            # refcount = 3
del b            # refcount = 2
del c            # refcount = 0 → object freed IMMEDIATELY
```

The key advantage of reference counting over periodic garbage collection (like Java's GC): objects are freed **immediately** when no longer needed, with deterministic memory release. This is why CPython's memory footprint is generally predictable.

## Cyclic Garbage Collector — Handling the Exception

Reference counting has one fundamental flaw: **circular references**. If object A holds a reference to object B, and B holds a reference back to A, deleting the names `a` and `b` drops the external reference count but both objects still reference each other — refcount stays at 1, never reaching 0.

```python
a = []
b = []
a.append(b)   # a references b — b's refcount = 2
b.append(a)   # b references a — a's refcount = 2

del a   # a's external refcount → 1 (b still references it)
del b   # b's external refcount → 1 (a still references it)
# Both objects still exist — neither will be freed by reference counting alone!
```

CPython's **cyclic garbage collector** (in the `gc` module) solves this. It periodically scans memory for reference cycles — groups of objects that reference each other but have no external references — and frees them.

```python
import gc

gc.collect()           # manually trigger the cyclic GC
gc.get_count()         # (gen0, gen1, gen2) — objects in each generation
gc.get_threshold()     # (700, 10, 10) — collection thresholds per generation

# Three generations of garbage collection:
# Generation 0: newly created objects — collected frequently
# Generation 1: survived one collection — collected less often
# Generation 2: long-lived objects — collected rarely (expensive)
```

**Generational GC rationale**: most objects are either very short-lived (function-local variables, temporary results) or very long-lived (module-level singletons, caches). By collecting young objects frequently and old objects rarely, the GC maximizes efficiency — it doesn't waste time scanning long-lived objects that are unlikely to be garbage.

## Mutable vs Immutable — Memory Implications

The mutability of a type has direct consequences for how Python handles memory:

```python
# IMMUTABLE types: int, float, str, tuple, frozenset, bytes
# "Modifying" creates a NEW object — the original is unchanged

x = 10
print(id(x))   # e.g. 9785600
x = x + 1
print(id(x))   # DIFFERENT address — a new int object was created
               # The old int(10) object still exists until its refcount hits 0

# MUTABLE types: list, dict, set, custom classes
# Modifying changes the SAME object — all names pointing to it see the change

lst = [1, 2, 3]
print(id(lst))   # e.g. 140234567
lst.append(4)
print(id(lst))   # SAME address — same object, modified in place
```

**Why Python strings are immutable**: String immutability enables a critical optimization — interning. Because strings can't change, the same string literal can be shared across the entire interpreter. It also makes strings safe to use as dictionary keys (their hash can't change after insertion).

**Why Python integers are immutable**: Immutable integers can be cached as singletons. CPython pre-allocates integers -5 to 256 at startup — all assignments to these values share a single object, saving millions of heap allocations in typical programs.

## The Small Integer and String Cache

CPython's integer cache and string interning are direct consequences of the object model:

```python
# Integer cache: -5 to 256
a = 256
b = 256
a is b   # True — same cached singleton object

a = 257
b = 257
a is b   # False — outside cache, new objects created each time

# String interning: short identifier-like strings
a = "hello"
b = "hello"
a is b   # True — interned: single object, two names

a = "hello world"   # space prevents automatic interning
b = "hello world"
a is b   # False — two separate string objects (in most contexts)
```

## Memory Impact of Data Structures

Understanding `sys.getsizeof()` reveals the overhead of Python's object model:

```python
import sys

sys.getsizeof(42)           # 28 bytes — int object header alone
sys.getsizeof("hello")      # 54 bytes — str with 5 chars
sys.getsizeof([1, 2, 3])    # 88 bytes — list HEADER only, not including element objects
                             # actual memory = 88 + 3 × 28 (ints) = 172 bytes
sys.getsizeof((1, 2, 3))    # 72 bytes — tuple is more compact than list
sys.getsizeof({1, 2, 3})    # 216 bytes — set has hash table overhead
sys.getsizeof({})           # 64 bytes — empty dict

# For large numerical data, NumPy eliminates Python object overhead
import numpy as np
lst = list(range(1_000_000))   # ~8.5 MB (each int is 28 bytes)
arr = np.arange(1_000_000)     # ~8 MB raw, but no per-element Python objects
```

## __slots__ — Eliminating __dict__ Overhead

By default, every Python object stores its instance attributes in a **per-instance dictionary** (`__dict__`). This dictionary has its own hash table overhead — about 232 bytes for a simple 2-attribute class. At scale (millions of objects), this becomes significant.

`__slots__` replaces `__dict__` with fixed-offset storage on the object itself — like C struct fields:

```python
class RegularPoint:
    def __init__(self, x, y):
        self.x = x
        self.y = y

class SlottedPoint:
    __slots__ = ("x", "y")   # no __dict__ — attributes at fixed offsets

    def __init__(self, x, y):
        self.x = x
        self.y = y

import sys
rp = RegularPoint(1, 2)
sp = SlottedPoint(1, 2)

print(sys.getsizeof(rp) + sys.getsizeof(rp.__dict__))   # ~232 bytes
print(sys.getsizeof(sp))                                  # ~56 bytes — 4x smaller

sp.z = 3   # AttributeError — no __dict__, can't add undeclared attributes
```

## weakref — Reference Without Incrementing Count

A `weakref` (weak reference) points to an object without preventing garbage collection — it doesn't increment the reference count. This is essential for caches, observer patterns, and parent-child relationships where you don't want the cache to keep objects alive indefinitely.

```python
import weakref

class DataObject:
    pass

obj = DataObject()
weak = weakref.ref(obj)

print(weak())    # <DataObject object> — object still alive
print(weak() is obj)  # True — same object

del obj          # reference count drops to 0 — object freed immediately
print(weak())    # None — object has been garbage collected; weakref returns None
```

**Practical use case — cache that doesn't prevent GC**:
```python
import weakref

class Cache:
    def __init__(self):
        self._store = weakref.WeakValueDictionary()
        # When the value object has no other strong references, it's automatically
        # removed from the cache. The cache doesn't keep objects alive.

    def set(self, key, value):
        self._store[key] = value

    def get(self, key):
        return self._store.get(key)
```

## Interview Questions

**Q: What is the difference between a variable and an object in Python?**
An object is a value stored on the heap with a type pointer, a reference count, and its data. A variable is a name in a namespace dictionary (a `dict`) that maps the name string to an object pointer. Assigning a variable just creates or updates an entry in this dictionary — it never copies the object. Multiple names can reference the same object simultaneously.

**Q: How does Python's garbage collection work?**
Python uses two mechanisms: **reference counting** (primary) and a **cyclic garbage collector** (secondary). Reference counting frees objects immediately when their reference count reaches zero — deterministic and fast. The cyclic GC (`gc` module) periodically scans for circular references — groups of objects referencing each other with no external references — which reference counting alone cannot handle. The cyclic GC uses three generations to focus collection effort on recently allocated, short-lived objects.

**Q: What is a circular reference and why is it a problem?**
A circular reference occurs when object A references object B, and B references back to A (directly or through a chain). When you delete the external names pointing to A and B, their reference counts drop to 1 (each still references the other) — never reaching 0. Reference counting alone never frees them. They become memory leaks that only the cyclic GC can reclaim. Common causes: parent-child relationships where the child holds a reference to the parent; doubly-linked lists.

**Q: What is the difference between mutable and immutable objects in terms of memory?**
Immutable objects (int, str, tuple) cannot be changed in place — any "modification" creates a new object. This allows safe interning and caching (the same object can be shared). Mutable objects (list, dict, set) can be changed in place — all names referencing the same object see the change. Mutation in-place is more memory efficient (no allocation) but requires careful aliasing management.

**Q: What is `__slots__` and when would you use it?**
`__slots__` replaces the per-instance `__dict__` dictionary with fixed-offset attribute storage on the object. This eliminates the hash table overhead of `__dict__`, reducing memory by 3-4x per instance. Use it when creating thousands or millions of instances of a class with a known, fixed set of attributes. The trade-off: no dynamic attribute addition, no `__dict__`, and more complex inheritance.

**Q: What is a weak reference and when is it needed?**
A weak reference points to an object without incrementing its reference count — it doesn't prevent garbage collection. When the object's reference count drops to zero, the weak reference becomes `None`. Use weak references in caches (so the cache doesn't prevent GC of objects no longer needed elsewhere) and in observer/event patterns where subscribers shouldn't prevent their subjects from being freed.

## Summary

- Variables are **names in namespace dicts** bound to heap objects — not values stored in variables
- Every Python object has: **ob_refcnt** (reference count), **ob_type** (type pointer), **data**
- **Reference counting** — refcount hits 0 → immediate deallocation; the primary GC mechanism
- `sys.getrefcount(obj)` always reports N+1 (the function argument adds a temporary reference)
- **Cyclic GC** (`gc` module) — handles circular references that reference counting can't free
- Three GC generations: gen0 (young, collected often), gen1, gen2 (old, collected rarely)
- `id()` returns the memory address — same `id` means same object; `is` is True
- **Immutable** objects (int, str, tuple) — "modification" creates a new object; enables caching/interning
- **Mutable** objects (list, dict, set) — change in place; all aliases see the change
- Integer cache: -5 to 256; string interning: short identifier-like strings
- `sys.getsizeof()` — reports object header size only; nested objects measured separately
- `__slots__` — replaces `__dict__` with fixed-offset storage; 3-4x memory saving at scale
- `weakref` — reference without incrementing refcount; use for caches and observer patterns
