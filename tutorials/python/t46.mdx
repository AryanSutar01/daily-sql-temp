## What Mutability Really Means in Python's Memory Model

The words "mutable" and "immutable" describe a relationship between an object and its value — can the object's value change after it is created, or is it fixed forever? This distinction has far-reaching consequences in Python: it affects memory safety, function argument behaviour, dictionary key validity, performance, and correctness.

In Python, **all values are objects**. When you assign `x = 42`, Python creates an integer object on the heap with value 42, and `x` is a name (label) pointing to that object. The question of mutability is: can the *object itself* be modified, or must you create a new object to represent a new value?

```
Immutable types — value CANNOT change after creation:
  int, float, bool, str, tuple, frozenset, bytes, complex

Mutable types — value CAN change in place:
  list, dict, set, bytearray, custom class instances (usually)
```

This matters for three key reasons:
1. **Aliasing safety** — with mutable types, two names pointing to the same object can interfere with each other
2. **Hashability** — only immutable (hashable) objects can be dict keys or set members
3. **Function arguments** — mutable arguments can be modified by functions; immutable ones cannot

## Immutable Types — "Modification" Creates a New Object

When you perform an operation that appears to modify an immutable object, Python actually creates a **brand new object** and rebinds the name to it. The original object is unchanged — if any other name was pointing to it, that name still sees the original value.

```python
# Integers — immutable
x = 10
print(id(x))   # e.g. 9785600 — memory address of the int object

x = x + 1     # creates a NEW int object with value 11
print(id(x))   # DIFFERENT address — x now points to a new object
               # The original int(10) object still exists until its refcount drops to 0

# Proof that the original is unaffected
a = 10
b = a      # both a and b point to the same int(10) object
a = a + 1  # a now points to a NEW int(11); b still points to int(10)
print(b)   # 10 — unchanged; b was never modified
```

Strings behave the same way — every string operation returns a new string object. This has an important performance implication: building a string with `+` in a loop is O(n²) because each concatenation creates a new string:

```python
# INEFFICIENT — creates n intermediate string objects
result = ""
for word in ["Python", "is", "powerful"]:
    result += word + " "   # new string object every iteration: O(n²)

# CORRECT — join() builds the final string in one pass: O(n)
result = " ".join(["Python", "is", "powerful"])
print(result)   # "Python is powerful"
```

Tuples are also immutable — you cannot add, remove, or replace elements. However, **immutability applies at the reference level, not recursively**. A tuple can contain mutable objects, and those inner objects can be modified:

```python
t = (1, 2, 3)
t[0] = 99    # TypeError — tuples are immutable at the reference level

# But a tuple CAN contain mutable objects
t = ([1, 2], [3, 4])
t[0].append(99)   # works — you're modifying the list object, not the tuple
print(t)          # ([1, 2, 99], [3, 4]) — tuple references unchanged, list content changed

t[0] = []    # TypeError — you cannot replace the tuple's reference to the list
```

This subtlety makes tuples with mutable elements unhashable (because their "effective content" can change), which is why `hash((1, [2, 3]))` raises `TypeError`.

## Mutable Types — Changes Are Visible to All References

Mutable objects can be changed in place — the object at a specific memory address changes its content without changing its address. Every name or container that references the object sees the change immediately.

```python
# Lists — mutable
lst = [1, 2, 3]
print(id(lst))   # e.g. 140234567

lst.append(4)    # modifies the same object in place
print(id(lst))   # SAME address — same object, different content

# The aliasing consequence
a = [1, 2, 3]
b = a          # b and a point to the SAME list object

b.append(4)    # modifies the shared object
print(a)       # [1, 2, 3, 4] — a sees the change through its reference
print(b)       # [1, 2, 3, 4] — same object

# Dicts and sets — same aliasing behaviour
d1 = {"x": 1, "y": 2}
d2 = d1         # alias — same dict object

d2["z"] = 3    # modifies the shared dict
print(d1)      # {'x': 1, 'y': 2, 'z': 3} — d1 sees the change
```

## Why It Matters — Function Arguments

Python passes object **references** to functions — not copies. This means:
- If you pass an immutable object, the function can't affect the caller's variable (rebinding the parameter inside the function just creates a new local name)
- If you pass a mutable object, the function can modify it in place, and the caller's variable will reflect the change

```python
# Immutable argument — function cannot change the caller's variable
def increment(n):
    n += 1       # creates a NEW int; the local name 'n' is rebound
    print(f"inside: {n}")   # 11

x = 10
increment(x)
print(x)   # 10 — unchanged; 'x' was never modified, only 'n' was rebound locally

# Mutable argument — function CAN change the caller's object
def add_item(collection, item):
    collection.append(item)   # modifies the shared object in place

items = [1, 2, 3]
add_item(items, 4)
print(items)   # [1, 2, 3, 4] — the function modified the original

# Safe version — work on a copy inside the function
def add_item_safe(collection, item):
    collection = list(collection)   # create a local copy; doesn't affect caller
    collection.append(item)
    return collection               # caller gets the new list via return value

items = [1, 2, 3]
new_items = add_item_safe(items, 4)
print(items)      # [1, 2, 3] — original unchanged
print(new_items)  # [1, 2, 3, 4]
```

This behaviour is sometimes called "pass by object reference" or "pass by sharing" — Python passes a reference to the object, not the object's value and not the variable itself.

## Hashability — Why Dict Keys Must Be Immutable

Python's `dict` and `set` are implemented as **hash tables**. Inserting an object requires computing `hash(obj)` to determine which bucket it goes into. Looking up `d[key]` requires computing `hash(key)` again and finding the matching bucket.

For this to work correctly, an object's hash value must be **stable** — it must never change after the object is used as a key. If the hash changed, the lookup would compute a different bucket number and fail to find the key, breaking the dict.

This is why only **immutable objects are hashable** by default. Mutable objects (lists, dicts, sets) can have their content changed after insertion, which would change their hash and corrupt the data structure.

```python
# Hashable — can be dict keys or set members
d = {
    1: "integer",
    3.14: "float",
    True: "bool",
    "hello": "string",
    (1, 2): "tuple of immutables"
}
s = {1, 2.5, "hello", (3, 4)}   # set of hashable objects

# Unhashable — raises TypeError
d = {[1, 2]: "list key"}     # TypeError: unhashable type: 'list'
d = {{}: "dict key"}         # TypeError: unhashable type: 'dict'

# Tuples: hashable ONLY if ALL elements are hashable
hash((1, 2, 3))       # works — all elements are immutable
hash((1, [2, 3]))     # TypeError — contains a mutable list
```

## `frozenset` — The Immutable Set

`frozenset` is the immutable, hashable version of `set`. It supports all non-mutating set operations (union, intersection, difference) but not `add`, `remove`, or `discard`. Because it's immutable, it's hashable and can be used as a dict key or set member.

```python
# frozenset — immutable, hashable
fs = frozenset([1, 2, 3, 2, 1])   # duplicates removed automatically
print(fs)       # frozenset({1, 2, 3})

fs.add(4)       # AttributeError — frozenset is immutable

# Can be used as a dict key or set member because it's hashable
d = {frozenset([1, 2]): "pair_one_two"}
s = {frozenset([1, 2]), frozenset([3, 4])}

# Set operations work
fs1 = frozenset([1, 2, 3])
fs2 = frozenset([2, 3, 4])
fs1 & fs2   # frozenset({2, 3}) — intersection
fs1 | fs2   # frozenset({1, 2, 3, 4}) — union
fs1 - fs2   # frozenset({1}) — difference
```

## Common Pitfalls

### Pitfall 1 — Mutable Default Argument (The Classic Bug)

```python
# WRONG — the [] is created once at function definition, shared across all calls
def add_item(item, lst=[]):
    lst.append(item)
    return lst

print(add_item(1))   # [1]
print(add_item(2))   # [1, 2] — expected [2], but the list persisted!

# CORRECT — create a fresh list on each call
def add_item(item, lst=None):
    if lst is None:
        lst = []
    lst.append(item)
    return lst
```

### Pitfall 2 — Shallow Copy vs Deep Copy for Nested Structures

```python
import copy

# Shallow copy: outer container is new, but nested objects are SHARED
matrix = [[1, 2, 3], [4, 5, 6]]
shallow = matrix.copy()   # or matrix[:]

shallow[0].append(99)     # modifies the SHARED inner list
print(matrix[0])          # [1, 2, 3, 99] — original affected! ✗

# Deep copy: everything is recursively duplicated
deep = copy.deepcopy(matrix)
deep[0].append(99)
print(matrix[0])          # [1, 2, 3, 99] — unaffected ✓
```

### Pitfall 3 — Tuple with Mutable Element

```python
# A tuple looks immutable but its contents can change
t = ([1, 2], [3, 4])
t[0].append(99)   # modifies the list inside the tuple — no error
print(t)          # ([1, 2, 99], [3, 4]) — the tuple's references are fixed, not the objects

# This also makes the tuple unhashable
hash(t)   # TypeError: unhashable type: 'list'
```

## Interview Questions

**Q: What is the difference between mutable and immutable objects in Python?**
Immutable objects (int, str, tuple, frozenset) cannot be changed after creation. Any operation that appears to modify them creates a new object and rebinds the name. Mutable objects (list, dict, set) can be changed in place — the object at its memory address changes its content, and all names pointing to it see the change immediately.

**Q: Are tuples always immutable?**
Tuples are immutable at the **reference level** — you cannot add, remove, or reassign elements. But if a tuple contains mutable objects (like lists), those inner objects can still be modified through their own references. The tuple's pointers are fixed; the objects pointed to can change. This also means a tuple containing a list is unhashable, since its effective content can change.

**Q: Why can't you use a list as a dictionary key?**
Dictionary keys must be **hashable** — their hash value must never change after insertion. Lists are mutable; their content can change at any time, which would change their hash. If a list's hash changed after being inserted as a key, the dict would fail to find it on lookup (different hash → different bucket). Only immutable types with a stable hash are usable as dict keys.

**Q: What is the difference between `copy()` and `deepcopy()`?**
`copy()` creates a shallow copy — a new outer container, but elements inside still reference the same objects. Modifying a nested mutable object (a list inside a list) affects both the original and the copy. `copy.deepcopy()` recursively copies everything — every nested object gets a new independent copy. Use shallow copy for flat structures; deep copy for nested mutable structures.

**Q: Why does passing a list to a function allow the function to modify the original?**
Python passes object references, not values. The function parameter receives a reference to the same list object the caller has. Calling `.append()` or `.pop()` on it modifies that shared object. The caller's variable still points to the same object, so it sees the changes. Passing an integer doesn't have this problem — integers are immutable, so any "modification" inside the function creates a new local object.

## Summary

- **Immutable**: int, float, bool, str, tuple, frozenset — value fixed at creation; "changes" create new objects
- **Mutable**: list, dict, set — value can change in place; all aliases see the modification
- Immutable objects are **hashable** — can be dict keys and set members
- Mutable objects are **not hashable** — would corrupt hash tables if content changed after insertion
- `=` on mutable types creates an **alias** — both names share the same object
- Use `.copy()` for a flat shallow copy; `copy.deepcopy()` for nested independence
- **Function arguments** — passed by reference; mutable args can be modified by the called function
- Mutable defaults in function signatures are shared across calls — always use `None` as sentinel
- Tuples are immutable at the reference level — but can contain mutable objects that themselves change
- `frozenset` — immutable, hashable version of `set`; can be used as dict key or set member
