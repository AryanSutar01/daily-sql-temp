## Type Hints and Static Analysis: Runtime Annotations vs Compile-Time Safety

Python is fundamentally a dynamically typed language. The CPython interpreter resolves types at runtime and never enforces type safety before execution. However, as software systems scale to millions of lines of code across distributed teams, the lack of architectural type contracts leads to catastrophic runtime failures, subtle bugs, and unmaintainable code.

To solve this, Python introduced **Type Hints** (PEP 484). Type hints do not change how the CPython interpreter executes code. Instead, they provide a standardized syntax for **Static Analysis Tools** (like Mypy, Pyright, or Pyre) to inspect the codebase, build a Control Flow Graph (CFG), and mathematically prove that data structures conform to their contracts *before* the code ever runs.

### The Runtime Reality: `__annotations__`

When you add type hints to a function, the CPython interpreter simply parses them and stores them in a dictionary attached to the function object called `__annotations__`. During execution, the interpreter completely ignores them.

```python
def calculate_discount(price: float, discount_code: str) -> float:
    return price * 0.9

# At runtime, Python ignores the hints entirely. This executes perfectly:
# calculate_discount("100", 123) 

# The hints are simply stored in memory for third-party tools to inspect:
print(calculate_discount.__annotations__)
# {'price': <class 'float'>, 'discount_code': <class 'str'>, 'return': <class 'float'>}
```

## Static Analysis via Mypy

Because the Python interpreter ignores type hints, developers must run a static analyzer in their CI/CD pipelines to enforce the architecture. **Mypy** is the industry standard.

When Mypy executes, it parses the Python AST (Abstract Syntax Tree), simulates the flow of data through the entire application without executing the code, and flags any type contract violations. If Mypy finds a violation, it fails the build, preventing bugs from reaching production.

```bash
# Execute static analysis strictly
mypy main.py --strict
```

## Fundamental and Collection Annotations

Modern Python (3.9+) allows developers to use built-in types directly for collections, replacing the older, cumbersome `typing.List` or `typing.Dict` architecture.

```python
# Modern collection typing
active_users: list[str] = ["admin", "guest"]
user_sessions: dict[str, int] = {"admin": 12345}

# Union Types (Python 3.10+ uses the | operator instead of typing.Union)
def process_id(identifier: int | str) -> str:
    return str(identifier)

# Optional Types (equivalent to type | None)
def fetch_user(user_id: int) -> str | None:
    return "Alice" if user_id == 1 else None
```

## Architectural Concepts: Generics and `TypeVar`

A **Generic** architecture allows a function, class, or data structure to operate on multiple data types while still enforcing structural consistency. This is achieved using a `TypeVar`, which acts as a mathematical placeholder for a specific type.

```python
from typing import TypeVar

# T represents an unknown type that must remain mathematically consistent
T = TypeVar('T')

def extract_first(items: list[T]) -> T:
    return items[0]

# Mypy proves that extract_first on a list[int] MUST return an int.
first_number = extract_first([1, 2, 3]) 
```

### Covariance and Contravariance (Advanced)

When designing complex class hierarchies, you must decide how generics behave under inheritance. This is known as Variance.

If `Dog` is a subclass of `Animal`:
- **Covariant** (`TypeVar('T', covariant=True)`): A `list[Dog]` can be passed where a `list[Animal]` is expected. This is generally safe for read-only collections.
- **Contravariant** (`TypeVar('T', contravariant=True)`): A `Processor[Animal]` can be passed where a `Processor[Dog]` is expected. This is generally safe for write-only or consumer architectures.
- **Invariant** (Default): A `list[Dog]` CANNOT be passed where a `list[Animal]` is expected. Python's standard `list` is invariant because lists are mutable (if you pass a `list[Dog]` as a `list[Animal]`, a function could maliciously append a `Cat` to it!).

## `TypedDict` and `Literal`

When interacting with external REST APIs or databases, developers frequently pass dictionaries. A standard `dict[str, Any]` provides zero type safety. **`TypedDict`** enforces the exact key/value schema of a dictionary.

```python
from typing import TypedDict, Literal

class ConfigPayload(TypedDict):
    host: str
    port: int

def connect(config: ConfigPayload) -> None:
    print(config["host"]) # Mypy verifies "host" exists and is a str

# Literal restricts a parameter to an exact, specific set of hardcoded values
def shift_gear(gear: Literal["drive", "reverse", "neutral", "park"]) -> None:
    pass

shift_gear("drive") # Valid
# shift_gear("forward") # Mypy triggers a fatal error during static analysis
```

## Structural Subtyping: `Protocol`

Historically, Python developers used Abstract Base Classes (`abc.ABC`) to enforce interfaces. This is called **Nominal Subtyping** (types must explicitly declare inheritance). 

Python 3.8 introduced **`typing.Protocol`**, which enables **Structural Subtyping** (static Duck Typing). A Protocol defines an interface, and Mypy will statically verify that an object implements the interface, *even if the object does not inherit from the Protocol*.

```python
from typing import Protocol

# Defines a strict structural contract
class Writable(Protocol):
    def write(self, data: str) -> None:
        ...

# File does NOT inherit from Writable!
class File:
    def write(self, data: str) -> None:
        print(data)

# Mypy statically proves that File satisfies the Writable protocol.
def log(destination: Writable) -> None:
    destination.write("Error occurred")

log(File()) # Mypy approves this without requiring explicit inheritance
```

## Interview Questions

**Q: Do type hints improve runtime performance in Python?**
No. The CPython interpreter completely ignores type hints during execution, simply storing them in the `__annotations__` dictionary. They exist strictly for static analysis tools (like Mypy) and IDE autocompletion. They enforce architectural correctness before the code runs, but provide zero performance optimization at runtime. (Note: Tools like `mypyc` or Cython *can* use hints for C-compilation, but standard CPython does not).

**Q: What is the architectural difference between `Any` and a Generic `TypeVar`?**
Assigning `Any` to a variable completely disables static type checking for that variable; the analyzer assumes any operation on it is valid, effectively reverting to dynamic typing. A `TypeVar` strictly enforces that while the type is unknown initially, it must remain mathematically consistent throughout the function's execution (e.g., if a `list[T]` is passed in, a single `T` must be returned).

**Q: Why is a Python `list[T]` considered Invariant rather than Covariant?**
Because lists are mutable. If `list` were covariant, you could pass a `list[Dog]` into a function expecting a `list[Animal]`. That function could then append a `Cat` into the `list[Animal]`. When the function returns, your original `list[Dog]` now contains a `Cat`, destroying type safety. Read-only collections like `Sequence` are Covariant because they cannot be mutated.

**Q: Explain the difference between `Protocol` and `ABC`.**
`ABC` (Abstract Base Class) enforces Nominal Subtyping. A class must explicitly inherit from the `ABC` (`class MyClass(MyABC):`) for the relationship to exist. `Protocol` enforces Structural Subtyping (Static Duck Typing). A class does not need to inherit from the Protocol; as long as the class implements the methods defined in the Protocol, Mypy considers it a valid subtype.

**Q: How does `TypedDict` differ from a standard dictionary type hint `dict[str, str]`?**
A standard `dict[str, str]` dictates that *every* key must be a string and *every* value must be a string, but does not enforce specific key names. A `TypedDict` defines a rigid schema, requiring exact key names mapped to specific value types, functioning similarly to an interface in TypeScript.

## Summary

- **Type Hints:** Standardized syntax (PEP 484) ignored by the interpreter but used by static analyzers.
- **`__annotations__`:** The internal dictionary where CPython stores type hints at runtime.
- **Static Analysis:** Tools like Mypy simulate execution paths to prove structural correctness.
- **Modern Syntax:** Python 3.9+ supports standard collections (`list[int]`), and 3.10+ supports the `|` union operator.
- **`TypeVar`:** Used to build Generic architectures that enforce consistency across unknown types.
- **Variance:** The rules governing how generics behave under inheritance (Covariant, Contravariant, Invariant).
- **`TypedDict`:** Enforces exact dictionary schemas for complex payloads.
- **`Protocol`:** Enables static duck typing (structural subtyping) without requiring explicit inheritance.
