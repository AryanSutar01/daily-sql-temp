## Why Python Has Three Kinds of Methods

In object-oriented languages like Java, all methods are instance methods by default. Python was designed with a clearer separation of concerns, offering three distinct method types that reflect *what information a method actually needs to do its job*:

- **Instance methods** — need access to `self` (the specific object instance) to read or modify its state
- **Class methods** — need access to `cls` (the class itself) to create instances or modify class-level state, but don't need a specific instance
- **Static methods** — don't need the instance or the class; they are utility functions that logically belong inside the class but could theoretically be standalone functions

Choosing the wrong type is a design smell. An instance method that never uses `self` should be a static method. A class method that hardcodes the class name instead of using `cls` breaks subclass polymorphism. Using the right type communicates intent clearly to other developers reading your code.

## Instance Methods — The Default

Instance methods are the standard. Python automatically passes the calling object as the first argument (`self`) when you call an instance method. By convention this first parameter is always named `self`, though technically any name works. Through `self`, the method can read and modify any attribute of that specific instance.

```python
class BankAccount:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance
        self._transactions = []   # private by convention (leading underscore)

    def deposit(self, amount):
        """Instance method — needs self to modify THIS account's balance."""
        if amount <= 0:
            raise ValueError("Deposit amount must be positive")
        self.balance += amount
        self._transactions.append(("deposit", amount))
        return self.balance

    def withdraw(self, amount):
        if amount > self.balance:
            raise ValueError("Insufficient funds")
        self.balance -= amount
        self._transactions.append(("withdrawal", amount))
        return self.balance

    def get_statement(self):
        """Reads instance state — clearly an instance method."""
        lines = [f"Account: {self.owner}", f"Balance: ₹{self.balance}"]
        for tx_type, amount in self._transactions:
            lines.append(f"  {tx_type}: ₹{amount}")
        return "\n".join(lines)

acc = BankAccount("Alice", 1000)
acc.deposit(500)   # Python internally calls BankAccount.deposit(acc, 500)
acc.withdraw(200)
print(acc.get_statement())
```

When Python executes `acc.deposit(500)`, it looks up `deposit` on the class, finds it's a function, and automatically creates a **bound method** — a wrapper that passes `acc` as the first argument. This is called the **descriptor protocol** — functions are descriptors, and accessing them through an instance binds them.

## `@classmethod` — Receives the Class

A class method receives the **class** as its first argument (`cls`, by convention) instead of an instance. Python applies `@classmethod` as a descriptor that intercepts attribute access and passes the class automatically.

Class methods are called on the class itself (`User.from_csv(...)`) rather than on an instance, though calling them on an instance (`user.from_csv(...)`) also works — Python always passes the class, not the instance.

The most important use of class methods is as **factory methods** (alternative constructors). Many classes have multiple ways to be created from different input formats. Rather than overloading `__init__` with complex conditional logic, class methods provide clean, named constructors:

```python
import json
from datetime import datetime

class User:
    _instance_count = 0   # class-level variable shared by all instances

    def __init__(self, name, email, role="viewer"):
        self.name = name
        self.email = email
        self.role = role
        self.created_at = datetime.now()
        User._instance_count += 1

    @classmethod
    def get_count(cls):
        """Accesses class state — no instance needed. cls = User (or subclass)."""
        return cls._instance_count

    @classmethod
    def from_csv_row(cls, row: str):
        """Factory method: create a User from a CSV string like 'Alice,alice@ex.com,admin'."""
        parts = row.strip().split(",")
        return cls(parts[0], parts[1], parts[2] if len(parts) > 2 else "viewer")

    @classmethod
    def from_dict(cls, data: dict):
        """Factory method: create a User from a dict (e.g., from a JSON API response)."""
        return cls(
            name=data["name"],
            email=data["email"],
            role=data.get("role", "viewer")
        )

    @classmethod
    def from_json(cls, json_str: str):
        """Factory method: parse a JSON string and create a User."""
        return cls.from_dict(json.loads(json_str))

    def __repr__(self):
        return f"User(name={self.name!r}, email={self.email!r}, role={self.role!r})"

# Factory methods provide clean, readable alternative constructors
u1 = User("Alice", "alice@example.com")
u2 = User.from_csv_row("Bob,bob@example.com,admin")
u3 = User.from_dict({"name": "Carol", "email": "carol@example.com"})
u4 = User.from_json('{"name": "Dave", "email": "dave@example.com", "role": "admin"}')

print(User.get_count())   # 4 — class method reads class-level state
```

### Why `cls` Instead of Hardcoding the Class Name

This is the key advantage of `@classmethod` over just calling `User(...)` directly. If you use `cls(...)`, subclasses that inherit and call the factory method get an instance of the **correct subclass**:

```python
class AdminUser(User):
    def __init__(self, name, email):
        super().__init__(name, email, role="admin")
        self.permissions = ["read", "write", "delete"]

# If from_csv_row used User(...) instead of cls(...):
u = AdminUser.from_csv_row("Alice,alice@example.com")
type(u)   # <class 'User'> — WRONG: we called it on AdminUser but got a User

# Because from_csv_row uses cls(...):
u = AdminUser.from_csv_row("Alice,alice@example.com")
type(u)   # <class 'AdminUser'> — CORRECT: cls is AdminUser when called on AdminUser
```

This polymorphic behaviour is what makes class methods fundamental to object-oriented design in Python.

## `@staticmethod` — No Implicit Argument

A static method receives **no implicit first argument** — neither `self` nor `cls`. From Python's perspective, it's just a regular function that happens to live inside a class namespace for organizational purposes.

Static methods are appropriate when the logic:
1. Is related to the class conceptually (so it makes sense to group it there)
2. Doesn't need to read or modify instance or class state
3. Would make sense as a standalone module function, but belongs here for discoverability

```python
import hashlib, re

class PasswordManager:
    _min_length = 8
    _requires_upper = True
    _requires_digit = True

    def __init__(self, username):
        self.username = username
        self._password_hash = None

    @staticmethod
    def validate_password(password: str) -> tuple[bool, str]:
        """Pure utility — takes a string, returns validation result.
        Doesn't need the instance (we're not saving a password here)
        or the class (we're not reading class config).
        This is correct as a static method."""
        if len(password) < 8:
            return False, f"Too short — minimum 8 characters"
        if not any(c.isupper() for c in password):
            return False, "Must contain at least one uppercase letter"
        if not any(c.isdigit() for c in password):
            return False, "Must contain at least one digit"
        if not re.search(r"[!@#$%^&*]", password):
            return False, "Must contain a special character (!@#$%^&*)"
        return True, "Password is valid"

    @staticmethod
    def hash_password(password: str) -> str:
        """Pure transformation — input string → hashed string.
        No instance or class state needed."""
        return hashlib.sha256(password.encode("utf-8")).hexdigest()

    @staticmethod
    def generate_reset_token() -> str:
        """Utility for generating a secure random token."""
        import secrets
        return secrets.token_urlsafe(32)

    def set_password(self, password: str):
        """Instance method — uses self to store the hash on this specific user."""
        valid, message = PasswordManager.validate_password(password)
        if not valid:
            raise ValueError(message)
        self._password_hash = PasswordManager.hash_password(password)

# Can be called on the class — no instance needed
valid, msg = PasswordManager.validate_password("weak")
print(valid, msg)   # False, "Too short — minimum 8 characters"

token = PasswordManager.generate_reset_token()
print(len(token))   # 43 characters (URL-safe base64)

# Can also be called on an instance — same result
pm = PasswordManager("alice")
pm.validate_password("Str0ng!Pass")   # True, "Password is valid"
```

**Why not just a module-level function?** Grouping `validate_password` inside `PasswordManager` signals that it belongs to the domain of password management. It shows up in documentation auto-generated from the class. It can be called as `PasswordManager.validate_password(...)` which is self-documenting. A module-level `validate_password(...)` is less discoverable and less clearly scoped.

## Side-by-Side Comparison

The best way to solidify understanding is to see all three types used on the same class:

```python
from datetime import date, datetime

class DateHelper:
    """A class demonstrating all three method types."""
    fmt = "%Y-%m-%d"   # class variable

    def __init__(self, date_str: str):
        self.date = datetime.strptime(date_str, DateHelper.fmt)

    def format(self, fmt=None) -> str:
        """Instance method — uses self.date (instance state)."""
        return self.date.strftime(fmt or self.fmt)

    def days_until(self, other: "DateHelper") -> int:
        """Instance method — computes difference between two instances."""
        return (other.date - self.date).days

    @classmethod
    def today(cls) -> "DateHelper":
        """Class method — alternative constructor; uses cls to create the right type."""
        return cls(str(date.today()))

    @classmethod
    def from_timestamp(cls, ts: float) -> "DateHelper":
        """Another factory — creates from Unix timestamp."""
        return cls(datetime.fromtimestamp(ts).strftime(cls.fmt))

    @staticmethod
    def is_weekend(date_str: str) -> bool:
        """Static method — pure utility; no instance or class state."""
        d = datetime.strptime(date_str, "%Y-%m-%d")
        return d.weekday() >= 5   # 5=Saturday, 6=Sunday

    @staticmethod
    def is_leap_year(year: int) -> bool:
        """Static — pure computation with no state dependency."""
        return year % 4 == 0 and (year % 100 != 0 or year % 400 == 0)

# Usage
today = DateHelper.today()               # @classmethod — alternative constructor
d = DateHelper("2024-03-15")
print(d.format())                        # "2024-03-15" — instance method
print(d.days_until(today))               # difference in days — instance method
print(DateHelper.is_weekend("2024-03-16"))  # True (Saturday) — static method
print(DateHelper.is_leap_year(2024))     # True — static method
```

## When to Use Which

The decision tree is simple:

```
Does the method need to READ or MODIFY an instance's attributes (self)?
  YES → instance method (the default)
  NO  ↓

Does the method need to CREATE instances (cls(...)) or access class-level state?
  YES → @classmethod
  NO  ↓

Is the method a pure utility that logically belongs to this class?
  YES → @staticmethod
  NO  → consider making it a standalone module-level function
```

```python
# Quick examples of each decision

class Order:
    _tax_rate = 0.18   # class variable

    def __init__(self, items):
        self.items = items

    def total(self):
        """Needs self.items → instance method."""
        return sum(item.price for item in self.items)

    def total_with_tax(self):
        """Needs self.total() and cls._tax_rate → instance method."""
        return self.total() * (1 + Order._tax_rate)

    @classmethod
    def set_tax_rate(cls, rate):
        """Modifies class state → classmethod."""
        cls._tax_rate = rate

    @classmethod
    def from_cart(cls, cart):
        """Alternative constructor → classmethod."""
        return cls(cart.items)

    @staticmethod
    def is_valid_item_code(code: str) -> bool:
        """Pure validation, no state needed → staticmethod."""
        return len(code) == 8 and code.isalnum()
```

## Interview Questions

**Q: What is the difference between `@staticmethod` and `@classmethod`?**
`@classmethod` receives `cls` (the class) as its first implicit argument — it can access and modify class-level state and is essential for factory methods and inheritance-aware operations. `@staticmethod` receives no implicit argument — it's a regular function scoped to the class namespace, used for utility functions that don't need class or instance state. The key test: does the method need to create instances or access class variables? Use `@classmethod`. Does it need neither? Use `@staticmethod`.

**Q: When would you use `@classmethod` as a factory method?**
When you have multiple ways to create an instance from different input formats — e.g., `User.from_csv(row)`, `User.from_dict(data)`, `User.from_json(str)`. Using `cls(...)` instead of `ClassName(...)` ensures that subclasses calling the inherited factory method get an instance of themselves (not the parent class), enabling correct polymorphic behaviour.

**Q: Why use `cls` instead of the class name in `@classmethod`?**
Using `cls` makes the class method polymorphic. When `Dog.create()` calls `cls()`, `cls` is `Dog` — not `Animal` (where the method was defined). If the method hardcoded `Animal(...)`, subclasses calling it would always get `Animal` instances. Using `cls` respects the calling class in the inheritance hierarchy.

**Q: Can you call a `@staticmethod` on an instance?**
Yes — `PasswordManager.validate_password(pwd)` and `pm.validate_password(pwd)` both work. But calling on the class is the idiomatic style — it signals that the method has no instance dependency.

**Q: Why use `@staticmethod` instead of a module-level function?**
Grouping the function inside the class improves discoverability and signals conceptual belonging. `PasswordManager.validate_password()` is self-documenting: this validation logic belongs to the password management domain. A module-level `validate_password()` is less clear about scope and is less discoverable in documentation.

## Summary

- **Instance method** — default; receives `self`; reads or modifies instance state; called via `obj.method()`
- **`@classmethod`** — receives `cls`; used for factory methods, class-level state, and inheritance-aware operations
- **`@staticmethod`** — no implicit argument; pure utility function scoped to the class namespace
- `cls` always refers to the **actual class called on** — enables correct polymorphism in subclasses
- Both `@classmethod` and `@staticmethod` can be called on the class or an instance
- Use `@classmethod` for: alternative constructors, class-level counters/configs, inheritance-safe operations
- Use `@staticmethod` for: validators, converters, utilities that belong conceptually but need no state
- Decision test: needs `self`? → instance. Needs `cls`? → classmethod. Needs neither? → staticmethod
