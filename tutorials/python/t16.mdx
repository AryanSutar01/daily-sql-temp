## The Memory Architecture of Object-Oriented Programming

Python's execution model is deeply **Object-Oriented (OOP)**. Everything in Python—from simple integers to functions and modules—is an object allocated on the CPython heap. 

Conceptually, OOP is a paradigm that organizes software design around **Objects** rather than logical procedures. An object is a data structure that tightly couples state (Attributes) and behavior (Methods). This architectural coupling ensures that data is mutated strictly by the functions designed to handle it, heavily reducing global state pollution.

### `PyTypeObject` vs `PyObject`

Understanding the memory model is crucial for high-performance Python. 
A **Class** is a blueprint. When Python parses a class definition, it allocates a `PyTypeObject` in C. This object possesses a dictionary (`__dict__`) containing all the class attributes and methods.

An **Instance** is a concrete realization. When you instantiate a class (`acc = BankAccount()`), Python allocates a new `PyObject`. Crucially, this instance gets its *own* separate `__dict__`.

```python
class BankAccount:
    # Class Attribute: Lives in the PyTypeObject's __dict__.
    # Shared exactly once across all instances to save memory.
    bank_name = "Global Trust"

    def __init__(self, owner, balance=0):
        # Instance Attributes: Live in the PyObject's __dict__.
        # Unique to every individual account.
        self.owner = owner
        self.balance = balance
```

## The Descriptor Protocol and `self`

Unlike languages like Java or C++ where the instance context (`this`) is implicit at the compiler level, Python requires `self` to be explicitly passed as the first parameter of every instance method. 

How does `acc.deposit(100)` automatically pass `acc` as `self`? It relies on the **Descriptor Protocol**.

In Python, functions are non-data descriptors. When you access a method on an instance (`acc.deposit`), you aren't retrieving the raw function. The interpreter triggers the function's internal `__get__` method. This dynamically generates a **Bound Method Object** (`PyMethodObject`). This bound object wraps the raw function and securely binds the `acc` instance to the first parameter. When you invoke it, it translates the call to `BankAccount.deposit(acc, 100)`.

## Encapsulation and Name Mangling

Encapsulation restricts external access to an object's internal state. Python does not implement strict C-level `private` memory barriers. Instead, it relies on conventions and namespace manipulation:

- **Single Underscore (`_var`):** A gentleman's agreement. It signals to other developers that the attribute is internal and subject to change without notice. The interpreter does not enforce this restriction whatsoever.
- **Double Underscore (`__var`):** Triggers **Name Mangling**. During compilation, the parser statically rewrites the attribute name to `_ClassName__var`. This provides a structural barrier to prevent subclasses from accidentally overwriting internal state in complex inheritance hierarchies.

```python
class SecureVault:
    def __init__(self):
        self._internal = 1      # Protected by convention
        self.__secret = 42      # Mangled to _SecureVault__secret
```

## Memory Optimization: `__slots__`

By default, every instance object uses a hash table (`__dict__`) to store its attributes. While this allows for dynamic attribute assignment at runtime, hash tables carry massive memory overhead. If you instantiate one million `User` objects, the RAM consumption of one million dictionaries will crash your system.

Python provides `__slots__` to explicitly declare the structural shape of the class. When defined, the CPython interpreter suppresses the creation of the `__dict__`. Instead, it allocates a highly optimized, static C-array for the attributes, saving hundreds of megabytes of RAM in large-scale architectures.

```python
class OptimizedUser:
    # Destroys the __dict__ and allocates a static C-array
    __slots__ = ['id', 'username', 'email']

    def __init__(self, uid, name, email):
        self.id = uid
        self.username = name
        self.email = email
        
# user = OptimizedUser(1, "bob", "bob@example.com")
# user.is_admin = True # AttributeError! Dynamic assignment is blocked.
```

## Abstracting Access: `@property`

Directly accessing attributes (`obj.value`) is fast, but it violates encapsulation because it prevents you from adding validation logic later without breaking the public API. 

The `@property` decorator is a built-in Descriptor that allows you to define a method but access it syntactically like a variable. This achieves the architectural encapsulation of Java's `get()` and `set()` methods without the verbose boilerplate.

```python
class Temperature:
    def __init__(self, c):
        self._celsius = c

    @property
    def celsius(self):
        return self._celsius

    @celsius.setter
    def celsius(self, value):
        if value < -273.15:
            raise ValueError("Below absolute zero!")
        self._celsius = value
```

## Interview Questions

**Q: Explain the exact mechanism of `self` via the Descriptor Protocol.**
Functions in Python implement the descriptor `__get__` method. When a function is accessed via an instance (`obj.method`), `__get__` intercepts the access and returns a Bound Method Object. This wrapper object holds a reference to both the instance and the original function. When called, the wrapper injects the instance object as the first argument (`self`), effectively executing `Class.method(obj, args)`.

**Q: Why does Python use Name Mangling (`__var`) instead of true private variables?**
Python's philosophy is "we are all consenting adults here." Name mangling is not designed for security; it is designed to prevent namespace collisions. If a subclass defines an attribute with the same name as an internal base class attribute, it would silently overwrite the state. Mangling it to `_BaseClass__var` ensures the subclass (`_SubClass__var`) cannot accidentally collide with it.

**Q: What is the architectural purpose of `__slots__`?**
To drastically reduce memory consumption. Standard objects use a dynamic `__dict__` hash table, which incurs massive memory overhead. `__slots__` disables the dictionary, replacing it with a static, tightly packed C-array. It is strictly used for performance optimization in systems that instantiate millions of uniform objects.

**Q: What is the architectural difference between `@classmethod` and `@staticmethod`?**
Both skip the `self` instance binding. A `@classmethod` triggers a descriptor that binds the Class Object (`cls`) as the first argument, primarily used to implement Factory patterns (alternative constructors). A `@staticmethod` returns the raw function without binding anything; it is fundamentally just a procedural function housed inside the class namespace purely for organizational hygiene.

## Summary

- **Memory Model:** Classes are `PyTypeObject` blueprints; Instances are `PyObject` concrete allocations with distinct `__dict__` hash tables.
- **`self`:** Dynamically injected via the Descriptor Protocol returning Bound Method Objects.
- **Name Mangling (`__var`):** Prevents attribute namespace collisions in deep inheritance trees.
- **`__slots__`:** Replaces the `__dict__` with a static C-array, optimizing RAM at the cost of dynamic assignment.
- **`@property`:** Maintains API stability by wrapping getter/setter logic behind standard attribute syntax.
