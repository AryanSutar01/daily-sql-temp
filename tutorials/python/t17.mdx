## Inheritance and the MRO: How CPython Resolves Method Lookups

Inheritance is the foundational structural mechanism of Object-Oriented Programming (OOP) that allows a child class to reuse, extend, or override the behavior of a parent class.

Conceptually, inheritance establishes an **IS-A relationship** (e.g., a `PostgresDriver` IS-A `DatabaseDriver`). When a child class is defined, Python mathematically wires the new Class Object to its parent Class Object in memory. If an attribute or method is not found on the child instance or child class, the interpreter dynamically traverses up the inheritance chain to locate it.

### CPython Class Memory Structures (`PyTypeObject`)

In CPython, a class is an instance of a metaclass (usually `type`), and is defined internally by a C struct called `PyTypeObject`. This struct holds critical pointers that power inheritance:
- `tp_base`: A pointer to the immediate parent class.
- `tp_bases`: A tuple of pointers to all immediate base classes (critical for Multiple Inheritance).
- `tp_mro`: A tuple representing the fully calculated Method Resolution Order.

When you call `dog.bark()`, the interpreter checks the instance's dictionary (`__dict__`). If it fails, it checks the class's dictionary. If it fails there, the interpreter iterates sequentially through the `tp_mro` tuple, checking each parent class dictionary until it finds the `bark` method. If it reaches `object` and still fails, it raises an `AttributeError`.

```python
class Animal:
    def eat(self):
        return "Consuming nutrients"

class Dog(Animal):
    def bark(self):
        return "Woof!"

dog = Dog()
# dog.eat() succeeds because the interpreter delegates the lookup via the MRO pointer to Animal
```

## Multiple Inheritance and the Diamond Problem

Python is one of the few mainstream languages (unlike Java or C#) that fully supports **Multiple Inheritance**—a class can inherit from multiple independent parent classes.

This introduces severe architectural complexity known as the **Diamond Problem**. If Class D inherits from Class B and Class C, and both B and C inherit from Class A, what happens if D calls a method defined in both B and C? Which path does the interpreter take?

### Method Resolution Order (MRO) and C3 Linearization

Python solves the Diamond Problem using a strict, mathematical algorithm called **C3 Linearization**. This algorithm calculates the **Method Resolution Order (MRO)**—a flattened, one-dimensional tuple representing the exact sequence in which Python will search the parent classes.

C3 Linearization guarantees three critical properties:
1. A child class is always searched before its parents.
2. If a class inherits from multiple parents, they are searched in the exact left-to-right order specified in the class definition.
3. The graph is monotonic (the order of parents is preserved consistently across all subclasses).

```python
class A: pass
class B(A): pass
class C(A): pass
# D inherits from B and C. The left-to-right order is B, then C.
class D(B, C): pass

# The algorithm guarantees D is searched first, then B, then C, then A, then object.
print(D.__mro__)
# (<class 'D'>, <class 'B'>, <class 'C'>, <class 'A'>, <class 'object'>)
```

If the inheritance graph is impossible to linearize without violating these rules (e.g., circular dependencies), Python will refuse to compile the class and throw a `TypeError: Cannot create a consistent method resolution order (MRO)`.

## The Delegation Proxy: `super()`

When a child class overrides a parent's method, the parent's implementation is masked in the local namespace. To invoke the masked parent method, Python provides the `super()` function.

Architecturally, `super()` does not just return the immediate parent. It returns a **Descriptor Proxy Object** that dynamically delegates method calls to the *next* class in the computed MRO of the current instance. 

This behavior is absolutely critical in multiple inheritance architectures. It ensures that every parent's initialization logic (e.g., `__init__`) is executed exactly once, in the correct algorithmic order, without explicitly hardcoding parent class names.

```python
class Logger:
    def __init__(self):
        print("Logger initialized")
        super().__init__()

class Database:
    def __init__(self):
        print("Database initialized")
        super().__init__()

# Multiple Inheritance: left-to-right
class MonitoredDatabase(Logger, Database):
    def __init__(self):
        print("MonitoredDatabase initialized")
        # super() looks at the MRO of MonitoredDatabase, not just the parent of MonitoredDatabase.
        # MRO: MonitoredDatabase -> Logger -> Database -> object
        super().__init__()

db = MonitoredDatabase()
# Output:
# MonitoredDatabase initialized
# Logger initialized
# Database initialized
```

Notice how `Logger` calls `super().__init__()`, and instead of going to `object` (its nominal parent), the proxy routes the call to `Database` based on the MRO of the actual instance being created (`MonitoredDatabase`).

## Polymorphism and Duck Typing

**Polymorphism** is the concept that different objects can be treated identically by a function or system as long as they expose a conforming interface. In statically typed, compiled languages (like C++ or Java), polymorphism strictly requires a shared inheritance hierarchy (a nominal type system).

Python completely bypasses this via a mechanism known as **Duck Typing**. Because Python evaluates types dynamically at runtime, the interpreter does not care what class an object belongs to or what it inherits from. It only checks if the object possesses the required method/attribute at the exact microsecond the operation is attempted.

*"If it walks like a duck and quacks like a duck, the interpreter executes it as a duck."*

```python
class TextFile:
    def write(self, data): 
        print(f"Writing to text file: {data}")

class NetworkSocket:
    def write(self, data): 
        print(f"Sending over TCP: {data}")

# Polymorphic architecture: This function accepts ANY object with a write() method.
# Zero shared inheritance is required.
def log_data(destination, data):
    destination.write(data) # The interpreter just attempts the lookup dynamically
```

## Mixins: Composition via Multiple Inheritance

A **Mixin** is a highly specific architectural pattern. It is a small class designed exclusively to provide a single slice of functionality (like logging, authentication checking, or JSON serialization) to other classes via multiple inheritance. 

Mixins are never meant to be instantiated on their own. They typically do not contain an `__init__` method, and they hold no state (no instance attributes). They provide a mechanism to share behavior horizontally across unrelated classes, bypassing the rigidity and fragility of deep vertical inheritance trees.

```python
import json

class JSONSerializeMixin:
    """A Mixin that provides serialization capabilities without maintaining state."""
    def to_json(self):
        return json.dumps(self.__dict__)

# User inherits core behavior from object, and serialization capabilities from the Mixin
class User(JSONSerializeMixin):
    def __init__(self, name, role):
        self.name = name
        self.role = role

u = User("Alice", "Admin")
print(u.to_json()) # {"name": "Alice", "role": "Admin"}
```

### Architectural Warning: `__slots__` and Multiple Inheritance

If your classes use `__slots__` to optimize memory (by suppressing the creation of the `__dict__` hash map), multiple inheritance becomes treacherous. If multiple parent classes define `__slots__`, Python will refuse to compile the child class. Only one parent in the inheritance graph can possess a `__dict__` or define non-empty `__slots__`. Mixins must be completely empty (no `__slots__`, no state) to safely combine with slotted base classes.

## Interview Questions

**Q: What is the exact purpose of the C3 Linearization algorithm in Python?**
It mathematically computes the Method Resolution Order (MRO) for complex multiple-inheritance hierarchies. It guarantees that a child class is always searched before its parents, that multiple parents are searched in the exact left-to-right order they were defined, and that the hierarchy graph is monotonic (consistent). If the graph contains unresolvable circular dependencies, C3 throws an exception at class creation time.

**Q: How does `super()` behave differently in Python compared to Java or C++?**
In Java/C++, `super` is a static keyword pointing directly to the nominal parent class. In Python, `super()` returns a dynamic proxy object. When a method is called, this proxy inspects the `__mro__` of the *current instance type* and routes the call to the next class in that sequence. This allows `super()` in a sibling class (like `Logger`) to route calls to another sibling class (like `Database`) in a multiple-inheritance diamond.

**Q: Explain the architectural difference between Polymorphism via Inheritance and Duck Typing.**
Polymorphism via Inheritance (Nominal Subtyping) requires objects to share a common base class to guarantee interface conformity to the compiler. Duck Typing (Structural Subtyping) is dynamic polymorphism where the interpreter ignores inheritance entirely and simply attempts to invoke the method at runtime, succeeding if the method exists in the object's `__dict__` or class MRO.

**Q: What is the distinction between Inheritance (IS-A) and Composition (HAS-A)?**
Inheritance tightly couples classes based on identity (a `PostgresDriver` IS-A `DatabaseDriver`). Composition couples classes by embedding instances inside one another (a `DatabaseDriver` HAS-A `ConnectionPool`). Modern software architecture strongly favors Composition over Inheritance, as it creates looser coupling, avoids deep fragile MRO hierarchies, and allows dependencies to be swapped at runtime via dependency injection.

**Q: How do you design a safe Mixin?**
A safe Mixin must not contain an `__init__` method, must not declare any instance state (attributes), and should not define `__slots__`. It should solely consist of pure methods that operate on expected state provided by the concrete classes that inherit the Mixin.

## Summary

- **Inheritance (`tp_base`):** An IS-A relationship allowing child classes to reuse parent memory structures.
- **Multiple Inheritance:** A class inheriting from multiple, independent base classes concurrently.
- **MRO (Method Resolution Order):** The strict sequence in which Python searches for attributes, calculated via the C3 Linearization algorithm.
- **`super()`:** A dynamic proxy object that delegates calls to the next class in the MRO sequence, preventing duplicate `__init__` calls.
- **Duck Typing:** Dynamic runtime polymorphism based purely on method presence rather than rigid inheritance hierarchies.
- **Mixins:** Small, focused, stateless classes used to inject shared behavior horizontally across unrelated architectures.
