## System Telemetry

In production systems, `print()` is insufficient for diagnostics. It writes synchronously to standard output without metadata, severity routing, or file persistence. 

Python provides the `logging` module to establish a structured telemetry pipeline. This pipeline filters messages by severity and routes them to multiple destinations—such as the console, log files, or remote monitoring servers—simultaneously.

## The Logging Pipeline

The logging workflow consists of three core mechanical components:
1. **Logger**: The entry point. Application code sends messages to the Logger.
2. **Formatter**: Converts the raw log record into a structured string format, injecting metadata like timestamps, file names, and line numbers.
3. **Handler**: The routing mechanism that dictates where the formatted string goes (e.g., `StreamHandler` for console output, `FileHandler` for disk storage).

```python
import logging
import sys

# 1. Create the Logger (use __name__ to identify the module context)
logger = logging.getLogger(__name__)
logger.setLevel(logging.DEBUG) # Master switch: allow DEBUG and above

# 2. Define the Formatter
formatter = logging.Formatter(
    "%(asctime)s | %(levelname)-8s | %(name)s | %(message)s"
)

# 3. Configure Handlers
# Route INFO and above to the console
console_handler = logging.StreamHandler(sys.stdout)
console_handler.setLevel(logging.INFO)
console_handler.setFormatter(formatter)

# Route DEBUG and above to a file
file_handler = logging.FileHandler("system.log")
file_handler.setLevel(logging.DEBUG)
file_handler.setFormatter(formatter)

# Attach handlers to the logger
logger.addHandler(console_handler)
logger.addHandler(file_handler)

# Execution
logger.debug("Database query executed") # Routed to file only
logger.error("Database connection lost") # Routed to file AND console
```

## Standard Severity Levels

The pipeline filters messages based on integer severity values. If a handler is set to `WARNING` (30), it drops `INFO` (20) and `DEBUG` (10) messages entirely.

| Level | Integer Value | Usage |
| :--- | :--- | :--- |
| `DEBUG` | 10 | Granular diagnostic variables for development. |
| `INFO` | 20 | State transitions and normal lifecycle events. |
| `WARNING` | 30 | Recoverable anomalies; the program continues. |
| `ERROR` | 40 | Operation failure; the specific task failed. |
| `CRITICAL`| 50 | Fatal failure causing immediate process termination. |

By default, the root logger is configured to drop anything below `WARNING`.

## Exception Telemetry

When an exception occurs, standard log statements require manual traceback extraction. The logging module provides `logger.exception()` to automatically capture the active thread's stack trace and inject it into the log payload at the `ERROR` level.

```python
import logging

logger = logging.getLogger(__name__)

def process_payment(amount):
    try:
        if amount < 0:
            raise ValueError("Negative amount")
    except ValueError:
        # Logs as ERROR and automatically appends the multi-line traceback
        logger.exception("Payment processing failed")
```

## Interactive Debugging (PDB)

When logging is insufficient to track down state corruption, Python provides the `pdb` (Python Debugger) module to pause the Virtual Machine and inject an interactive REPL into the current stack frame.

In Python 3.7+, the `breakpoint()` built-in function is the standard mechanism to intercept execution.

```python
def compute_metrics(data):
    total = 0
    for value in data:
        # Pauses VM execution and opens a terminal prompt
        breakpoint() 
        total += value
    return total
```

### Core PDB Commands

When the VM halts at a breakpoint, you can control execution using these commands:
- `n` (next): Execute the current line and step to the next line.
- `s` (step): Step *into* a function call.
- `c` (continue): Resume VM execution until the next breakpoint is encountered.
- `p var`: Print the memory value of `var`.
- `l` (list): Display the surrounding source code context.
- `q` (quit): Terminate the debugger and the program.

## Debugging Without Breakpoints

If you cannot halt the VM, you can still extract detailed state information using the `traceback` module.

```python
import traceback
import logging

logger = logging.getLogger(__name__)

try:
    1 / 0
except Exception:
    # Extracts the stack trace into a string variable
    tb_str = traceback.format_exc()
    logger.error("Critical fault:\n%s", tb_str)
```

## Interview Questions

**Q: Why should you instantiate loggers using `logging.getLogger(__name__)` instead of `logging.info()`?**
Using `__name__` binds the logger to the specific module's namespace (e.g., `app.database.postgres`). Because the logging hierarchy mirrors the package structure, this allows developers to configure telemetry for specific subsystems (e.g., muting `app.database` while leaving `app.api` at DEBUG level). Relying on the global root logger (`logging.info()`) conflates all messages, making large systems impossible to trace.

**Q: What is the mechanical difference between `logger.setLevel()` and `handler.setLevel()`?**
`logger.setLevel()` acts as the primary gatekeeper; if a message's severity is lower than the logger's level, it is instantly discarded. If it passes, the message is propagated to the Handlers. `handler.setLevel()` dictates whether a *specific routing destination* will accept the message. You can configure a logger to pass all `DEBUG` messages, while a specific file handler drops everything below `ERROR`.

**Q: How do you globally disable `breakpoint()` statements in a production environment?**
The `breakpoint()` function executes the hook defined in `sys.breakpointhook()`. You can disable it globally by setting the environment variable `PYTHONBREAKPOINTHOOK=0`. This instructs the VM to bypass all breakpoints without requiring any code modification.

**Q: How does `logging` affect performance in high-throughput systems, and how do you optimize it?**
String formatting is computationally expensive. Writing `logger.debug(f"Data: {huge_dict}")` forces the VM to format the string *before* evaluating the severity level. If the level is set to `INFO`, the computation was wasted. You should use deferred formatting: `logger.debug("Data: %s", huge_dict)`. The logging engine will skip the string interpolation entirely if the configured log level drops the message.

## Summary

- **Telemetry Pipeline:** Loggers capture data, Formatters structure it, and Handlers route it to destinations.
- **Severity Levels:** A numerical filtering mechanism (DEBUG=10 to CRITICAL=50).
- **`logger.exception()`**: Automatically captures and injects full stack traces at the ERROR level.
- **Hierarchy:** Loggers are bound to modules via `__name__` for granular subsystem control.
- **`breakpoint()`**: Halts the VM to allow interactive stack frame inspection via `pdb`.
- **Deferred Evaluation:** Use `%s` interpolation (`logger.debug("Val: %s", val)`) to avoid expensive string formatting when logs are muted.
