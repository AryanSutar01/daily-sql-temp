## Dataclasses and NamedTuples: Code Generation, `__slots__`, and Memory Efficiency

When constructing complex, data-intensive software architectures, developers frequently need structural containers to marshal data between subsystems. Using a standard Python `class` requires excessive boilerplate: writing a custom `__init__`, manually defining a `__repr__` for logging, and implementing `__eq__` for comparisons. 

Python provides two advanced architectural solutions to eliminate this boilerplate via metaprogramming and structural optimization: **Dataclasses** and **NamedTuples**.

## The Metaprogramming of `@dataclass`

Introduced in Python 3.7 (PEP 557), `@dataclass` is a class decorator that acts as a **dynamic code generator**. 

When Python compiles a class, it stores the type hints in the `__annotations__` dictionary. The `@dataclass` decorator inspects this dictionary at class creation time. It then physically generates the Abstract Syntax Tree (AST) code for the `__init__`, `__repr__`, and `__eq__` methods as strings, compiles them via `exec()`, and attaches the compiled bytecode directly to the class via `setattr()`. 

Because dataclasses generate standard Python methods, they are structurally identical to normal classes. They support deep inheritance, custom methods, and standard mutability.

```python
from dataclasses import dataclass, field

@dataclass
class NetworkNode:
    ip_address: str
    port: int
    
    # The Mutable Default Trap is solved using default_factory
    active_connections: list = field(default_factory=list)
    
    # Exclude sensitive data from the auto-generated __repr__
    _secret_key: str = field(default="hidden", repr=False)

node = NetworkNode("192.168.1.1", 8080)
# The dynamically generated __repr__ in action:
# NetworkNode(ip_address='192.168.1.1', port=8080, active_connections=[])
```

### The Mutable Default Trap
If you define a dataclass field as `active_connections: list = []`, that exact list instance is evaluated once and stored in the Class Object's memory (`PyTypeObject`). Every instance of the dataclass will share the exact same memory pointer! Appending to the list in `Node A` will corrupt the list in `Node B`. 

The `field(default_factory=list)` parameter instructs the code generator to execute the `list()` callable inside the `__init__`, guaranteeing a brand-new memory allocation for every instance.

### Frozen Dataclasses and Hashing

By default, dataclasses are mutable. If you need strict immutability, you must freeze it (`@dataclass(frozen=True)`). 

Architecturally, setting `frozen=True` tells the decorator to synthesize a `__setattr__` method that raises a `FrozenInstanceError` on any assignment. Furthermore, only immutable objects can be safely hashed. By freezing the dataclass, the decorator automatically generates a `__hash__` method, allowing the object to be used as a dictionary key or inserted into a `set`.

```python
@dataclass(frozen=True)
class DatabaseConfig:
    host: str
    port: int

config = DatabaseConfig("localhost", 5432)
# config.port = 8080  # Raises FrozenInstanceError
```

### Post-Initialization Logic

Because the `@dataclass` decorator completely overwrites `__init__`, you cannot place custom validation logic inside the constructor. The architecture provides `__post_init__`, a designated hook that executes the exact millisecond after the auto-generated `__init__` completes its assignments.

```python
@dataclass
class User:
    username: str
    age: int

    def __post_init__(self):
        if self.age < 18:
            raise ValueError("Age restriction violated.")
```

## `NamedTuple`: C-Level Memory Efficiency

A `NamedTuple` (from the `typing` module) solves the same structural problem but employs a fundamentally different memory architecture. 

While a dataclass generates a standard dictionary-backed Python object (consuming significant RAM due to the `__dict__` hash table), a `NamedTuple` inherits directly from Python's C-level `tuple`. 
Because it is a tuple, it has no `__dict__`. It allocates a tightly packed C-array, drastically reducing the memory footprint. It is strictly immutable, natively hashable, and supports high-speed index-based access and unpacking.

```python
from typing import NamedTuple

class Coordinate(NamedTuple):
    latitude: float
    longitude: float

c = Coordinate(34.05, -118.24)

# Memory access operates natively at C-speed because it is a tuple
print(c[0])  # 34.05

# Natively supports structural unpacking
lat, lon = c
```

## Architectural Comparison

| Feature | `@dataclass` | `NamedTuple` |
| :--- | :--- | :--- |
| **Memory Model** | Dictionary-backed object (`__dict__`) | C-level packed array (`tuple`) |
| **Mutability** | Mutable (unless `frozen=True`) | Strictly Immutable at the C-level |
| **Performance** | Standard object overhead | Highly memory-efficient |
| **Methods** | Full OOP support | Methods allowed, but less idiomatic |
| **Unpacking/Indexing** | Requires custom implementation | Native and C-optimized |

## Interview Questions

**Q: Explain the internal code generation process of the `@dataclass` decorator.**
The decorator inspects the class's `__annotations__` dictionary. It dynamically constructs Python source code strings for methods like `__init__` and `__repr__` based on those annotations. It then passes these strings into the `exec()` function to compile them into bytecode, and uses `setattr()` to bind the generated functions to the class object, drastically reducing boilerplate while maintaining native execution speed.

**Q: Why does a dataclass require `field(default_factory=list)` instead of simply `list = []`?**
Default arguments are evaluated exactly once at module load time. If `list = []` is used, the single list object is stored on the Class Object. Every instance will reference the identical memory pointer, causing shared-state corruption. `default_factory` forces the `__init__` to execute the callable upon instantiation, guaranteeing unique heap allocations.

**Q: Structurally, how does a `NamedTuple` differ from a `@dataclass(frozen=True)`?**
While both are immutable, their memory architectures are distinct. A `NamedTuple` is a C-level subclass of `tuple`; it has no `__dict__`, uses less memory, and natively supports index access (`obj[0]`) and structural unpacking (`a, b = obj`). A frozen dataclass is a standard custom object with a `__dict__` that simply overrides `__setattr__` to throw an error; it cannot be unpacked or indexed natively.

**Q: Why are standard dataclasses not hashable by default?**
Hashable objects must guarantee immutability (their hash value must never change over their lifecycle). Because standard dataclasses are mutable, their internal state can change, which would corrupt dictionary lookups. Using `frozen=True` enforces immutability, prompting the decorator to safely auto-generate a `__hash__` method.

## Summary

- **`@dataclass`**: A metaprogramming generator that synthesizes `__init__`, `__repr__`, and `__eq__` via `exec()`.
- **`field()`**: Configures attributes, specifically solving the mutable default trap via `default_factory`.
- **`__post_init__`**: The architectural hook for executing validation logic immediately after the auto-constructor.
- **`NamedTuple`**: A strictly immutable, highly memory-efficient structural class inheriting from the C-level `tuple`.
- **Decision Matrix**: Use `dataclasses` for complex, mutable domain entities. Use `NamedTuples` for massive arrays of read-only, high-performance data structures.
