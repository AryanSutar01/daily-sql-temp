## Design Patterns in Python: Factory, Singleton, Strategy, and Observer

Design Patterns (as popularized by the Gang of Four) are standardized, architectural solutions to common software engineering problems. 

In statically typed, compiled languages like Java or C++, implementing these patterns requires massive amounts of Object-Oriented boilerplate (abstract classes, interfaces, strict type hierarchies). Python's dynamic typing, First-Class Functions (`PyFunctionObject`), and First-Class Classes (`PyTypeObject`) allow engineers to implement these patterns natively, often replacing dozens of lines of Java boilerplate with a single Python decorator or closure.

Understanding how to translate rigid OOP patterns into dynamic Pythonic architecture is a hallmark of senior engineering.

## The Factory Pattern: First-Class Class Objects

The Factory Pattern delegates the instantiation of objects to a central method, allowing the system to determine exactly which subclass to instantiate dynamically at runtime.

In Java, this requires creating a dedicated `Factory` class with a `switch` statement returning various hardcoded instantiations. In Python, Classes are **First-Class Objects** (`PyTypeObject`). You do not need to call them immediately. You can assign the class itself to a dictionary, pass it around memory, and instantiate it dynamically later.

```python
class JSONParser:
    def parse(self, data): return "Parsed JSON"

class XMLParser:
    def parse(self, data): return "Parsed XML"

# Pythonic Factory Architecture: A dynamic mapping of First-Class Class objects
PARSER_REGISTRY = {
    "json": JSONParser,
    "xml": XMLParser
}

def get_parser(format_type):
    # Dynamically retrieves the PyTypeObject and instantiates it ()
    parser_class = PARSER_REGISTRY.get(format_type)
    if not parser_class:
        raise ValueError(f"Unknown format: {format_type}")
    
    return parser_class() # Instantiation happens here

parser = get_parser("json")
```

## The Singleton Pattern: Module-Level Architecture

The Singleton Pattern mathematically guarantees that a class only ever has one active instance in memory. 

Developers often attempt to implement this by overriding the `__new__` dunder method (the C-level `tp_new` slot responsible for raw memory allocation) to return a cached instance. While valid, this is considered an over-engineered anti-pattern in modern Python.

### The Pythonic Singleton: `sys.modules`
The most robust, thread-safe Singleton architecture in Python is **The Module**. 
As dictated by the `sys.modules` cache dictionary, the CPython interpreter mathematically guarantees that a module is compiled and executed exactly *once* per OS process. By instantiating a global object inside a module, you leverage the interpreter's C-level import lock (the GIL) to guarantee thread-safe initialization.

```python
# database.py
class DatabaseConnection:
    def __init__(self):
        self.connected = True

# Instantiated exactly once when the module is first imported.
# This object is now a mathematically guaranteed Singleton across the entire application.
db_instance = DatabaseConnection() 

# consumer.py
# Imports the exact same pointer from the sys.modules cache
from database import db_instance 
```

## The Strategy Pattern: First-Class Callables

The Strategy Pattern allows an algorithm's behavior to be selected dynamically at runtime. 
In Java, this requires defining a strict `Strategy` Interface, creating multiple concrete classes that implement that interface, and passing an instance of the class into a Context object.

Because Python treats functions as First-Class Objects (`PyFunctionObject`), the Strategy Pattern is drastically simplified. You do not need an Interface class. You simply pass the memory pointer of the raw function into the Context object.

```python
# Strategy Algorithms (Raw Callables)
def discount_10_percent(price):
    return price * 0.9

def discount_flat_20(price):
    return price - 20

class ShoppingCart:
    def __init__(self, price, discount_strategy=None):
        self.price = price
        self.discount_strategy = discount_strategy

    def checkout(self):
        if self.discount_strategy:
            # Dynamically executes the injected PyFunctionObject
            return self.discount_strategy(self.price)
        return self.price

# Injecting the strategy dynamically
cart = ShoppingCart(100, discount_strategy=discount_10_percent)
print(cart.checkout()) # 90.0
```

## The Observer Pattern and the Memory Leak Trap

The Observer Pattern defines a one-to-many dependency: when a central Subject changes state, all registered Observers are automatically notified. This is heavily utilized in UI frameworks and Event-Driven systems.

Architecturally, the Subject maintains a standard `list` of Observers. When an Observer registers, the Subject appends the Observer to the list, incrementing the Observer's C-level reference count (`ob_refcnt`).

### The Lapsed Listener Memory Leak
This creates a massive architectural vulnerability known as the **Lapsed Listener Problem**. 
If a component in the application finishes its lifecycle and is "deleted" by the user, the component should be destroyed by the Garbage Collector. However, because the central Subject still holds a strong reference to the component in its `observers` list, the reference count never drops to zero. The destroyed component remains permanently locked in RAM (a Memory Leak), and the Subject continues blindly dispatching events to a dead object.

### The Weakref Solution
To build an enterprise-grade Observer pattern, the Subject must use the `weakref` module. A weak reference creates a pointer to an object *without* incrementing its `ob_refcnt`. If the external application deletes the Observer, its reference count hits zero, and the Garbage Collector destroys it immediately. The weak reference in the Subject's list instantly evaluates to `None`, allowing the Subject to safely purge it from the registry.

```python
import weakref

class EventBus:
    def __init__(self):
        # Uses a WeakSet to hold references without incrementing ob_refcnt
        self._observers = weakref.WeakSet()

    def subscribe(self, observer):
        self._observers.add(observer)

    def emit(self, event_data):
        # The WeakSet automatically purges observers that have been Garbage Collected
        for observer in self._observers:
            observer.notify(event_data)

class Logger:
    def notify(self, data):
        print(f"Log: {data}")

bus = EventBus()
log = Logger()
bus.subscribe(log)

# The Logger is destroyed! 
# Because EventBus used a WeakSet, it does not prevent the destruction.
del log 

# EventBus cleanly emits to 0 observers without crashing or leaking memory.
bus.emit("System Booting") 
```

## Interview Questions

**Q: Explain how Python's First-Class objects eliminate the need for verbose Factory classes.**
In strict OOP languages, Classes are structural blueprints, not memory objects, requiring dedicated Factory classes with `switch` statements to orchestrate instantiation. In Python, Classes are `PyTypeObject` instances residing on the heap. Because they are objects, you can place the Class pointers directly into a hash table (`dict`). The Factory pattern is reduced to a single $O(1)$ dictionary lookup that retrieves the Class object and dynamically invokes its `__call__` method to instantiate it.

**Q: Why is overriding `__new__` to create a Singleton considered an anti-pattern compared to Module singletons?**
Overriding `__new__` adds unnecessary metaclass overhead and complexity. More importantly, ensuring thread-safety requires manually implementing Mutex Locks to prevent two OS threads from executing `__new__` simultaneously and creating two instances. By simply instantiating the object globally inside a module (`instance = MyClass()`), you mathematically rely on the CPython `sys.modules` Import Lock, which automatically enforces thread-safe Singleton execution at the C-level without any developer boilerplate.

**Q: Architecturally, how does Python simplify the Strategy Pattern?**
The Strategy Pattern requires injecting dynamic behavior into a Context object. In Java, this mandates defining a strict Interface class and passing polymorphic objects. Python treats functions as `PyFunctionObject`s. Therefore, you bypass the Interface class entirely and simply pass the raw function pointer into the Context object as an argument. The Context invokes the function dynamically, eliminating deep inheritance hierarchies.

**Q: What is the Lapsed Listener Problem, and how do Weak References solve it?**
The Lapsed Listener Problem is a Memory Leak occurring in the Observer Pattern. The central Subject maintains a list of Observers, holding a strong reference to each. When an Observer is logically "deleted" by the program, it is not destroyed in RAM because the Subject's list prevents its reference count from reaching zero. By utilizing `weakref.WeakSet`, the Subject creates a pointer without incrementing the reference count. When the application deletes the Observer, it is instantly garbage collected, and the WeakSet automatically safely removes the dead pointer.

## Summary

- **First-Class Objects:** Classes (`PyTypeObject`) and Functions (`PyFunctionObject`) are heap-allocated objects that can be stored in dictionaries or passed as variables.
- **Factory Pattern:** Reduced to an $O(1)$ dictionary mapping string keys directly to Class objects.
- **Singleton Pattern:** Reliant on the `sys.modules` Import Lock to guarantee mathematically safe, single-instance evaluation.
- **Strategy Pattern:** Bypasses Interface classes by injecting raw Callable function pointers directly into Context objects.
- **Observer Pattern:** Must utilize `weakref` to prevent strong references from trapping destroyed objects in RAM (Lapsed Listener Memory Leaks).
