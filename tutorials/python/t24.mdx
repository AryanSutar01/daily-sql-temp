## What Are Design Patterns?

Design patterns are proven, reusable solutions to commonly occurring problems in software design. They're not code - they're templates or blueprints you adapt to your situation.

Three categories:
- **Creational** - how objects are created (Singleton, Factory, Builder)
- **Structural** - how objects are composed (Decorator, Adapter, Facade)
- **Behavioral** - how objects communicate (Observer, Strategy, Command)

## 1. Singleton Pattern

Ensures a class has **only one instance** throughout the application's lifetime.

```python
class Singleton:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

s1 = Singleton()
s2 = Singleton()
print(s1 is s2)   # True - same object
```

### Thread-Safe Singleton

```python
import threading

class ThreadSafeSingleton:
    _instance = None
    _lock = threading.Lock()

    def __new__(cls):
        if cls._instance is None:
            with cls._lock:
                if cls._instance is None:   # double-checked locking
                    cls._instance = super().__new__(cls)
        return cls._instance
```

### Real-World Use: Database Connection Pool

```python
class DatabasePool:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance._connections = []
            cls._instance._max_connections = 10
        return cls._instance

    def get_connection(self):
        if len(self._connections) < self._max_connections:
            conn = f"Connection-{len(self._connections) + 1}"
            self._connections.append(conn)
            return conn
        raise Exception("No connections available")

pool1 = DatabasePool()
pool2 = DatabasePool()
print(pool1 is pool2)   # True - one shared pool
```

## 2. Factory Pattern

Delegates the **creation of objects** to a factory function or class, hiding the instantiation logic from the caller.

### Simple Factory

```python
class Dog:
    def speak(self) -> str:
        return "Woof!"

class Cat:
    def speak(self) -> str:
        return "Meow!"

class Bird:
    def speak(self) -> str:
        return "Tweet!"

def animal_factory(animal_type: str):
    animals = {
        "dog": Dog,
        "cat": Cat,
        "bird": Bird,
    }
    cls = animals.get(animal_type.lower())
    if cls is None:
        raise ValueError(f"Unknown animal: {animal_type}")
    return cls()

a = animal_factory("dog")
print(a.speak())   # Woof!
```

### Factory Method Pattern (with inheritance)

```python
from abc import ABC, abstractmethod

class Notification(ABC):
    @abstractmethod
    def send(self, message: str) -> None: ...

class EmailNotification(Notification):
    def send(self, message: str) -> None:
        print(f"Email: {message}")

class SMSNotification(Notification):
    def send(self, message: str) -> None:
        print(f"SMS: {message}")

class PushNotification(Notification):
    def send(self, message: str) -> None:
        print(f"Push: {message}")

class NotificationFactory:
    @staticmethod
    def create(channel: str) -> Notification:
        channels = {
            "email": EmailNotification,
            "sms": SMSNotification,
            "push": PushNotification,
        }
        cls = channels.get(channel)
        if not cls:
            raise ValueError(f"Unsupported channel: {channel}")
        return cls()

# Client code doesn't know about concrete classes
notifier = NotificationFactory.create("email")
notifier.send("Your order has been placed!")

notifier = NotificationFactory.create("sms")
notifier.send("OTP: 123456")
```

## 3. Observer Pattern

Defines a **one-to-many dependency** - when one object (subject) changes state, all its dependents (observers) are notified automatically.

```python
from abc import ABC, abstractmethod
from typing import List

class Observer(ABC):
    @abstractmethod
    def update(self, event: str, data: dict) -> None: ...

class Subject:
    def __init__(self):
        self._observers: List[Observer] = []

    def subscribe(self, observer: Observer) -> None:
        self._observers.append(observer)

    def unsubscribe(self, observer: Observer) -> None:
        self._observers.remove(observer)

    def notify(self, event: str, data: dict) -> None:
        for observer in self._observers:
            observer.update(event, data)

# Concrete observers
class EmailAlert(Observer):
    def update(self, event: str, data: dict) -> None:
        print(f"Email Alert - {event}: {data}")

class SMSAlert(Observer):
    def update(self, event: str, data: dict) -> None:
        print(f"SMS Alert - {event}: {data}")

class AuditLogger(Observer):
    def update(self, event: str, data: dict) -> None:
        print(f"Audit Log - {event}: {data}")

# Concrete subject
class OrderService(Subject):
    def place_order(self, order_id: int, amount: float) -> None:
        print(f"Order {order_id} placed for ₹{amount}")
        self.notify("ORDER_PLACED", {"order_id": order_id, "amount": amount})

    def cancel_order(self, order_id: int) -> None:
        print(f"Order {order_id} cancelled")
        self.notify("ORDER_CANCELLED", {"order_id": order_id})

service = OrderService()
service.subscribe(EmailAlert())
service.subscribe(SMSAlert())
service.subscribe(AuditLogger())

service.place_order(101, 2999.0)
# Order 101 placed for ₹2999.0
# Email Alert - ORDER_PLACED: {'order_id': 101, 'amount': 2999.0}
# SMS Alert - ORDER_PLACED: {'order_id': 101, 'amount': 2999.0}
# Audit Log - ORDER_PLACED: {'order_id': 101, 'amount': 2999.0}
```

## 4. Strategy Pattern

Defines a family of algorithms, encapsulates each one, and makes them interchangeable at runtime.

```python
from abc import ABC, abstractmethod

class SortStrategy(ABC):
    @abstractmethod
    def sort(self, data: list) -> list: ...

class BubbleSort(SortStrategy):
    def sort(self, data: list) -> list:
        d = data[:]
        n = len(d)
        for i in range(n):
            for j in range(n - i - 1):
                if d[j] > d[j+1]:
                    d[j], d[j+1] = d[j+1], d[j]
        return d

class QuickSort(SortStrategy):
    def sort(self, data: list) -> list:
        if len(data) <= 1:
            return data
        pivot = data[len(data)//2]
        left = [x for x in data if x < pivot]
        mid = [x for x in data if x == pivot]
        right = [x for x in data if x > pivot]
        return self.sort(left) + mid + self.sort(right)

class Sorter:
    def __init__(self, strategy: SortStrategy):
        self._strategy = strategy

    def set_strategy(self, strategy: SortStrategy) -> None:
        self._strategy = strategy

    def sort(self, data: list) -> list:
        return self._strategy.sort(data)

sorter = Sorter(BubbleSort())
print(sorter.sort([5, 3, 1, 4, 2]))

sorter.set_strategy(QuickSort())
print(sorter.sort([5, 3, 1, 4, 2]))
```

## 5. Decorator Pattern (Structural)

Adds behaviour to an object dynamically without modifying its class.

```python
from abc import ABC, abstractmethod

class Coffee(ABC):
    @abstractmethod
    def cost(self) -> float: ...

    @abstractmethod
    def description(self) -> str: ...

class BasicCoffee(Coffee):
    def cost(self) -> float:
        return 50.0

    def description(self) -> str:
        return "Basic Coffee"

class CoffeeDecorator(Coffee):
    def __init__(self, coffee: Coffee):
        self._coffee = coffee

    def cost(self) -> float:
        return self._coffee.cost()

    def description(self) -> str:
        return self._coffee.description()

class Milk(CoffeeDecorator):
    def cost(self) -> float:
        return self._coffee.cost() + 10.0

    def description(self) -> str:
        return self._coffee.description() + " + Milk"

class Sugar(CoffeeDecorator):
    def cost(self) -> float:
        return self._coffee.cost() + 5.0

    def description(self) -> str:
        return self._coffee.description() + " + Sugar"

coffee = BasicCoffee()
coffee = Milk(coffee)
coffee = Sugar(coffee)
coffee = Milk(coffee)

print(coffee.description())   # Basic Coffee + Milk + Sugar + Milk
print(coffee.cost())          # 75.0
```

## Interview Questions

**Q: What is the Singleton pattern and when would you use it?**
Singleton ensures a class has only one instance. Use it for shared resources like a database connection pool, configuration manager, or logger - where multiple instances would cause conflicts or waste resources.

**Q: What is the difference between Factory Method and Simple Factory?**
A simple factory is just a function or static method that creates objects. Factory Method is a design pattern where the creation logic is deferred to subclasses - each subclass decides what to instantiate.

**Q: What is the Observer pattern? Give a real-world example.**
Observer defines a one-to-many relationship - when one object changes, all subscribed observers are notified. Real-world examples: event systems, UI frameworks (button click → multiple handlers), notification systems, pub/sub messaging.

**Q: What is the Strategy pattern?**
Strategy defines a family of interchangeable algorithms and lets you switch between them at runtime. Example: a payment system that supports multiple payment methods (credit card, UPI, wallet) - each is a strategy, swappable without changing the checkout code.

**Q: How is the Decorator pattern different from Python's `@decorator` syntax?**
The structural Decorator pattern wraps an object to add behaviour dynamically. Python's `@decorator` syntax is a language feature that wraps a function. They share the same concept - wrapping to extend behaviour - but operate at different levels (object vs function).

## Summary

- **Singleton** - one instance only; use for shared global resources; make thread-safe with a lock
- **Factory** - decouple object creation from usage; client doesn't know the concrete class
- **Observer** - one-to-many event notification; subject notifies all subscribers on state change
- **Strategy** - swap algorithms at runtime without changing the calling code
- **Decorator (structural)** - add behaviour to objects dynamically by wrapping them
- Design patterns improve code reusability, flexibility, and communication between developers
