## Two Approaches to Database Access in Python

Python gives you two distinct ways to interact with databases, each targeting a different level of abstraction:

```
Raw drivers (psycopg2, mysql-connector)
  → Direct SQL execution — you write SQL strings, the driver executes them
  → Full control over every query, transaction, and result format
  → Best for data engineering, ETL pipelines, analytics, and bulk operations
  → Minimal overhead between your Python code and the database

SQLAlchemy
  → Two modes:
      Core — SQL expression builder (database-agnostic, programmatic SQL)
      ORM  — Python classes = database tables (object-relational mapping)
  → More abstraction; works across MySQL, PostgreSQL, SQLite, Oracle
  → Best for web applications, business logic with complex data models
```

The choice between them is architectural: raw drivers prioritize control and performance; SQLAlchemy prioritizes portability and developer productivity at the cost of some transparency.

## Transactions — The Foundation of Database Integrity

Before writing any code, understanding transactions is essential. A **transaction** is a sequence of database operations that are treated as a single atomic unit. The defining property is **ACID**:

- **Atomicity**: All operations in the transaction succeed together, or none of them are applied. There is no partial state.
- **Consistency**: The database moves from one valid state to another — constraints and rules are never violated.
- **Isolation**: Concurrent transactions do not interfere with each other — each sees a consistent snapshot.
- **Durability**: Once committed, the data survives system crashes and restarts.

This is why database connections need explicit commit/rollback:

```python
# Without transaction control — dangerous
conn = psycopg2.connect(...)
cursor = conn.cursor()

cursor.execute("UPDATE accounts SET balance = balance - 500 WHERE id = 1")  # debit
# If Python crashes here, we've debited but not credited — money disappears!
cursor.execute("UPDATE accounts SET balance = balance + 500 WHERE id = 2")  # credit
conn.commit()   # both changes are applied atomically, or neither is
```

If an error occurs between the two `UPDATE` statements, `conn.rollback()` reverts both, leaving the database in its original state. This is why every production database interaction should be inside a transaction managed by a context manager.

## psycopg2 — Raw PostgreSQL Driver

`psycopg2` is the standard PostgreSQL adapter for Python. It maps Python types to PostgreSQL types and gives you complete control over SQL execution.

```bash
pip install psycopg2-binary
```

```python
import psycopg2

# Basic connection
conn = psycopg2.connect(
    host="localhost",
    port=5432,
    database="mydb",
    user="postgres",
    password="secret",
)

cursor = conn.cursor()

# Execute a query — ALWAYS use parameterized queries
cursor.execute("SELECT id, name, salary FROM employees WHERE salary > %s", (80000,))
rows = cursor.fetchall()    # list of tuples

for row in rows:
    print(row)   # (1, 'Alice', 90000)

# Fetch one row
cursor.execute("SELECT * FROM employees WHERE id = %s", (1,))
row = cursor.fetchone()   # None if no match

cursor.close()
conn.close()
```

**Why `%s` and not f-strings?** Parameterized queries (`%s`) pass values separately from the SQL statement. The psycopg2 driver handles escaping, so a user cannot inject malicious SQL. An f-string like `f"WHERE name = '{user_input}'"` is vulnerable to SQL injection — a critical security flaw. **Always use parameterized queries.**

## Always Use Context Managers

Context managers guarantee that connections are properly closed and transactions are committed or rolled back, even when exceptions occur.

```python
import psycopg2
from contextlib import contextmanager

@contextmanager
def get_connection():
    conn = psycopg2.connect(
        host="localhost", database="mydb",
        user="postgres", password="secret",
    )
    try:
        yield conn
        conn.commit()      # commit if no exception
    except Exception:
        conn.rollback()    # rollback if exception occurred
        raise
    finally:
        conn.close()       # always close the connection

# Usage — connection lifecycle managed automatically
with get_connection() as conn:
    with conn.cursor() as cur:
        cur.execute("SELECT * FROM employees")
        rows = cur.fetchall()
```

The pattern `try → yield → commit / except → rollback / finally → close` is the production-safe transaction boundary. It ensures:
1. Successful operations are committed
2. Failed operations are rolled back (database is not left in a partial state)
3. The connection is always returned to the pool or closed

## INSERT, UPDATE, DELETE

DML (Data Manipulation Language) operations modify data and **must be followed by `conn.commit()`** (or they're rolled back when the connection closes).

```python
with get_connection() as conn:
    with conn.cursor() as cur:
        # INSERT a single row
        cur.execute(
            "INSERT INTO employees (name, salary, department) VALUES (%s, %s, %s)",
            ("Alice", 90000, "Engineering"),
        )

        # INSERT many rows efficiently — executemany sends all rows in one network round-trip
        data = [("Bob", 75000, "Marketing"), ("Carol", 85000, "Engineering")]
        cur.executemany(
            "INSERT INTO employees (name, salary, department) VALUES (%s, %s, %s)",
            data,
        )
        # For very large bulk inserts, use COPY command or psycopg2.extras.execute_values
        # — much faster than executemany for 10K+ rows

        # UPDATE
        cur.execute(
            "UPDATE employees SET salary = %s WHERE id = %s",
            (95000, 1),
        )
        print(f"Rows updated: {cur.rowcount}")   # number of affected rows

        # DELETE
        cur.execute("DELETE FROM employees WHERE id = %s", (5,))
        print(f"Rows deleted: {cur.rowcount}")
```

## Fetch Results as Dicts

By default, psycopg2 returns rows as plain tuples. `RealDictCursor` returns rows as dictionaries, making the code more readable and robust to column order changes.

```python
import psycopg2.extras

with psycopg2.connect(...) as conn:
    with conn.cursor(cursor_factory=psycopg2.extras.RealDictCursor) as cur:
        cur.execute("SELECT id, name, salary FROM employees")
        rows = cur.fetchall()

for row in rows:
    print(row["name"], row["salary"])   # dict access by column name
    # vs tuple: row[0], row[1] — fragile if column order changes
```

## pandas + psycopg2

For analytical workloads, loading SQL results directly into a pandas DataFrame is more efficient than fetching rows and manually constructing the DataFrame.

```python
import pandas as pd
import psycopg2

conn = psycopg2.connect(host="localhost", database="mydb", user="postgres", password="secret")

# Read SQL query directly into DataFrame — most efficient approach
df = pd.read_sql(
    "SELECT * FROM employees WHERE department = 'Engineering'",
    conn
)
print(df.head())

# Parameterized query with pandas
df = pd.read_sql(
    "SELECT * FROM employees WHERE salary > %(min_salary)s",
    conn,
    params={"min_salary": 80000}
)

conn.close()
```

## SQLAlchemy — Core

SQLAlchemy Core is a SQL expression language that lets you write database-agnostic SQL in Python. It is not an ORM — you still write "SQL", just using Python objects instead of strings.

```bash
pip install sqlalchemy psycopg2-binary
```

```python
from sqlalchemy import create_engine, text

# Connection string format: dialect+driver://user:password@host:port/database
engine = create_engine(
    "postgresql+psycopg2://postgres:secret@localhost:5432/mydb",
    echo=False,      # True to log all generated SQL (useful for debugging)
    pool_size=5,     # number of persistent connections in the pool
    pool_timeout=30, # seconds to wait for an available connection
    pool_recycle=3600,  # recycle connections after 1 hour (avoids stale connections)
)

# Execute raw SQL with named parameters
with engine.connect() as conn:
    result = conn.execute(
        text("SELECT id, name, salary FROM employees WHERE salary > :min_salary"),
        {"min_salary": 80000}
    )
    for row in result:
        print(row.name, row.salary)   # attribute-style access
```

## SQLAlchemy — pandas Integration

The most common use of SQLAlchemy in data engineering is as the connection engine for pandas read/write operations.

```python
import pandas as pd
from sqlalchemy import create_engine

engine = create_engine("postgresql+psycopg2://postgres:secret@localhost:5432/mydb")

# Read
df = pd.read_sql("SELECT * FROM orders WHERE status = 'completed'", engine)

# Read with parameters
df = pd.read_sql(
    "SELECT * FROM orders WHERE created_at >= %(start_date)s",
    engine,
    params={"start_date": "2024-01-01"},
)

# Write
df.to_sql("processed_orders", engine, if_exists="append", index=False)
df.to_sql("staging_table", engine, if_exists="replace", index=False, chunksize=1000)
# if_exists:
#   "fail"    — raise error if table exists (default)
#   "replace" — drop and recreate the table before inserting
#   "append"  — add rows to existing table
```

`chunksize=1000` tells pandas to insert rows in batches of 1,000 rather than all at once. This prevents memory issues and avoids single enormous INSERT statements that can timeout or overflow database limits.

## SQLAlchemy ORM

The ORM (Object-Relational Mapper) maps Python classes to database tables. You interact with Python objects and SQLAlchemy translates your operations into SQL. This is the approach used by most web frameworks (Flask-SQLAlchemy, Django ORM).

```python
from sqlalchemy import Column, Integer, String, Float, create_engine
from sqlalchemy.orm import DeclarativeBase, Session

class Base(DeclarativeBase):
    pass

class Employee(Base):
    __tablename__ = "employees"

    id = Column(Integer, primary_key=True)
    name = Column(String(100), nullable=False)
    salary = Column(Float)
    department = Column(String(100))

    def __repr__(self):
        return f"Employee(id={self.id}, name={self.name}, salary={self.salary})"

engine = create_engine("postgresql+psycopg2://postgres:secret@localhost:5432/mydb")
Base.metadata.create_all(engine)   # create tables if they don't exist

# CRUD Operations
with Session(engine) as session:
    # Create
    emp = Employee(name="Alice", salary=90000, department="Engineering")
    session.add(emp)
    session.commit()

    # Read — SELECT queries
    employees = session.query(Employee).filter(Employee.salary > 80000).all()
    for e in employees:
        print(e)

    # Update — modify the object, commit flushes changes
    emp = session.query(Employee).filter_by(name="Alice").first()
    emp.salary = 95000
    session.commit()

    # Delete
    session.query(Employee).filter_by(name="Alice").delete()
    session.commit()
```

**When ORM, when raw SQL?**
- ORM: web applications with business entities, CRUD APIs, code that benefits from Python object manipulation
- Raw SQL / Core: analytics, ETL, bulk operations, performance-critical queries, complex joins the ORM handles poorly

## Connection Pooling

Opening a database connection involves network overhead: DNS resolution, TCP handshake, authentication, and session initialization. This takes 10–100ms per connection. Connection pooling pre-opens a set of connections and reuses them, eliminating this overhead from every query.

```python
from sqlalchemy import create_engine
from sqlalchemy.pool import QueuePool

engine = create_engine(
    "postgresql+psycopg2://postgres:secret@localhost:5432/mydb",
    poolclass=QueuePool,
    pool_size=10,       # number of persistent connections maintained
    max_overflow=20,    # additional connections allowed when pool is exhausted
    pool_timeout=30,    # seconds to wait for a connection before raising PoolTimeout
    pool_recycle=3600,  # recycle connections after 1 hour (prevents stale connections)
)
# This engine should be created ONCE at application startup, not per request
```

**Create one engine per application, not one per request.** The engine manages the connection pool. If you create a new engine per request, you create a new connection per request — eliminating all the benefits of pooling.

## Environment Variables for Credentials

```python
import os
from sqlalchemy import create_engine
from dotenv import load_dotenv

load_dotenv()   # load from .env file for local development

DB_URL = (
    f"postgresql+psycopg2://{os.getenv('DB_USER')}:{os.getenv('DB_PASSWORD')}"
    f"@{os.getenv('DB_HOST')}:{os.getenv('DB_PORT', 5432)}/{os.getenv('DB_NAME')}"
)

engine = create_engine(DB_URL)
```

In production, environment variables are injected by the deployment platform (Kubernetes secrets, AWS Secrets Manager, Heroku config vars) — the `.env` file is only for local development and must never be committed to version control.

## Interview Questions

**Q: What is the difference between psycopg2 and SQLAlchemy?**
psycopg2 is a low-level PostgreSQL driver — you write raw SQL strings and it executes them against PostgreSQL specifically. SQLAlchemy is a higher-level toolkit with two modes: Core (a database-agnostic SQL expression builder) and ORM (maps Python classes to tables). psycopg2 gives you full SQL control and maximum performance. SQLAlchemy adds database portability, an integrated connection pool, and the ORM for object-oriented data access.

**Q: Why should you use parameterized queries instead of string formatting?**
String formatting (f-strings, `%` operator) directly embeds user input into the SQL string. A malicious user can inject SQL commands that change the query's intent — this is SQL injection, one of the most dangerous web vulnerabilities. Parameterized queries send the SQL statement and values separately — the database treats the values as data, never as SQL code.

**Q: What is connection pooling and why is it important?**
Opening a database connection takes 10–100ms (TCP handshake + authentication). Without pooling, every query in a web application would require a new connection — too slow for production. A connection pool maintains a set of pre-opened, authenticated connections and reuses them across requests. SQLAlchemy's engine includes a built-in pool, which is why you create one engine at startup rather than one per request.

**Q: What is ACID and why does it matter?**
ACID is the set of properties that guarantee database transaction reliability: **Atomicity** (all-or-nothing), **Consistency** (valid state to valid state), **Isolation** (concurrent transactions don't interfere), **Durability** (committed data survives crashes). In practice, ACID means you can safely transfer money between accounts — either both the debit and credit happen, or neither does. Without ACID guarantees, concurrent writes could corrupt data.

**Q: What does `if_exists="replace"` vs `"append"` do in `to_sql()`?**
`"replace"` drops the entire table and recreates it before inserting — use for full refreshes where the table should contain exactly the new data. `"append"` inserts rows into an existing table without touching existing data — use for incremental loads. `"fail"` (default) raises an error if the table already exists — use when you want to prevent accidental overwrites.

**Q: When would you use the SQLAlchemy ORM vs raw SQL?**
Use the ORM in web applications where you model business entities (User, Order, Product), perform CRUD operations, and benefit from Python object manipulation and relationship navigation. Use raw SQL or SQLAlchemy Core for analytics, ETL pipelines, bulk operations, and complex queries where full SQL control and performance are critical — the ORM's query generation can be inefficient for non-trivial aggregations and joins.

## Summary

- **psycopg2** — low-level PostgreSQL driver; always use parameterized queries (`%s`), never f-strings or `%`
- Context manager: `try → yield → commit / except → rollback / finally → close` — production transaction pattern
- `executemany()` — bulk insert multiple rows; use `execute_values` or COPY for very large batches
- `RealDictCursor` — returns rows as dicts; robust to column order changes
- **SQLAlchemy Core** — SQL expression builder; database-agnostic; works with `pd.read_sql()` / `df.to_sql()`
- **SQLAlchemy ORM** — map Python classes to tables; full CRUD with Python objects; best for web apps
- Connection pool — create one `engine` at startup; `pool_size` persistent connections; `max_overflow` for bursts
- `pool_recycle=3600` — prevent stale connections that silently fail after idle timeout
- Never hardcode credentials — use `os.getenv()` with `python-dotenv` for local development
- **ACID** — Atomicity, Consistency, Isolation, Durability — the foundation of reliable database operations
