## Denormalization: Trade-offs in Distributed Architectures

Denormalization is the architectural admission that joining massive tables at runtime is too computationally expensive for the CPU and memory bandwidth. It is a calculated violation of 3NF (Third Normal Form) to prioritize **Read Latency** over **Write Throughput**.

### The CAP Theorem and Relational Data

While the CAP theorem strictly applies to distributed systems, a similar trade-off exists when denormalizing a single relational database: you are trading immediate consistency for performance.

If you store the `user_name` directly in the `comments` table (denormalization), what happens when the user changes their name?
1. **Synchronous Update (High Consistency):** You write a trigger that locks the `users` row and scans all 5,000 of the user's comments to update the name. This causes massive lock contention and destroys write throughput.
2. **Asynchronous Update (Eventual Consistency):** You update the `users` table immediately, and queue a background job to update the 5,000 comments. The database reads are incredibly fast, but for a few seconds (or minutes), the data is stale (Eventually Consistent).

### OLTP vs OLAP Architectures

- **OLTP (Online Transaction Processing):** E-commerce checkouts, banking ledgers. The priority is data integrity, ACID compliance, and fast writes. **Rule:** Keep OLTP heavily normalized. Let the application cache handle read performance.
- **OLAP (Online Analytical Processing):** Data warehouses, reporting dashboards. The priority is scanning billions of rows to calculate aggregates. **Rule:** Heavily denormalize into Star Schemas (Fact and Dimension tables). The data is usually loaded via batch ETL pipelines, so write amplification is irrelevant.

**Architectural Standard**: Never denormalize your core OLTP schema to fix a slow query. First, try covering indexes. Second, try application-level caching (Redis). If the database *must* serve the read, implement managed denormalization using a **Materialized View**, decoupling the write complexity from the core schema.

## What is Denormalization?

Denormalization is the deliberate introduction of redundancy into a normalized database schema to improve read performance. It trades write complexity for read speed.

```
Normalized (3NF):             Denormalized:
orders → customers             orders (has customer_name stored directly)
orders → products              orders (has product_name stored directly)

Read: requires JOINs           Read: no JOINs needed - faster
Write: no redundancy           Write: must update name in multiple places
```

## When to Denormalize

**Consider denormalization when:**
- Queries require many expensive JOINs that run thousands of times per second
- The data being denormalized changes rarely (product names, category names)
- You're building a read-heavy analytics/reporting system
- You're building a data warehouse (star schema)

**Don't denormalize when:**
- The denormalized data changes frequently (user email, price - these cause data drift)
- Your system is primarily write-heavy
- The JOIN performance is acceptable - measure before optimizing

## Common Denormalization Patterns

### 1. Storing Computed Values

Storing computed values (like an order total) is the most common denormalization pattern in e-commerce systems. The trade-off is explicit: you're moving computation cost from read time to write time. Every read is instant (no SUM join), but every write must keep the stored value synchronized. The synchronization mechanism — whether a database trigger, an ORM lifecycle hook, or a message queue event — becomes critical infrastructure. If it fails silently, your stored totals drift from reality, producing subtle financial discrepancies.

```sql
-- Normalized: calculate total on every read
SELECT SUM(oi.quantity * oi.unit_price) FROM order_items WHERE order_id = 1;

-- Denormalized: store total in orders table
ALTER TABLE orders ADD COLUMN item_total DECIMAL(10,2);
-- Update it when order_items change (trigger or application code)
-- Read is now instant: SELECT item_total FROM orders WHERE id = 1;
```

### 2. Storing Foreign Key Labels

Storing a label (like `category_name`) alongside its foreign key (`category_id`) eliminates a JOIN at read time. But this introduces **update anomalies**: if the category name ever changes (e.g., "Electronics" → "Consumer Electronics"), you must find and update every product row. In a database with proper normalization, changing the category name requires updating exactly one row in the `categories` table, and all products instantly reflect the change. With denormalization, a batch `UPDATE products SET category_name = 'Consumer Electronics'` affecting millions of rows is required.

```sql
-- Normalized: JOIN to get category name
SELECT p.name, c.name AS category
FROM products p JOIN categories c ON p.category_id = c.id;

-- Denormalized: store category_name directly in products
ALTER TABLE products ADD COLUMN category_name VARCHAR(100);
-- Read: SELECT name, category_name FROM products; (no JOIN)
-- Risk: if category name changes, must update all products
```

### 3. Precomputed Aggregates (Summary Tables)

A summary table is a dedicated physical table that stores pre-aggregated metrics. It is a more explicit, controllable form of denormalization than a Materialized View. The `customer_stats` table caches per-customer metrics that would normally require a full scan of `orders` and `order_items`. The update mechanism (a trigger on `orders` or a scheduled cron job) must be carefully designed: triggers update in real-time (accurate but adds write latency), while scheduled jobs batch-update (introduces staleness but zero write overhead).

```sql
-- Create a summary table (updated via trigger or scheduled job)
CREATE TABLE customer_stats (
  customer_id   BIGINT PRIMARY KEY REFERENCES users(id),
  order_count   INT DEFAULT 0,
  total_spent   DECIMAL(12,2) DEFAULT 0,
  last_order_at TIMESTAMPTZ,
  updated_at    TIMESTAMPTZ DEFAULT NOW()
);

-- Dashboard query: instant, no aggregation needed
SELECT u.name, cs.order_count, cs.total_spent
FROM users u
JOIN customer_stats cs ON u.id = cs.customer_id
WHERE cs.total_spent > 50000;
```

### 4. Materialized Views (Managed Denormalization)

A Materialized View is the database's own managed form of denormalization. Unlike a regular View (which is just a stored query), a Materialized View physically writes the query result to disk. Queries against it are just table scans — no JOINs, no aggregations at query time. `REFRESH MATERIALIZED VIEW CONCURRENTLY` rebuilds the cache without taking an exclusive lock — reads continue during refresh. Without `CONCURRENTLY`, refresh takes an exclusive lock, blocking all reads for the duration. The refresh strategy (real-time via trigger, scheduled, or on-demand) determines how stale the data can be.

```sql
-- PostgreSQL: let the database manage the denormalized copy
CREATE MATERIALIZED VIEW monthly_sales AS
SELECT
  DATE_TRUNC('month', created_at) AS month,
  category_id,
  SUM(total) AS revenue
FROM orders o
JOIN order_items oi ON o.id = oi.order_id
JOIN products p ON oi.product_id = p.id
GROUP BY 1, 2;

CREATE INDEX ON monthly_sales(month, category_id);

-- Refresh on a schedule (e.g., nightly)
REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_sales;
```

### 5. Star Schema (Data Warehousing)

In analytics databases, data is deliberately denormalized into fact and dimension tables:

```sql
-- Fact table: transactions
CREATE TABLE fact_sales (
  date_id      INT,
  product_id   INT,
  customer_id  INT,
  region_id    INT,
  quantity     INT,
  revenue      DECIMAL(12,2)
);

-- Dimension tables: denormalized attributes
CREATE TABLE dim_product (
  product_id   INT PRIMARY KEY,
  product_name VARCHAR(200),
  category     VARCHAR(100),    -- denormalized (normally separate table)
  subcategory  VARCHAR(100)     -- denormalized
);
```

This allows analytics queries to be extremely fast - one JOIN to each dimension instead of many nested JOINs through a normalized schema.

## Risks of Denormalization

| Risk | Description | Mitigation |
|------|-------------|-----------|
| Data drift | Denormalized copy gets out of sync with source | Triggers, scheduled jobs, or materialized views |
| Write complexity | Every write must update multiple places | Encapsulate in procedures/triggers |
| Storage bloat | Same data stored multiple times | Acceptable trade-off in most cases |
| Confusion | Developers unsure which is authoritative | Document clearly, use views as interface |

## Summary

- Denormalization adds controlled redundancy to speed up reads
- Common patterns: precomputed totals, stored labels, summary tables, materialized views
- Use when JOINs are too expensive and data changes rarely
- Materialized views are the safest form of denormalization - the database manages the refresh
- Star schema is intentional denormalization for analytics - optimizes for read performance
- Always measure query performance before denormalizing - premature optimization is costly
