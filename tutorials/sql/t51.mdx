## Analytical Architecture: Data Cubes and Columnar Execution

Cohort analysis and Funnel tracking are the foundation of product analytics. However, executing these queries against a production OLTP (Online Transaction Processing) database often leads to catastrophic performance degradation.

### The HashAggregate Memory Exhaustion

To calculate a retention cohort, the database must join a massive `events` table (millions of rows) against a `users` table, extract date metrics, and group the results. 
The Query Optimizer typically executes this via a **HashAggregate**. It attempts to build an in-memory hash table where every key is a combination of `(cohort_month, months_since_join)`. 
If you add more dimensions (e.g., `device_type`, `country`, `marketing_campaign`), you create a **Multidimensional Data Cube**. The cardinality (unique combinations) explodes exponentially. The HashAggregate will immediately exhaust `work_mem` and spill to disk, bringing the query to a grinding halt.

### Row-Oriented vs Column-Oriented Storage

Standard SQL databases (PostgreSQL, MySQL) use **Row-Oriented** storage. To calculate the `COUNT(DISTINCT user_id)` for a funnel, the database must load the entire 8KB disk page from disk, even though you only need the `user_id` and `event_type` columns.

This is why modern data teams export this data to **Column-Oriented** OLAP Data Warehouses (like Snowflake, BigQuery, or ClickHouse). In a columnar database, the `event_type` column is stored entirely by itself in contiguous disk blocks. The database can scan billions of event types per second without ever loading the unrelated JSON payloads or timestamps into RAM.

**Architectural Rule**: While writing complex cohort SQL is a necessary skill, never run these queries against the primary read-replica of a production application. At scale, this level of aggregation strictly belongs in a columnar Data Warehouse.

## Cohort Analysis

A cohort is a group of users who share a common characteristic, typically their first activity date. Cohort analysis tracks what those users do over time.

### Monthly Cohort Retention

To build a retention grid, the query must first determine every user's cohort (their "month zero") and then join that back to their entire activity history. The `DATE_PART` math calculates the exact number of months elapsed between the cohort month and any subsequent order. Finally, conditional aggregation (`COUNT(DISTINCT CASE WHEN ...)`) pivots the rows into a horizontal format, counting how many unique users from the cohort returned in month 1, month 2, etc.

```sql
WITH cohorts AS (
  -- Each user's first purchase month = their cohort
  SELECT
    customer_id,
    DATE_TRUNC('month', MIN(created_at))::DATE AS cohort_month
  FROM orders
  GROUP BY customer_id
),
activity AS (
  -- All purchases with cohort info and relative month offset
  SELECT
    o.customer_id,
    c.cohort_month,
    DATE_TRUNC('month', o.created_at)::DATE AS order_month,
    (
      (DATE_PART('year', o.created_at) - DATE_PART('year', c.cohort_month)) * 12
      + DATE_PART('month', o.created_at) - DATE_PART('month', c.cohort_month)
    )::INT AS months_since_join
  FROM orders o
  JOIN cohorts c ON o.customer_id = c.customer_id
)
SELECT
  cohort_month,
  -- Month 0 = cohort size
  COUNT(DISTINCT CASE WHEN months_since_join = 0 THEN customer_id END) AS m0,
  COUNT(DISTINCT CASE WHEN months_since_join = 1 THEN customer_id END) AS m1,
  COUNT(DISTINCT CASE WHEN months_since_join = 2 THEN customer_id END) AS m2,
  COUNT(DISTINCT CASE WHEN months_since_join = 3 THEN customer_id END) AS m3,
  COUNT(DISTINCT CASE WHEN months_since_join = 6 THEN customer_id END) AS m6,
  COUNT(DISTINCT CASE WHEN months_since_join = 12 THEN customer_id END) AS m12
FROM activity
GROUP BY cohort_month
ORDER BY cohort_month;
```

### Cohort Retention as Percentage

Raw counts are useful, but stakeholders need percentages. The retention rate for each month is simply the count of returners divided by the cohort size (month 0 count). `NULLIF(m0, 0)` prevents division-by-zero errors for cohorts that somehow have zero members. The resulting table — cohort rows with M1%, M3%, M6%, M12% columns — is the standard "retention grid" used in product analytics to evaluate product-market fit and churn trends.

```sql
WITH cohort_data AS (
  -- ... same as above ...
  SELECT cohort_month,
    COUNT(DISTINCT CASE WHEN months_since_join = 0  THEN customer_id END) AS m0,
    COUNT(DISTINCT CASE WHEN months_since_join = 1  THEN customer_id END) AS m1,
    COUNT(DISTINCT CASE WHEN months_since_join = 3  THEN customer_id END) AS m3,
    COUNT(DISTINCT CASE WHEN months_since_join = 6  THEN customer_id END) AS m6,
    COUNT(DISTINCT CASE WHEN months_since_join = 12 THEN customer_id END) AS m12
  FROM activity
  GROUP BY cohort_month
)
SELECT
  cohort_month,
  m0 AS cohort_size,
  ROUND(m1  * 100.0 / NULLIF(m0, 0), 1) AS m1_retention_pct,
  ROUND(m3  * 100.0 / NULLIF(m0, 0), 1) AS m3_retention_pct,
  ROUND(m6  * 100.0 / NULLIF(m0, 0), 1) AS m6_retention_pct,
  ROUND(m12 * 100.0 / NULLIF(m0, 0), 1) AS m12_retention_pct
FROM cohort_data
ORDER BY cohort_month;
```

## Funnel Analysis

A funnel tracks how many users progress through a sequence of steps (e.g., visited → signed up → made first purchase).

```sql
-- E-commerce funnel: 5 steps
WITH funnel AS (
  SELECT
    COUNT(DISTINCT user_id) FILTER (WHERE event_type = 'page_view')     AS step1_viewed,
    COUNT(DISTINCT user_id) FILTER (WHERE event_type = 'add_to_cart')   AS step2_carted,
    COUNT(DISTINCT user_id) FILTER (WHERE event_type = 'checkout_start') AS step3_checkout,
    COUNT(DISTINCT user_id) FILTER (WHERE event_type = 'payment_info')   AS step4_payment,
    COUNT(DISTINCT user_id) FILTER (WHERE event_type = 'purchase')       AS step5_purchased
  FROM user_events
  WHERE created_at >= NOW() - INTERVAL '30 days'
)
SELECT
  'Step 1: Viewed'     AS step, step1_viewed AS users, 100.0 AS conversion_pct FROM funnel
UNION ALL
SELECT 'Step 2: Added to Cart', step2_carted,
  ROUND(step2_carted * 100.0 / NULLIF(step1_viewed, 0), 1) FROM funnel
UNION ALL
SELECT 'Step 3: Started Checkout', step3_checkout,
  ROUND(step3_checkout * 100.0 / NULLIF(step1_viewed, 0), 1) FROM funnel
UNION ALL
SELECT 'Step 4: Payment Info', step4_payment,
  ROUND(step4_payment * 100.0 / NULLIF(step1_viewed, 0), 1) FROM funnel
UNION ALL
SELECT 'Step 5: Purchased', step5_purchased,
  ROUND(step5_purchased * 100.0 / NULLIF(step1_viewed, 0), 1) FROM funnel;
```

## Ordered Funnel (User Must Complete Steps in Order)

A simple funnel counts users who performed each event type, regardless of order. But a real conversion funnel requires that users complete steps *in sequence*: you cannot count someone as having started checkout if they never added to cart. The ordered funnel approach captures the **first timestamp** of each event per user using `MIN(CASE WHEN event_type = ... THEN created_at END)`. Then it uses cumulative timestamp comparisons (`t2 > t1 AND t3 > t2`) to enforce ordering. A user who did `t3` before `t1` is correctly excluded.

```sql
WITH step_times AS (
  SELECT
    user_id,
    MIN(CASE WHEN event_type = 'signup_start'    THEN created_at END) AS t1,
    MIN(CASE WHEN event_type = 'email_verified'  THEN created_at END) AS t2,
    MIN(CASE WHEN event_type = 'profile_created' THEN created_at END) AS t3,
    MIN(CASE WHEN event_type = 'first_purchase'  THEN created_at END) AS t4
  FROM user_events
  GROUP BY user_id
)
SELECT
  COUNT(*)                                                AS step1_started,
  COUNT(*) FILTER (WHERE t2 > t1)                        AS step2_verified,
  COUNT(*) FILTER (WHERE t2 > t1 AND t3 > t2)            AS step3_profile,
  COUNT(*) FILTER (WHERE t2 > t1 AND t3 > t2 AND t4 > t3) AS step4_purchased
FROM step_times
WHERE t1 IS NOT NULL;
```

## Retention Analysis

### Day-N Retention

Day-N retention asks a precise question: of all the users who signed up on a given day, what percentage came back exactly N days later? It's different from "at any point after day N" — it measures activity on that specific day. The technique uses a `LEFT JOIN` between signups and activity, and `CASE WHEN r.active_date = s.signup_date + N` selects only users who were active on that exact day offset. `COUNT(DISTINCT user_id)` inside the CASE ensures a user is only counted once per day even if they triggered multiple events.

```sql
-- What % of users who signed up on day 0 came back on day N?
WITH signups AS (
  SELECT user_id, DATE(created_at) AS signup_date FROM users
),
returns AS (
  SELECT DISTINCT user_id, DATE(event_time) AS active_date FROM user_activity
)
SELECT
  s.signup_date,
  COUNT(DISTINCT s.user_id) AS cohort_size,
  COUNT(DISTINCT CASE WHEN r.active_date = s.signup_date + 1  THEN s.user_id END) AS day1,
  COUNT(DISTINCT CASE WHEN r.active_date = s.signup_date + 7  THEN s.user_id END) AS day7,
  COUNT(DISTINCT CASE WHEN r.active_date = s.signup_date + 14 THEN s.user_id END) AS day14,
  COUNT(DISTINCT CASE WHEN r.active_date = s.signup_date + 30 THEN s.user_id END) AS day30
FROM signups s
LEFT JOIN returns r ON s.user_id = r.user_id
GROUP BY s.signup_date
ORDER BY s.signup_date;
```

## Active User Metrics (DAU, WAU, MAU)

DAU (Daily Active Users), WAU (Weekly Active Users), and MAU (Monthly Active Users) are the fundamental engagement metrics for any product. The challenge is that WAU and MAU require a **rolling window** — they should include distinct users from the last 7 or 30 days, not just the current day. This is achieved using `RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW`, which instructs the window function to include all rows where the `ORDER BY` value falls within 6 days behind the current row, effectively creating a 7-day rolling distinct user count.

```sql
-- Daily, Weekly, Monthly Active Users
SELECT
  DATE(event_time) AS date,
  COUNT(DISTINCT user_id) AS dau,
  COUNT(DISTINCT user_id) OVER (
    ORDER BY DATE(event_time)
    RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW
  ) AS wau_7d,
  COUNT(DISTINCT user_id) OVER (
    ORDER BY DATE(event_time)
    RANGE BETWEEN INTERVAL '29 days' PRECEDING AND CURRENT ROW
  ) AS mau_30d
FROM user_activity
GROUP BY DATE(event_time)
ORDER BY date;
```

## LTV - Lifetime Value

Customer Lifetime Value (LTV) is one of the most important metrics in e-commerce and SaaS. At its core, it is the total revenue a customer has generated since acquisition. The `monthly_ltv` normalization divides total revenue by the number of months since first purchase, making customers with different tenure lengths comparable. `HAVING COUNT(*) >= 2` filters out one-time buyers since their LTV trajectory is not yet established. This query is typically the input to customer segmentation, marketing spend decisions, and churn risk modeling.

```sql
-- Customer LTV: revenue per customer over their lifetime
SELECT
  customer_id,
  COUNT(*)                                               AS total_orders,
  SUM(total)                                             AS ltv,
  ROUND(AVG(total), 2)                                   AS avg_order_value,
  MAX(created_at) - MIN(created_at)                      AS customer_lifetime,
  ROUND(SUM(total) / NULLIF(
    EXTRACT(DAY FROM MAX(created_at) - MIN(created_at)) / 30.0,
    0
  ), 2)                                                  AS monthly_ltv
FROM orders
WHERE status = 'completed'
GROUP BY customer_id
HAVING COUNT(*) >= 2
ORDER BY ltv DESC;
```

## Summary

- Cohort analysis: group users by first activity date, track their behavior over time
- Use `CASE WHEN months_since_join = N THEN customer_id END` inside COUNT(DISTINCT ...) for cohort columns
- Funnel analysis: count users at each step using FILTER (WHERE event_type = '...')
- Ordered funnel: track event timestamps and check t2 > t1 > t0 etc.
- DAU/WAU/MAU: use window function with RANGE BETWEEN for rolling distinct user counts
- LTV: SUM(order total) per customer, normalize by lifetime duration for monthly LTV
