## The Architecture of SQL Dialects: Parsers and ASTs

The fact that SQL is "standardized" (ANSI SQL) but structurally fragmented across databases (PostgreSQL, MySQL, SQL Server) is a direct result of how database engines process queries.

### The Parser vs The Execution Engine

When you submit a query, it hits the database's **Parser**. The Parser's only job is to validate the syntax against the ANSI standard and build a logical **Abstract Syntax Tree (AST)**. 

However, the AST must be handed off to the **Execution Engine** to actually read the disk. 
Every database company built their physical execution engine completely differently. PostgreSQL uses MVCC and TOAST; SQL Server relies heavily on Clustered Indexes; Oracle uses Redo Logs. 
Because the underlying physical architecture is radically different, each vendor had to invent proprietary SQL keywords (Dialect Extensions) to expose their specific hardware optimizations to the developer. For example, PostgreSQL created the `JSONB` keyword to expose its GIN indexing architecture, something the ANSI standard could not anticipate.

### The ORM Dialect Adapter

This architectural fragmentation is why Object-Relational Mappers (ORMs like Prisma, Hibernate, or SQLAlchemy) require you to configure a specific database driver. 
The ORM acts as an intermediate compiler. You write generic application code (`user.orders.count()`), and the ORM builds an internal AST. It then passes this AST through a **Dialect Adapter**, which translates the generic logic into the highly specific, physically optimized SQL syntax required by your specific target engine.

## Why Dialects Differ

SQL has an ANSI standard, but every database adds extensions and diverges in edge cases. Understanding these differences is essential when switching between systems or writing portable SQL.

## String Concatenation

```sql
-- PostgreSQL, SQLite, Standard SQL
SELECT first_name || ' ' || last_name AS full_name FROM users;

-- MySQL, SQL Server
SELECT CONCAT(first_name, ' ', last_name) AS full_name FROM users;

-- All databases support CONCAT() - safest for portability
```

## Auto-Increment / Identity

Defining a surrogate primary key with an auto-incrementing integer is standard practice. PostgreSQL 10+ introduced the SQL-standard `GENERATED ALWAYS AS IDENTITY`, which is safer than the legacy `SERIAL` types because it prevents manual inserts from accidentally advancing the sequence (unless explicitly overridden with `OVERRIDING SYSTEM VALUE`). MySQL relies on the non-standard `AUTO_INCREMENT` modifier. SQL Server uses `IDENTITY(1,1)` where the arguments represent the seed and the increment step.

```sql
-- PostgreSQL
id BIGSERIAL PRIMARY KEY
id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY

-- MySQL
id BIGINT AUTO_INCREMENT PRIMARY KEY

-- SQL Server
id BIGINT IDENTITY(1,1) PRIMARY KEY

-- SQLite
id INTEGER PRIMARY KEY AUTOINCREMENT
```

## Getting Last Inserted ID

Retrieving the auto-generated ID of a newly inserted row is a very common pattern — you need the new ID to insert related rows in child tables. PostgreSQL's `RETURNING` clause is the most powerful and composable solution: it can return any column (including multiple) and works inside CTEs (`WITH ins AS (INSERT ... RETURNING id) INSERT INTO ...`). MySQL's `LAST_INSERT_ID()` and SQL Server's `SCOPE_IDENTITY()` are session-scoped functions that are safe in concurrent environments because they return the ID generated by the **current session's** last insert, not the globally last inserted ID.

```sql
-- PostgreSQL: use RETURNING
INSERT INTO users (name) VALUES ('Alice') RETURNING id;

-- MySQL
INSERT INTO users (name) VALUES ('Alice');
SELECT LAST_INSERT_ID();

-- SQL Server
INSERT INTO users (name) VALUES ('Alice');
SELECT SCOPE_IDENTITY();

-- SQLite
SELECT last_insert_rowid();
```

## LIMIT / TOP

Limiting result sets is fundamental for pagination and performance. PostgreSQL, MySQL, and SQLite use the `LIMIT n OFFSET m` syntax, which is portable and intuitive. SQL Server uses `TOP n` for simple limits and the ANSI-compliant `OFFSET m ROWS FETCH NEXT n ROWS ONLY` for pagination (requires `ORDER BY`). Oracle historically used `ROWNUM` (which filters *before* sorting, making it error-prone) and added `FETCH FIRST n ROWS ONLY` in version 12c. For production pagination on large tables, cursor-based pagination (using `WHERE id > last_seen_id`) is always preferred over `OFFSET` because `OFFSET n` still forces the database to read and discard the first `n` rows.

```sql
-- PostgreSQL, MySQL, SQLite
SELECT * FROM users ORDER BY id LIMIT 10;
SELECT * FROM users ORDER BY id LIMIT 10 OFFSET 20;

-- SQL Server / MS Access
SELECT TOP 10 * FROM users ORDER BY id;
SELECT TOP 10 PERCENT * FROM users ORDER BY id;
-- Offset in SQL Server (2012+)
SELECT * FROM users ORDER BY id OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY;

-- Oracle
SELECT * FROM users WHERE ROWNUM <= 10;
-- Oracle 12c+
SELECT * FROM users ORDER BY id FETCH FIRST 10 ROWS ONLY;
```

## Date Functions

Date manipulation is one of the most fragmented areas across SQL dialects. The ANSI-standard `EXTRACT()` function and `CURRENT_TIMESTAMP` are widely supported, but date truncation and interval arithmetic vary significantly. PostgreSQL's `DATE_TRUNC()` and natural interval arithmetic (`NOW() + INTERVAL '7 days'`) are expressive and intuitive. MySQL uses `DATE_ADD()` and `DATE_FORMAT()`. SQL Server relies on `DATEADD()`, `DATEDIFF()`, and `GETDATE()`. When writing cross-database analytics code, always prefer `EXTRACT()` over `YEAR()` and `CURRENT_TIMESTAMP` over `NOW()` or `GETDATE()` for maximum portability.

```sql
-- Current timestamp
SELECT NOW();              -- MySQL, PostgreSQL
SELECT CURRENT_TIMESTAMP;  -- All databases (standard)
SELECT GETDATE();          -- SQL Server
SELECT SYSDATE FROM DUAL;  -- Oracle

-- Extract year
SELECT EXTRACT(YEAR FROM created_at);   -- PostgreSQL, MySQL, standard
SELECT YEAR(created_at);                -- MySQL, SQL Server
SELECT strftime('%Y', created_at);      -- SQLite

-- Date truncation
SELECT DATE_TRUNC('month', NOW());            -- PostgreSQL
SELECT DATE_FORMAT(NOW(), '%Y-%m-01');        -- MySQL
SELECT DATEADD(month, DATEDIFF(month, 0, GETDATE()), 0); -- SQL Server

-- Add interval
SELECT NOW() + INTERVAL '7 days';            -- PostgreSQL
SELECT DATE_ADD(NOW(), INTERVAL 7 DAY);      -- MySQL
SELECT DATEADD(day, 7, GETDATE());           -- SQL Server
```

## String Functions

String manipulation functions are superficially similar across databases but have meaningful edge case differences. `SUBSTRING(str, start, length)` is the ANSI standard and works everywhere (PostgreSQL also accepts `SUBSTR`). `CHARINDEX()` (SQL Server) and `INSTR()` (MySQL, Oracle) are non-standard replacements for ANSI `POSITION()`. The most important difference is **case sensitivity**: PostgreSQL's `LIKE` is case-sensitive by default, requiring `ILIKE` for case-insensitive matching. MySQL's `LIKE` is case-insensitive by default (governed by the column's collation). SQL Server's behavior depends entirely on the collation of the column or database.

```sql
-- Substring
SELECT SUBSTRING(name, 1, 3) FROM users;     -- All
SELECT SUBSTR(name, 1, 3) FROM users;        -- PostgreSQL, SQLite, Oracle
SELECT LEFT(name, 3) FROM users;             -- MySQL, SQL Server, PostgreSQL

-- String position
SELECT POSITION('o' IN name) FROM users;     -- PostgreSQL, MySQL (standard)
SELECT CHARINDEX('o', name) FROM users;      -- SQL Server
SELECT INSTR(name, 'o') FROM users;          -- MySQL, Oracle

-- Case-insensitive like
SELECT * FROM users WHERE name ILIKE '%alice%';   -- PostgreSQL
SELECT * FROM users WHERE name LIKE '%alice%';    -- MySQL (case-insensitive by default)
SELECT * FROM users WHERE name LIKE '%alice%' COLLATE SQL_Latin1_General_CP1_CI_AS; -- SQL Server
```

## Conditional Expressions

`CASE WHEN` is the universal conditional expression supported by every SQL database — always use it in shared or portable code. MySQL's `IF(condition, true_val, false_val)` is a convenient shorthand but non-standard and unavailable in PostgreSQL or SQL Server. SQL Server's `IIF()` is identical in purpose to MySQL's `IF()` but uses a different name. `COALESCE(a, b, c)` is the ANSI-standard way to return the first non-NULL value in a list, making it the preferred choice over Oracle's `NVL()` or SQL Server's `ISNULL()`, both of which only accept two arguments.

```sql
-- CASE WHEN: all databases
SELECT CASE WHEN age >= 18 THEN 'Adult' ELSE 'Minor' END FROM users;

-- IF: MySQL only
SELECT IF(age >= 18, 'Adult', 'Minor') AS category FROM users;

-- IIF: SQL Server
SELECT IIF(age >= 18, 'Adult', 'Minor') AS category FROM users;

-- COALESCE: all databases (standard SQL)
SELECT COALESCE(phone, 'N/A') FROM users;

-- NVL: Oracle
SELECT NVL(phone, 'N/A') FROM users;

-- ISNULL: SQL Server
SELECT ISNULL(phone, 'N/A') FROM users;
```

## Upsert (Insert or Update)

An upsert atomically inserts a row if it doesn't exist, or updates it if it does — critical for idempotent data pipelines, synchronization jobs, and event processing. PostgreSQL's `ON CONFLICT DO UPDATE` is the cleanest implementation: `EXCLUDED` is a virtual table referring to the row that *would have been inserted*, making it easy to reference the new values in the `SET` clause. MySQL's `ON DUPLICATE KEY UPDATE` triggers on any unique constraint violation. SQL Server's `MERGE` statement is the most verbose but also the most flexible, supporting separate `WHEN MATCHED`, `WHEN NOT MATCHED BY TARGET`, and `WHEN NOT MATCHED BY SOURCE` clauses.

```sql
-- PostgreSQL
INSERT INTO users (email, name) VALUES ('a@b.com', 'Alice')
ON CONFLICT (email) DO UPDATE SET name = EXCLUDED.name;

-- MySQL
INSERT INTO users (email, name) VALUES ('a@b.com', 'Alice')
ON DUPLICATE KEY UPDATE name = VALUES(name);

-- SQL Server (MERGE)
MERGE INTO users AS target
USING (VALUES ('a@b.com', 'Alice')) AS source (email, name)
ON target.email = source.email
WHEN MATCHED THEN UPDATE SET name = source.name
WHEN NOT MATCHED THEN INSERT (email, name) VALUES (source.email, source.name);
```

## JSON Support

JSON support is one of the starkest dialect differences. PostgreSQL's JSONB is the gold standard: it stores data in a binary parsed format, supports GIN indexing for fast containment queries, and provides rich operators (`->`, `->>`). MySQL 5.7+ stores JSON in a binary format and uses `JSON_EXTRACT(col, '$.path')` path expressions. SQL Server does not have a native JSON column type — JSON is stored as `NVARCHAR` text, and SQL Server provides functions like `JSON_VALUE()` (extracts a scalar) and `JSON_QUERY()` (extracts a sub-object) to query it without parsing overhead at the application level.

```sql
-- PostgreSQL: JSONB (most powerful)
SELECT settings ->> 'theme' FROM users;
SELECT * FROM users WHERE settings @> '{"theme": "dark"}';

-- MySQL 5.7+
SELECT JSON_EXTRACT(settings, '$.theme') FROM users;
SELECT * FROM users WHERE JSON_CONTAINS(settings, '"dark"', '$.theme');

-- SQL Server (since 2016 - no native JSON type, stored as NVARCHAR)
SELECT JSON_VALUE(settings, '$.theme') FROM users;
```

## CTEs and Recursive CTEs

Common Table Expressions are now supported by all major databases, but the `RECURSIVE` keyword requirement differs. PostgreSQL and SQLite require the explicit `WITH RECURSIVE` keyword to signal that the CTE is recursive. MySQL 8+ supports recursion but does not require the `RECURSIVE` keyword — MySQL detects recursion automatically. SQL Server uses `WITH` (without `RECURSIVE`) and enables recursion via a `@@MAXRECURSION` option (default: 100 levels; use 0 for unlimited). Oracle requires column aliases to be declared in the CTE header rather than inside the CTE body.

```sql
-- All major databases support standard CTEs:
WITH cte AS (SELECT ...)
SELECT * FROM cte;

-- Recursive CTEs (RECURSIVE keyword varies):
-- PostgreSQL, SQLite:
WITH RECURSIVE cte AS (...)

-- SQL Server, MySQL 8+:
WITH cte AS (...)  -- MySQL doesn't need RECURSIVE keyword, uses it automatically

-- Oracle:
WITH cte (col1, col2) AS (...)  -- must list columns
```

## Portability Tips

1. **Use standard SQL** where possible: CASE, COALESCE, CAST, BETWEEN, standard JOINs
2. **Avoid database-specific functions** in shared code: use SUBSTRING not LEFT/RIGHT, use EXTRACT not YEAR()
3. **Test on both databases** when migrating - even "the same" functions can have edge case differences
4. **Document your dialect** - note which database a script targets at the top of the file
5. **Use an ORM** when portability matters - Prisma, SQLAlchemy handle most dialect differences

## Quick Cheat Sheet

| Task | PostgreSQL | MySQL | SQL Server |
|------|-----------|-------|------------|
| Auto-increment | BIGSERIAL | AUTO_INCREMENT | IDENTITY(1,1) |
| Last insert ID | RETURNING id | LAST_INSERT_ID() | SCOPE_IDENTITY() |
| Limit rows | LIMIT n | LIMIT n | TOP n |
| Add days | + INTERVAL '7 days' | DATE_ADD(d, INTERVAL 7 DAY) | DATEADD(day,7,d) |
| Current time | NOW() | NOW() | GETDATE() |
| Concat | string1 \|\| string2 | CONCAT(s1, s2) | s1 + s2 |
| Case-insensitive LIKE | ILIKE | LIKE (default) | LIKE (with collation) |
| Upsert | ON CONFLICT DO UPDATE | ON DUPLICATE KEY UPDATE | MERGE |
| JSON | JSONB (->, ->>) | JSON_EXTRACT | JSON_VALUE |

## Summary

- All databases support core SQL: SELECT, WHERE, GROUP BY, ORDER BY, JOINs, CASE, COALESCE
- Key differences: auto-increment syntax, LIMIT vs TOP, date functions, upsert syntax, JSON support
- PostgreSQL has the most powerful feature set (JSONB, LATERAL, FILTER, recursive CTEs)
- MySQL is case-insensitive by default for LIKE; PostgreSQL is case-sensitive (use ILIKE)
- Window functions work in all modern databases (MySQL 8+, SQL Server 2012+, SQLite 3.25+)
- When writing portable SQL: prefer standard functions, avoid database-specific shortcuts
