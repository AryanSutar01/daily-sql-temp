## Numeric Functions: Hardware FPU vs. Software Arithmetic

When you run numeric functions in SQL, you must understand *where* the math is actually being computed, because it dictates both speed and accuracy.

### Hardware Math (FLOAT / DOUBLE PRECISION)

If you run `ROUND()`, `POWER()`, or `SQRT()` on a `FLOAT` or `DOUBLE PRECISION` column, the database passes the raw 64-bit IEEE 754 binary floating-point value directly to the server's CPU **Floating Point Unit (FPU)**. 
- **Speed**: Blisteringly fast (hardware-level parallel SIMD instructions).
- **Accuracy Hazard**: Susceptible to IEEE 754 precision loss. `0.1 + 0.2` evaluated at the hardware level will yield `0.30000000000000004`. If you use `FLOAT` for financial data, your numeric functions will compound these rounding errors, destroying financial integrity.

### Software Math (NUMERIC / DECIMAL)

If you run numeric functions on a `DECIMAL(10,2)` column, the server's FPU is completely bypassed. `DECIMAL` types are processed using a software-level **Arbitrary Precision Arithmetic** library built into the database engine (similar to Java's `BigDecimal`).
- **Speed**: Significantly slower (up to 10x slower than FLOAT for complex operations like `POWER()` or logarithms), because the database must compute the math byte-by-byte in software to guarantee exactness.
- **Accuracy Guarantee**: Mathematically perfect for base-10 operations. `0.1 + 0.2` always equals `0.3`.

### The Integer Division Trap

In languages like Python 3, `17 / 5` yields `3.4`. In relational databases (like PostgreSQL and SQL Server), if both operands are integers, the database strictly applies **Integer Division**, truncating the decimal and returning `3`.

```sql
-- The classic interview trap:
SELECT count(shipped) / count(total) AS completion_rate FROM orders;
-- If 800 shipped and 1000 total: 800 / 1000 = 0 (Not 0.8!)

-- The fix: Force the hardware to upcast one integer to a FLOAT/NUMERIC
SELECT count(shipped)::FLOAT / count(total) FROM orders;
-- Or simply multiply by 1.0
SELECT count(shipped) * 1.0 / count(total) FROM orders;
```

## Common Numeric Functions

Numeric functions in SQL operate on scalar values and return scalar results. A critical quirk to internalize: PostgreSQL's `ROUND()` uses **banker's rounding** (round-half-to-even), so `ROUND(2.5)` returns 2 (rounds to even), while `ROUND(3.5)` returns 4. This prevents systematic upward bias in large datasets. Standard rounding is `ROUND(x + 0.0000001)` to force traditional half-up behavior if needed. The distinction between `TRUNC` and `FLOOR` matters for negative numbers: `TRUNC(-3.9)` returns `-3` (towards zero), while `FLOOR(-3.9)` returns `-4` (towards negative infinity).

```sql
-- Absolute value
SELECT ABS(-42);          -- 42
SELECT ABS(-3.14);        -- 3.14

-- Rounding
SELECT ROUND(3.14159, 2); -- 3.14
SELECT ROUND(3.14159, 0); -- 3.0
SELECT ROUND(3.5);        -- 4
SELECT ROUND(2.5);        -- 2 (banker's rounding in PostgreSQL - rounds to even)
SELECT ROUND(-3.5);       -- -4

-- Ceiling and Floor
SELECT CEIL(3.1);         -- 4  (round up to nearest integer)
SELECT CEILING(3.1);      -- 4  (synonym)
SELECT FLOOR(3.9);        -- 3  (round down to nearest integer)
SELECT FLOOR(-3.1);       -- -4 (towards negative infinity)

-- Truncate (cut off decimal - no rounding)
SELECT TRUNC(3.99);       -- 3
SELECT TRUNC(-3.99);      -- -3  (towards zero, unlike FLOOR)
SELECT TRUNC(3.456, 2);   -- 3.45  (PostgreSQL: truncate to 2 decimal places)
```

## Modulo - Remainder

`MOD(a, b)` or `a % b` returns the remainder after integer division. Its primary production use cases are determining parity (even/odd), consistent hash-based sharding, and deterministic sampling. When used for sharding (`user_id % N = shard_id`), it distributes rows deterministically and uniformly across N shards — the same user always routes to the same shard. For sampling, `WHERE id % 100 < 1` gives a deterministic 1% sample that doesn't change between runs, unlike `ORDER BY RANDOM() LIMIT N` which is non-deterministic and requires a full sort.

```sql
SELECT MOD(10, 3);        -- 1  (10 ÷ 3 = 3 remainder 1)
SELECT 10 % 3;            -- 1  (operator syntax)
SELECT MOD(15, 5);        -- 0  (evenly divisible)

-- Practical uses:
-- Check if a number is even or odd
SELECT id, CASE WHEN id % 2 = 0 THEN 'Even' ELSE 'Odd' END FROM orders;

-- Distribute records into N groups (sharding)
SELECT id, id % 4 AS shard_id FROM users;  -- groups 0, 1, 2, 3

-- Every Nth row
SELECT * FROM orders WHERE id % 10 = 0;  -- every 10th order
```

## Power and Roots

```sql
SELECT POWER(2, 10);      -- 1024
SELECT POWER(2.5, 3);     -- 15.625
SELECT SQRT(144);         -- 12.0
SELECT SQRT(2);           -- 1.4142...
SELECT CBRT(27);          -- 3.0  (cube root, PostgreSQL)

-- Compound interest: A = P(1 + r)^n
SELECT
  principal * POWER(1 + rate, years) AS future_value
FROM investments;
```

## Logarithms and Exponentials

`LN(x)` computes the natural logarithm (base e), used in statistics and compound growth models. `LOG(x)` in PostgreSQL is log base 10 (not base 2). For log base N, use `LOG(base, value)` in PostgreSQL. In analytics, log scales are used to normalize skewed distributions — `LOG(revenue + 1)` compresses the wide range of revenue values, making visualizations and ML features more tractable. The `+1` prevents `LOG(0)` which is undefined.

```sql
SELECT EXP(1);            -- 2.718... (e^1)
SELECT LN(2.718);         -- ~1.0 (natural log)
SELECT LOG(100);          -- 2.0 (log base 10)
SELECT LOG(2, 1024);      -- 10 (log base 2 of 1024, PostgreSQL)
```

## Random Numbers

`RANDOM()` in PostgreSQL returns a double-precision float uniformly distributed in `[0, 1)`. Note that `ORDER BY RANDOM()` for sampling is **extremely slow** on large tables because it assigns a random number to every row, then sorts all of them. For large-scale sampling, use `TABLESAMPLE BERNOULLI(1)` (1% sample) which operates at the storage block level and avoids a full sort. For reproducible random sequences (e.g., A/B test assignment), use `setseed(0.42)` before calling `RANDOM()` to seed the PRNG.

```sql
SELECT RANDOM();                          -- random float between 0 and 1
SELECT FLOOR(RANDOM() * 100) + 1;        -- random integer 1-100
SELECT FLOOR(RANDOM() * (max - min + 1)) + min; -- random between min and max

-- Random sample of 100 rows (approximately)
SELECT * FROM users WHERE RANDOM() < 0.01 LIMIT 100;

-- Shuffle rows randomly
SELECT * FROM products ORDER BY RANDOM() LIMIT 10;
```

## DIV - Integer Division

```sql
SELECT 17 / 5;            -- 3.4 (standard division in PostgreSQL)
SELECT 17 / 5::FLOAT;     -- 3.4
SELECT DIV(17, 5);        -- 3 (integer division, no remainder)
SELECT 17 :: INT / 5;     -- 3 (integer division via casting)
```

## GREATEST and LEAST

`GREATEST` and `LEAST` accept variadic arguments and return the maximum or minimum value across them. A crucial behavioral difference from `MAX`/`MIN`: both `GREATEST` and `LEAST` return `NULL` if **any** argument is `NULL` (in most databases). This differs from aggregate `MAX(col)`, which ignores NULLs. Use `COALESCE` to provide fallback values: `GREATEST(COALESCE(a, 0), COALESCE(b, 0))`. These functions are invaluable for enforcing business rules directly in SQL — capping discounts, enforcing minimum prices, and clamping scores to valid ranges.

```sql
SELECT GREATEST(10, 20, 5, 15);   -- 20
SELECT LEAST(10, 20, 5, 15);      -- 5

-- Enforce a minimum price
SELECT name, GREATEST(price, 0) AS non_negative_price FROM products;

-- Cap a value at a maximum
SELECT name, LEAST(discount, 50) AS capped_discount FROM promotions;

-- Clamp a value between min and max
SELECT GREATEST(0, LEAST(score, 100)) AS clamped_score FROM assessments;
```

## Practical Numeric Examples

```sql
-- Round currency to 2 decimal places
SELECT name, ROUND(price * 1.18, 2) AS price_with_gst FROM products;

-- Percentage calculation (avoid integer division)
SELECT
  category,
  COUNT(*) AS count,
  ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 2) AS percentage
FROM products
GROUP BY category;

-- Safe division (avoid divide by zero)
SELECT
  product_id,
  total_revenue / NULLIF(units_sold, 0) AS revenue_per_unit
FROM product_stats;

-- Bin ages into groups
SELECT
  CASE
    WHEN age < 18              THEN 'Under 18'
    WHEN age BETWEEN 18 AND 24 THEN '18-24'
    WHEN age BETWEEN 25 AND 34 THEN '25-34'
    WHEN age BETWEEN 35 AND 44 THEN '35-44'
    ELSE '45+'
  END AS age_group,
  COUNT(*) AS users
FROM users
GROUP BY 1
ORDER BY 1;
```

## Summary

- `ROUND(x, n)` - round to n decimal places; `CEIL` - up; `FLOOR` - down; `TRUNC` - cut off
- `MOD(a, b)` or `a % b` - remainder after division
- `POWER(base, exp)` - exponentiation; `SQRT` - square root
- `RANDOM()` - random float 0-1, useful for sampling and shuffle
- `GREATEST` / `LEAST` - pick the largest/smallest from a list of values
- Always use `NULLIF(denominator, 0)` to avoid divide-by-zero errors
- Use `100.0` (not `100`) in percentage calculations to avoid integer division truncation
