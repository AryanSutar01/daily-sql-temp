## The Transaction Manager and Connection Pooling

A transaction is not just a logical grouping of SQL statements; it is a physical state tracked by the database's **Transaction Manager**. Every active transaction consumes server memory, locks, and an active connection slot.

### The "Idle in Transaction" Danger

Modern web applications use Connection Pooling (like PgBouncer). When your application sends `BEGIN`, the database binds an active connection to your transaction. 
If your application code does something slow *inside* the transaction block (like making an HTTP request to Stripe, or waiting for user input), the transaction becomes **"Idle in transaction"**.
1. The database connection is held hostage and cannot be returned to the pool.
2. If this happens concurrently, the pool is exhausted, and the entire application crashes because new requests cannot get a database connection.
3. Long-running transactions prevent the database from cleaning up old row versions (MVCC vacuuming), causing massive table bloat.

**Architectural Rule**: Transactions must be entirely database-bound and execute as fast as physically possible. Never wrap network calls, file I/O, or complex application-side computations inside a `BEGIN / COMMIT` block.

## What is a Transaction?

A transaction is a sequence of SQL statements that execute as a single unit. Either all succeed (COMMIT) or none have any effect (ROLLBACK).

```sql
BEGIN;        -- start transaction
  statement1;
  statement2;
  statement3;
COMMIT;       -- make all changes permanent

-- OR:
ROLLBACK;     -- undo all changes since BEGIN
```

## COMMIT

`COMMIT` makes all changes in the current transaction permanent and visible to other sessions.

```sql
BEGIN;
  INSERT INTO orders (customer_id, total) VALUES (1, 5000);
  UPDATE products SET stock = stock - 1 WHERE id = 42;
COMMIT;
-- Both changes are now permanent and visible to everyone
```

## ROLLBACK

`ROLLBACK` undoes all changes made since the `BEGIN`, returning the database to its state before the transaction started.

```sql
BEGIN;
  DELETE FROM users WHERE id = 1;
  -- Wait... wrong user! Let me undo this.
ROLLBACK;
-- User still exists - DELETE was undone
```

## START TRANSACTION (Standard SQL)

`BEGIN`, `BEGIN WORK`, and `START TRANSACTION` are all equivalent in PostgreSQL. They mark the start of a transaction boundary. Once a transaction is open, all subsequent DML statements (`INSERT`, `UPDATE`, `DELETE`) are part of the same atomic unit. In PostgreSQL, DDL (`CREATE TABLE`, `ALTER TABLE`) can also be wrapped in a transaction and rolled back — this is a unique and powerful feature not available in MySQL or SQL Server, where DDL auto-commits immediately.

```sql
-- These are all equivalent:
BEGIN;
BEGIN WORK;
START TRANSACTION;
```

## SAVEPOINT - Partial Rollback

`SAVEPOINT` creates a named checkpoint within a transaction. You can roll back to it without undoing the entire transaction.

```sql
BEGIN;

  INSERT INTO orders (customer_id, total) VALUES (1, 5000);
  SAVEPOINT after_order;   -- checkpoint

  INSERT INTO order_items (order_id, product_id, qty) VALUES (999, 5, 1);
  -- Oops: order_id 999 doesn't exist - FK violation

  ROLLBACK TO after_order;  -- undo only back to the savepoint

  INSERT INTO order_items (order_id, product_id, qty) VALUES (LASTVAL(), 5, 1);

COMMIT;  -- commits the order (good) and the corrected item insert
```

## Autocommit Mode

In most databases, every SQL statement is automatically wrapped in its own transaction (autocommit = ON):

```sql
-- In autocommit mode, this is immediately committed:
UPDATE users SET name = 'Bob' WHERE id = 1;
-- Equivalent to:
BEGIN; UPDATE users SET name = 'Bob' WHERE id = 1; COMMIT;
```

To group statements, explicitly use `BEGIN` / `COMMIT`.

## Real-World: Order Placement

Order placement is the canonical transaction example because it requires multiple tables to remain perfectly consistent. If the payment insert succeeds but the stock decrement fails, you would have a paid order with no inventory reduction — a real financial discrepancy. Wrapping all steps in a single transaction guarantees that either all succeed (the happy path) or all are rolled back (the failure path). The database's WAL ensures this guarantee survives even a server crash between steps.

```sql
-- Complete order placement as one atomic operation
BEGIN;

  -- 1. Create the order
  INSERT INTO orders (customer_id, total_amount, status)
  VALUES (101, 2999.00, 'confirmed');

  -- 2. Get the new order ID
  -- (use RETURNING id or LASTVAL() or LAST_INSERT_ID())

  -- 3. Add order items
  INSERT INTO order_items (order_id, product_id, qty, unit_price)
  VALUES (LASTVAL(), 5, 1, 2999.00);

  -- 4. Reduce stock
  UPDATE products SET stock = stock - 1 WHERE id = 5;

  -- 5. Verify stock didn't go negative
  -- (CHECK constraint will catch this automatically)

  -- 6. Record the payment
  INSERT INTO payments (order_id, amount, status)
  VALUES (LASTVAL(), 2999.00, 'completed');

COMMIT;
-- If ANY step fails, ROLLBACK undoes everything - no partial orders
```

## Error Handling in Transactions

### PostgreSQL PL/pgSQL

In PL/pgSQL stored procedures, transaction control requires the `EXCEPTION ... WHEN OTHERS THEN ROLLBACK` pattern. This is analogous to a try/catch block in application code. A critical architectural detail: in PostgreSQL, a runtime error within a transaction automatically puts the transaction into an **aborted state** — you cannot execute any more SQL until you issue a `ROLLBACK`. Any attempt to run another query while in this aborted state will receive the error "ERROR: current transaction is aborted, commands ignored until end of transaction block".

```sql
DO $$
BEGIN
  UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
  UPDATE accounts SET balance = balance + 1000 WHERE id = 2;
  COMMIT;
EXCEPTION
  WHEN OTHERS THEN
    ROLLBACK;
    RAISE NOTICE 'Transaction failed: %', SQLERRM;
END;
$$;
```

### Application Code Pattern (Node.js)

The application-layer transaction pattern uses `try/catch/finally` to guarantee the connection is always released back to the pool, even on error. This is critical because a connection pool is a finite resource — a leaked connection (one not returned via `client.release()`) permanently reduces the pool's capacity until the server is restarted. The `ROLLBACK` in the catch block ensures the database transaction is properly aborted rather than left in an "idle in transaction" state, which holds locks indefinitely.

```javascript
const client = await pool.connect();
try {
  await client.query('BEGIN');
  await client.query('UPDATE accounts SET balance = balance - 1000 WHERE id = $1', [1]);
  await client.query('UPDATE accounts SET balance = balance + 1000 WHERE id = $1', [2]);
  await client.query('COMMIT');
} catch (err) {
  await client.query('ROLLBACK');
  throw err;
} finally {
  client.release();
}
```

## Transaction Isolation Levels

How much one transaction can see of another's in-progress work:

```sql
-- Set isolation level for a transaction
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
  SELECT ...
COMMIT;
```

| Level | Dirty Read | Non-Repeatable Read | Phantom Read |
|-------|-----------|---------------------|-------------|
| READ UNCOMMITTED | ✅ Possible | ✅ Possible | ✅ Possible |
| READ COMMITTED | ❌ Prevented | ✅ Possible | ✅ Possible |
| REPEATABLE READ | ❌ Prevented | ❌ Prevented | ✅ Possible |
| SERIALIZABLE | ❌ Prevented | ❌ Prevented | ❌ Prevented |

**PostgreSQL default:** READ COMMITTED
**Most protective:** SERIALIZABLE (but slower due to more locking)

## Locking

Transactions use locks to prevent conflicts:

```sql
-- Lock a row for update (prevents others from modifying it until commit)
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;

-- Lock without waiting (fail immediately if locked)
SELECT * FROM accounts WHERE id = 1 FOR UPDATE NOWAIT;

-- Skip locked rows (useful for job queues)
SELECT * FROM jobs WHERE status = 'pending' LIMIT 1 FOR UPDATE SKIP LOCKED;
```

## Summary

- `BEGIN` starts a transaction; `COMMIT` saves it; `ROLLBACK` undoes it
- `SAVEPOINT` creates a named checkpoint for partial rollbacks
- Autocommit wraps each statement in its own transaction by default
- Isolation levels control how much in-progress transactions can see of each other
- Always use transactions for multi-step operations that must be atomic
- Use `FOR UPDATE` to lock rows you intend to modify - prevents lost updates
