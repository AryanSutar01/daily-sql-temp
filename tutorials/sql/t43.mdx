## The Physical Lock Manager and MVCC Tuple Headers

Concurrency control is the hardest problem in database engineering. It is managed by two parallel systems: the Lock Manager (for writes) and MVCC (for reads).

### The Lock Manager and Wait Queues

When you execute `SELECT ... FOR UPDATE`, the database doesn't just flip a bit. It registers the request in the in-memory **Lock Manager**. 
If Transaction A holds the lock, and Transaction B requests it, Transaction B is placed in a **Wait Queue**. If 1,000 users try to buy the same ticket simultaneously, 1 user gets the lock, and 999 connections are suspended in the Wait Queue, completely exhausting the database connection pool. This is known as **Lock Contention**.

### MVCC Tuple Headers (xmin / xmax)

Instead of using the Lock Manager for reads (which would cause massive contention), PostgreSQL uses **MVCC (Multi-Version Concurrency Control)**. 
Every row on disk has hidden metadata columns in its header, primarily `xmin` (the Transaction ID that created the row) and `xmax` (the Transaction ID that deleted/updated it).

When Transaction 100 runs `SELECT`, it looks at the `xmin`/`xmax` of every row. If a row was created by Transaction 105, Transaction 100 mathematically knows that row is "in the future" and physically ignores it, scanning for an older version of the row instead. This requires zero locks, allowing thousands of concurrent readers to scan the exact same disk pages that writers are actively modifying.

## Why Concurrency Control?

When multiple transactions run simultaneously, they can conflict. Without concurrency control:
- Two users could buy the last item in stock
- A bank transfer could be lost if two transfers happen at the same time
- A report could read inconsistent data mid-transaction

Databases use **locks** and **MVCC** to prevent these problems.

## Lock Types

### Row-Level Locks

Row-level locking in SQL is explicit — you opt in using `FOR UPDATE` or `FOR SHARE`. `FOR UPDATE` acquires an **Exclusive Lock** on each returned row, preventing any other transaction from modifying or locking it until you commit. `FOR SHARE` acquires a **Shared Lock** that allows other readers but blocks writers. `FOR UPDATE SKIP LOCKED` is the basis of efficient job queue implementations: instead of blocking when a row is locked by another worker, it silently skips that row, allowing each worker to grab its own row without contention or retry loops.

```sql
-- Exclusive row lock: only you can read or modify this row until COMMIT
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;

-- Share lock: others can read but not modify
SELECT * FROM accounts WHERE id = 1 FOR SHARE;

-- Skip locked rows (great for job queues)
SELECT * FROM jobs WHERE status = 'pending'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;
-- Skips rows already locked by other workers
```

### Table-Level Locks

Table-level locks are the bluntest instrument in the database's concurrency toolkit. They are rarely taken by application SQL directly — instead, they are automatically acquired by DDL commands. `ALTER TABLE` always acquires `ACCESS EXCLUSIVE MODE`, which blocks every other operation on the table (reads, writes, other DDL) for the entire duration of the schema change. On a busy production table with millions of rows, even a simple `ALTER TABLE ADD COLUMN` can cause significant downtime. The solution is to use online DDL tools like `pt-online-schema-change` (MySQL) or `pg-osc` (PostgreSQL).

```sql
-- Lock entire table (blocks all reads and writes by others)
LOCK TABLE orders IN ACCESS EXCLUSIVE MODE;

-- Lock for writes only (reads still allowed)
LOCK TABLE orders IN ROW EXCLUSIVE MODE;

-- These are usually acquired implicitly by DDL commands
-- ALTER TABLE acquires ACCESS EXCLUSIVE automatically
```

## Deadlock

A deadlock occurs when two transactions each wait for a lock held by the other - a circular dependency. Neither can proceed.

```
Transaction 1: locks Row A, waits for Row B
Transaction 2: locks Row B, waits for Row A
→ Deadlock! Database detects and kills one transaction.
```

```sql
-- Transaction 1 (Session 1)
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- locks row 1
-- Waiting for row 2...
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

-- Transaction 2 (Session 2) - runs simultaneously
BEGIN;
UPDATE accounts SET balance = balance - 50 WHERE id = 2;   -- locks row 2
-- Waiting for row 1... DEADLOCK!
UPDATE accounts SET balance = balance + 50 WHERE id = 1;
```

**Preventing deadlocks:**
1. Always access resources in the same order (always lock row 1 before row 2)
2. Use `SELECT ... FOR UPDATE` to lock all rows you need at the start
3. Keep transactions short

## MVCC - Multi-Version Concurrency Control

PostgreSQL uses MVCC instead of pure locking for reads. Each transaction sees a **snapshot** of the database as it was when the transaction started. Writers don't block readers; readers don't block writers.

```
Without MVCC:          With MVCC:
Read blocks Write  →   Readers see a snapshot (old version)
Write blocks Read  →   Writers create new versions
                        Old versions cleaned up by VACUUM
```

```sql
-- Session 1
BEGIN;
SELECT COUNT(*) FROM orders;  -- sees 1000 rows

-- Session 2 (simultaneously)
INSERT INTO orders (...);
COMMIT;  -- adds row 1001

-- Back to Session 1
SELECT COUNT(*) FROM orders;  -- still sees 1000 rows (snapshot isolation)
COMMIT;
```

## Optimistic vs Pessimistic Locking

### Pessimistic Locking
Lock the row when you read it - assumes conflicts are likely:

```sql
-- Lock immediately, no one else can modify while you work
BEGIN;
SELECT * FROM inventory WHERE product_id = 5 FOR UPDATE;
-- ... decide whether to deduct stock ...
UPDATE inventory SET stock = stock - 1 WHERE product_id = 5;
COMMIT;
```

### Optimistic Locking
Don't lock - check for conflicts when updating (assumes conflicts are rare):

```sql
-- Read with version number
SELECT stock, version FROM inventory WHERE product_id = 5;
-- Got: stock=10, version=42

-- Update only if version hasn't changed (no one else modified it)
UPDATE inventory
SET stock = 9, version = 43
WHERE product_id = 5 AND version = 42;
-- If 0 rows affected → someone else updated it → retry
```

Optimistic locking is implemented in the application, not in SQL - but the pattern is common in ORMs (Hibernate, ActiveRecord, Prisma).

## Checking Lock Activity

When a production application slows down inexplicably, the first place to check in PostgreSQL is `pg_locks` and `pg_stat_activity`. `pg_locks` shows every lock currently held or requested in the system. `WHERE NOT granted` filters for locks that are *waiting* — these are the bottleneck. The `pg_blocking_pids()` function is the key tool for tracing the dependency chain: given a blocked PID, it returns the PIDs of all transactions blocking it. This is essential for identifying long-running transactions that are holding locks and starving other queries.

```sql
-- PostgreSQL: see current locks
SELECT
  pid,
  relation::regclass AS table,
  mode,
  granted
FROM pg_locks
WHERE NOT granted;   -- show only waiting locks

-- Find blocking and blocked queries
SELECT
  blocked.pid         AS blocked_pid,
  blocked.query       AS blocked_query,
  blocking.pid        AS blocking_pid,
  blocking.query      AS blocking_query
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking
  ON blocking.pid = ANY(pg_blocking_pids(blocked.pid));
```

## Summary

- Row locks (`FOR UPDATE`) prevent two transactions from modifying the same row
- `SKIP LOCKED` is ideal for job queue workers - skips rows locked by other workers
- Deadlock = circular lock dependency - database kills one transaction; prevent by consistent lock ordering
- MVCC (PostgreSQL): readers see a snapshot, never blocked by writers
- Pessimistic locking: lock early, safe but lower concurrency
- Optimistic locking: no lock, check version at update time, better concurrency but needs retry logic
