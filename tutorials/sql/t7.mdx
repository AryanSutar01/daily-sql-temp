## ORDER BY

`ORDER BY` sorts the result set by one or more columns. Without it, the database returns rows in no guaranteed order - the order can change between runs.

```sql
-- Sort ascending (default - A→Z, 0→9, oldest→newest)
SELECT * FROM users ORDER BY name;
SELECT * FROM users ORDER BY name ASC;   -- explicit

-- Sort descending (Z→A, 9→0, newest→oldest)
SELECT * FROM users ORDER BY name DESC;

-- Most recent orders first
SELECT * FROM orders ORDER BY created_at DESC;

-- Highest salary first
SELECT * FROM employees ORDER BY salary DESC;
```

## ASC vs DESC

| | ASC | DESC |
|-|-----|------|
| Numbers | 1, 2, 3... | ...3, 2, 1 |
| Text | A, B, C... | ...C, B, A |
| Dates | oldest first | newest first |
| Default? | ✅ Yes | ❌ No |

## Sort by Multiple Columns

The second column breaks ties in the first:

```sql
-- Sort by city, then by age within each city
SELECT name, city, age
FROM users
ORDER BY city ASC, age DESC;
```

Result:
```
+----------+-----------+-----+
| name     | city      | age |
+----------+-----------+-----+
| Rahul    | Delhi     | 35  |  ← Delhi first, oldest first
| Priya    | Delhi     | 22  |
| Amit     | Mumbai    | 40  |  ← Mumbai second
| Sneha    | Mumbai    | 30  |
| Kiran    | Pune      | 28  |  ← Pune last
+----------+-----------+-----+
```

## ORDER BY Column Position

You can reference columns by their position number in the SELECT list - but this is fragile and should be avoided in production:

```sql
-- Same as ORDER BY name ASC, age DESC
SELECT name, age, city FROM users ORDER BY 1 ASC, 2 DESC;
```

However, using position numbers in GROUP BY is common and acceptable:
```sql
SELECT city, COUNT(*) FROM users GROUP BY 1 ORDER BY 2 DESC;
```

## ORDER BY with SELECT Alias

ORDER BY runs after SELECT, so you can use aliases:

```sql
SELECT name, salary * 12 AS annual_salary
FROM employees
ORDER BY annual_salary DESC;  -- ✅ alias works here
```

## NULL Ordering

NULLs sort to the end in ASC by default in PostgreSQL, and to the beginning in MySQL.

```sql
-- PostgreSQL: control NULL position
SELECT * FROM users ORDER BY last_login DESC NULLS LAST;
SELECT * FROM users ORDER BY last_login ASC  NULLS FIRST;
```

## LIMIT

`LIMIT` restricts the number of rows returned:

```sql
-- First 10 rows
SELECT * FROM users LIMIT 10;

-- Top 5 highest-paid employees
SELECT name, salary FROM employees
ORDER BY salary DESC
LIMIT 5;

-- Fastest/simplest way to check a table
SELECT * FROM orders LIMIT 3;
```

> Always use `ORDER BY` with `LIMIT` - without it, which 10 rows you get is unpredictable.

## OFFSET - Pagination

`OFFSET` skips a number of rows before starting to return:

```sql
-- Page 1: rows 1-10
SELECT * FROM products ORDER BY id LIMIT 10 OFFSET 0;

-- Page 2: rows 11-20
SELECT * FROM products ORDER BY id LIMIT 10 OFFSET 10;

-- Page 3: rows 21-30
SELECT * FROM products ORDER BY id LIMIT 10 OFFSET 20;
```

**Pagination formula:**
```
OFFSET = (page_number - 1) × page_size
```

```sql
-- Dynamic pagination (replace :page and :size with values)
SELECT * FROM products
ORDER BY created_at DESC
LIMIT :size OFFSET (:page - 1) * :size;
```

**⚠️ OFFSET at large page numbers is slow:**
On page 1000 with 20 rows per page, the database still reads 20,000 rows and discards the first 19,980. For large datasets, use cursor-based pagination instead.

## Cursor-Based Pagination (Better for Production)

```sql
-- Instead of OFFSET, use the last seen ID as a cursor
-- First page
SELECT * FROM orders ORDER BY id DESC LIMIT 20;

-- Next page (pass the last id from previous page)
SELECT * FROM orders
WHERE id < :last_seen_id
ORDER BY id DESC
LIMIT 20;
```

This is always fast regardless of page number because it uses the index directly.

## FETCH (SQL Standard)

PostgreSQL and SQL Server support the SQL standard alternative to LIMIT:

```sql
-- PostgreSQL / SQL Server
SELECT * FROM users
ORDER BY id
FETCH FIRST 10 ROWS ONLY;

-- With offset
SELECT * FROM users
ORDER BY id
OFFSET 20 ROWS
FETCH NEXT 10 ROWS ONLY;
```

## TOP (SQL Server)

```sql
-- SQL Server syntax
SELECT TOP 10 * FROM users ORDER BY salary DESC;
SELECT TOP 10 PERCENT * FROM users ORDER BY salary DESC;
```

## Real-World Patterns

```sql
-- Leaderboard: top 10 users by score
SELECT name, score
FROM game_scores
ORDER BY score DESC
LIMIT 10;

-- Most recent 5 orders for a customer
SELECT order_id, total, status, created_at
FROM orders
WHERE customer_id = 101
ORDER BY created_at DESC
LIMIT 5;

-- Latest product page (page 3, 12 per page)
SELECT name, price, stock
FROM products
WHERE is_active = TRUE
ORDER BY created_at DESC
LIMIT 12 OFFSET 24;

-- Find the oldest unprocessed job in the queue
SELECT * FROM jobs
WHERE status = 'pending'
ORDER BY created_at ASC
LIMIT 1;
```

## Summary

- `ORDER BY col ASC` - sort ascending (default)
- `ORDER BY col DESC` - sort descending  
- Multiple columns - secondary column breaks ties in primary
- Always pair `LIMIT` with `ORDER BY` - without ordering, results are non-deterministic
- `OFFSET` enables pagination but becomes slow at large page numbers
- For production pagination on large tables, use cursor-based pagination (`WHERE id < :last_id`)
- `ORDER BY` aliases from SELECT are allowed; `WHERE` aliases are not
