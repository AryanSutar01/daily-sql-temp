## Aggregate Functions: How the Database Engine Computes Them

Aggregate functions look simple in SQL, but their physical implementation determines both correctness (in the presence of NULLs) and performance (especially with DISTINCT).

### HashAggregate: The Physical Implementation of GROUP BY

When you write `GROUP BY`, the database typically uses a **HashAggregate** operator:

```
Query: SELECT city, COUNT(*), SUM(salary) FROM employees GROUP BY city;

HashAggregate execution:
  1. Read rows one by one from the source (sequential scan or index scan)
  
  2. For each row [city='Mumbai', salary=80000]:
     Compute hash of group key: hash('Mumbai') = 42
     Look up hash table slot 42:
       If not found: create new entry {city='Mumbai', count=0, sum=0}
       Increment: {city='Mumbai', count=1, sum=80000}
  
  3. For each row [city='Delhi', salary=60000]:
     hash('Delhi') = 17
     Create: {city='Delhi', count=1, sum=60000}
  
  4. For each row [city='Mumbai', salary=95000]:
     hash('Mumbai') = 42
     Found! Increment: {city='Mumbai', count=2, sum=175000}
  
  5. After all rows processed:
     Emit one result row per hash table entry:
     ('Mumbai', 2, 175000), ('Delhi', 1, 60000), ...
```

**Memory requirement**: The hash table must fit in `work_mem` (PostgreSQL). If it doesn't fit, the database spills to disk using a Grace Hash Join variant — dramatically slower. For large GROUP BY operations on high-cardinality columns, increase `work_mem`.

### Two-Phase Aggregation: Partial + Final

For distributed databases and even single-node query optimization, aggregation is often split into **two phases** to minimize data movement:

```
Two-phase COUNT(*) by city on a partitioned table:

Phase 1 (Partial HashAggregate — one per partition):
  Partition 1 scan: {Mumbai: 3000, Delhi: 1500, Pune: 800}
  Partition 2 scan: {Mumbai: 2500, Delhi: 900,  Pune: 1200}

Phase 2 (Final HashAggregate — merge partial results):
  Merge Mumbai: 3000 + 2500 = 5500
  Merge Delhi:  1500 + 900  = 2400
  Merge Pune:   800  + 1200 = 2000

Result: {Mumbai: 5500, Delhi: 2400, Pune: 2000}
```

This is why EXPLAIN plans for GROUP BY often show TWO HashAggregate nodes — one partial and one final. Partial aggregation dramatically reduces the data transferred between query stages.

### The Cost of COUNT(DISTINCT col)

`COUNT(DISTINCT col)` requires tracking all unique values seen so far — this cannot be computed incrementally like COUNT(*):

```sql
-- COUNT(*): O(1) memory per group
SELECT city, COUNT(*) FROM employees GROUP BY city;
-- For each city: just keep a running counter (1 integer per group)

-- COUNT(DISTINCT dept): O(cardinality) memory per city!
SELECT city, COUNT(DISTINCT dept) FROM employees GROUP BY city;
-- For each city: must keep ALL unique dept values seen
-- If Mumbai has employees in 50 departments:
--   Hash set for Mumbai: {Engineering, Sales, Marketing, ..., HR} = 50 entries
-- Across all cities: potentially millions of values in memory

-- At very large scale: use HyperLogLog for approximate COUNT(DISTINCT)
-- PostgreSQL extension: CREATE EXTENSION hll;
-- SELECT city, hll_cardinality(hll_add_agg(hll_hash_text(dept)))
-- Returns approximate count with ~2% error but uses O(log log N) memory
```

## What Are Aggregate Functions?

Aggregate functions collapse multiple rows into a single summary value. Instead of returning one row per record, they return one value per group.

| Function | Returns | Ignores NULLs? |
|----------|---------|---------------|
| `COUNT(*)` | Number of rows | ❌ No |
| `COUNT(col)` | Number of non-NULL values | ✅ Yes |
| `SUM(col)` | Total of all values | ✅ Yes |
| `AVG(col)` | Average of all values | ✅ Yes |
| `MIN(col)` | Smallest value | ✅ Yes |
| `MAX(col)` | Largest value | ✅ Yes |

## COUNT

```sql
-- Count all rows
SELECT COUNT(*) AS total_users FROM users;

-- Count non-NULL values only
SELECT COUNT(phone) AS users_with_phone FROM users;

-- Count distinct values
SELECT COUNT(DISTINCT city) AS unique_cities FROM users;

-- Interview: Why might COUNT(*) differ from COUNT(column)?
-- COUNT(*) = 1000 but COUNT(phone) = 650 means 350 users have no phone (NULL)
```

## SUM

```sql
-- Total revenue
SELECT SUM(total) AS total_revenue FROM orders;

-- Total per category
SELECT category_id, SUM(price * stock) AS inventory_value
FROM products
GROUP BY category_id;

-- SUM with condition
SELECT SUM(CASE WHEN status = 'completed' THEN total ELSE 0 END) AS completed_revenue
FROM orders;
```

## AVG

```sql
-- Average order value
SELECT ROUND(AVG(total), 2) AS avg_order_value FROM orders;

-- Average salary per department
SELECT department, ROUND(AVG(salary), 0) AS avg_salary
FROM employees
GROUP BY department;
```

**Interview trap:** AVG ignores NULLs. If 3 of 5 salary values are NULL, AVG divides by 2, not 5. This inflates the average compared to what users might expect.

```sql
-- These give different results when NULLs are present:
SELECT AVG(salary) FROM employees;               -- divides by non-NULL count
SELECT SUM(salary) / COUNT(*) FROM employees;    -- divides by ALL rows
```

## MIN and MAX

```sql
-- Salary range
SELECT MIN(salary) AS lowest, MAX(salary) AS highest FROM employees;

-- Earliest and latest order
SELECT MIN(created_at) AS first_order, MAX(created_at) AS last_order
FROM orders;

-- Alphabetically first and last product name
SELECT MIN(name) AS first_alpha, MAX(name) AS last_alpha FROM products;

-- Per-customer order history
SELECT
  customer_id,
  MIN(created_at) AS first_purchase,
  MAX(created_at) AS last_purchase,
  MAX(total)      AS largest_order
FROM orders
GROUP BY customer_id;
```

## Aggregates Without GROUP BY

Without GROUP BY, aggregate functions collapse the ENTIRE table into one row:

```sql
SELECT
  COUNT(*)         AS total_orders,
  COUNT(DISTINCT customer_id) AS unique_customers,
  SUM(total)       AS total_revenue,
  ROUND(AVG(total), 2) AS avg_order,
  MIN(total)       AS smallest_order,
  MAX(total)       AS largest_order
FROM orders
WHERE status = 'completed';
```

## Multiple Aggregates in One Query

```sql
-- Complete sales summary
SELECT
  COUNT(*)                  AS total_orders,
  COUNT(DISTINCT customer_id) AS unique_buyers,
  SUM(total)                AS gross_revenue,
  SUM(total) * 0.18         AS gst_collected,
  ROUND(AVG(total), 2)      AS avg_order_value,
  MIN(total)                AS min_order,
  MAX(total)                AS max_order
FROM orders
WHERE status = 'completed'
  AND created_at >= '2024-01-01';
```

## HAVING - Filter After Aggregation

```sql
-- Only departments with more than 5 employees
SELECT department, COUNT(*) AS headcount
FROM employees
GROUP BY department
HAVING COUNT(*) > 5
ORDER BY headcount DESC;

-- Products with total sales > 1M
SELECT product_id, SUM(quantity * unit_price) AS revenue
FROM order_items
GROUP BY product_id
HAVING SUM(quantity * unit_price) > 1000000;
```

## Real-World: Customer Analytics Dashboard

```sql
SELECT
  customer_id,
  COUNT(*)                AS total_orders,
  SUM(total)              AS lifetime_value,
  ROUND(AVG(total), 2)    AS avg_order,
  MIN(created_at)         AS first_order_date,
  MAX(created_at)         AS last_order_date,
  MAX(created_at) - MIN(created_at) AS customer_tenure
FROM orders
WHERE status = 'completed'
GROUP BY customer_id
HAVING COUNT(*) >= 2
ORDER BY lifetime_value DESC
LIMIT 100;
```

## Summary

- Aggregate functions collapse many rows into one summary value
- `COUNT(*)` counts rows; `COUNT(col)` skips NULLs; `COUNT(DISTINCT col)` counts unique non-NULL values
- `AVG` ignores NULLs - this can inflate the average when many values are missing
- `HAVING` filters groups after aggregation (like WHERE but for aggregate results)
- You can have multiple aggregates in a single SELECT for a complete summary
