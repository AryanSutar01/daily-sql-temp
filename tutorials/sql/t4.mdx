## How DML Achieves Atomicity: The Write-Ahead Log

`INSERT`, `UPDATE`, and `DELETE` look simple on the surface — but ensuring they are **atomic** (all-or-nothing) even when the server crashes mid-operation requires a sophisticated logging mechanism.

### The Write-Ahead Log (WAL) Protocol

Every database that supports ACID uses a **WAL** (PostgreSQL calls it WAL; MySQL InnoDB calls it the redo log). The protocol is:

```
Rule: NEVER write data to disk before writing the log record first.

When you run: UPDATE accounts SET balance = balance - 1000 WHERE id = 1;

Step 1: Write WAL record (to WAL buffer → WAL file):
  LSN 00001: BEGIN TRANSACTION txn_id=42
  LSN 00002: UPDATE accounts, page=5, slot=3
             OLD: balance=5000
             NEW: balance=4000

Step 2: Modify the data page IN MEMORY (buffer pool):
  accounts table, page 5, slot 3: balance = 4000

Step 3: COMMIT:
  LSN 00003: COMMIT txn_id=42
  WAL buffer flushed to disk (fsync)
  → Commit is durable once WAL is on disk!
  
Step 4: (Asynchronously, later) Modified page flushed to data file

Crash recovery:
  Server crashes after step 3 but data page not yet on disk:
  On restart: read WAL log, replay all committed transactions
  → Database is consistent! (REDO)
  
  Server crashes after step 1 but before step 3 (no commit):
  On restart: read WAL log, find uncommitted transaction 42
  → Rollback: UNDO the partial changes using OLD values in WAL
```

This is why `COMMIT` might feel "slow" — the commit is only acknowledged after the WAL record is fsynced to disk. The data page may still be in memory (unflushed) — that's fine because WAL can recover it.

### MVCC: How Reads and Writes Don't Block Each Other

Modern databases use **MVCC (Multi-Version Concurrency Control)** to allow readers and writers to operate simultaneously without locks:

```
accounts table with MVCC (PostgreSQL conceptual):

Row tuple: [xmin, xmax, balance]
  xmin: transaction ID that CREATED this version
  xmax: transaction ID that DELETED this version (or 0 if still current)

Initial state (committed by transaction 1):
  [xmin=1, xmax=0, balance=5000]  ← current version

Transaction 42 runs: UPDATE SET balance = 4000
  New version created: [xmin=42, xmax=0, balance=4000]
  Old version marked: [xmin=1, xmax=42, balance=5000]

During transaction 42 (not yet committed):
  Transaction 50 runs SELECT: sees [xmin=1, xmax=0, balance=5000]
  → Transaction 50 reads the OLD version (balance=5000)
  → No lock needed! Reader doesn't wait for writer!

Transaction 42 commits:
  Transaction 60 runs SELECT: sees [xmin=42, xmax=0, balance=4000]
  → Now reads the NEW version (balance=4000)
```

**Key insight**: In MVCC, readers NEVER block writers, and writers NEVER block readers. This is fundamentally different from pessimistic locking systems. The trade-off: **dead rows** (old versions) accumulate and must be cleaned up by the `VACUUM` process (PostgreSQL) or purge thread (MySQL InnoDB).

### Row-Level Locking for DML

DML operations lock at the **row level** (not the table), which is why:

```sql
-- Transaction A:
UPDATE orders SET status = 'shipped' WHERE id = 100;  -- locks ROW 100 only

-- Transaction B (simultaneously):
UPDATE orders SET status = 'cancelled' WHERE id = 200;  -- locks ROW 200
-- → Both run in parallel! Different rows, no conflict.

-- Transaction C:
UPDATE orders SET status = 'cancelled' WHERE id = 100;
-- → WAITS for Transaction A to release its lock on row 100
-- → Then updates (overwriting Transaction A's result)
-- Or may deadlock if A and C are waiting for each other
```

**Deadlock** occurs when Transaction A holds Lock X and waits for Lock Y, while Transaction B holds Lock Y and waits for Lock X. Databases detect this via lock dependency graphs and kill one transaction automatically.

## DML - Data Manipulation Language

DML commands work with the **actual data** inside tables. Unlike DDL, all DML can be wrapped in a transaction and rolled back.

| Command | Purpose |
|---------|---------|
| `INSERT` | Add new rows |
| `UPDATE` | Modify existing rows |
| `DELETE` | Remove rows |

## INSERT

### Single Row

```sql
-- Always specify column names (safer, order-independent)
INSERT INTO users (name, email, city)
VALUES ('Alice', 'alice@email.com', 'Mumbai');

-- Without column names (must match exact column order - fragile)
INSERT INTO users
VALUES (DEFAULT, 'Bob', 'bob@email.com', 'Delhi', NOW());
```

### Multiple Rows (Batch Insert)

```sql
-- One INSERT, many rows - much faster than individual inserts
INSERT INTO products (name, price, category_id) VALUES
  ('Laptop',    75000.00, 1),
  ('Mouse',       599.00, 1),
  ('Keyboard',   1299.00, 1),
  ('Desk',       8999.00, 2),
  ('Chair',     12000.00, 2);
```

### INSERT ... SELECT

```sql
-- Insert rows from another table or query
INSERT INTO users_archive (id, name, email, created_at)
SELECT id, name, email, created_at
FROM users
WHERE created_at < '2023-01-01';

-- Insert aggregated data
INSERT INTO customer_stats (customer_id, total_orders, total_spent)
SELECT customer_id, COUNT(*), SUM(total)
FROM orders
GROUP BY customer_id;
```

### RETURNING (PostgreSQL)

```sql
-- Get the inserted row's data back immediately
INSERT INTO users (name, email)
VALUES ('Alice', 'alice@email.com')
RETURNING id, created_at;

-- Useful to get the auto-generated ID
INSERT INTO orders (customer_id, total)
VALUES (1, 5000.00)
RETURNING id;
```

### ON CONFLICT - Upsert

Handle duplicate key violations gracefully.

```sql
-- Do nothing on conflict (skip duplicates silently)
INSERT INTO users (email, name)
VALUES ('alice@email.com', 'Alice')
ON CONFLICT (email) DO NOTHING;

-- Update on conflict (upsert - insert or update)
INSERT INTO users (email, name, login_count)
VALUES ('alice@email.com', 'Alice', 1)
ON CONFLICT (email) DO UPDATE SET
  name        = EXCLUDED.name,
  login_count = users.login_count + 1,
  updated_at  = NOW();
-- EXCLUDED refers to the row that was attempted to be inserted
```

## UPDATE

### Basic Update

```sql
-- Update one column
UPDATE users SET city = 'Pune' WHERE id = 1;

-- Update multiple columns
UPDATE users
SET
  name       = 'Alice Kumar',
  city       = 'Bangalore',
  updated_at = NOW()
WHERE id = 1;
```

> ⚠️ **Always include a WHERE clause.** `UPDATE users SET status = 'inactive'` without WHERE updates EVERY row in the table.

### Update with Expressions

```sql
-- Increment / decrement
UPDATE products SET stock     = stock - 1      WHERE id = 5;
UPDATE users    SET login_count = login_count + 1 WHERE id = 42;

-- Apply a calculation
UPDATE order_items SET total_price = quantity * unit_price;

-- Update using CASE
UPDATE users
SET tier = CASE
  WHEN total_spent >= 100000 THEN 'Platinum'
  WHEN total_spent >= 50000  THEN 'Gold'
  WHEN total_spent >= 10000  THEN 'Silver'
  ELSE 'Bronze'
END;
```

### UPDATE from Another Table (PostgreSQL)

```sql
-- Update using values from a joined table
UPDATE orders
SET status = 'confirmed'
FROM payments
WHERE orders.id = payments.order_id
  AND payments.status = 'completed';

-- MySQL syntax uses JOIN
UPDATE orders o
JOIN payments p ON o.id = p.order_id
SET o.status = 'confirmed'
WHERE p.status = 'completed';
```

### RETURNING (PostgreSQL)

```sql
-- See which rows were updated
UPDATE users
SET status = 'inactive'
WHERE last_login < NOW() - INTERVAL '1 year'
RETURNING id, name, email;
```

## DELETE

### Basic Delete

```sql
-- Delete specific rows
DELETE FROM users WHERE id = 1;

-- Delete with multiple conditions
DELETE FROM orders
WHERE status = 'cancelled'
  AND created_at < NOW() - INTERVAL '90 days';
```

> ⚠️ **Always include a WHERE clause.** `DELETE FROM users` without WHERE deletes every single row.

### Delete Using a Subquery

```sql
-- Delete users who have never ordered
DELETE FROM users
WHERE id NOT IN (
  SELECT DISTINCT customer_id FROM orders
);

-- Delete duplicate rows, keep lowest ID
DELETE FROM users
WHERE id NOT IN (
  SELECT MIN(id) FROM users GROUP BY email
);
```

### DELETE from Multiple Tables (MySQL)

```sql
-- Delete related rows in one query (MySQL)
DELETE oi FROM order_items oi
JOIN orders o ON oi.order_id = o.id
WHERE o.status = 'cancelled';
```

### RETURNING (PostgreSQL)

```sql
-- See what was deleted
DELETE FROM sessions
WHERE expires_at < NOW()
RETURNING id, user_id, created_at;
```

## Safe DML Practices

### Always Preview with SELECT First

```sql
-- Step 1: See exactly what will be affected
SELECT * FROM users WHERE last_login < '2022-01-01';

-- Step 2: If it looks right, run the DELETE
DELETE FROM users WHERE last_login < '2022-01-01';
```

### Use Transactions for Multi-Step Operations

```sql
BEGIN;

UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
UPDATE accounts SET balance = balance + 1000 WHERE id = 2;

-- Check the result looks correct
SELECT id, balance FROM accounts WHERE id IN (1, 2);

COMMIT;   -- save if correct
-- ROLLBACK;  -- undo if something looks wrong
```

### Batch Large Deletes

```sql
-- ❌ Dangerous on large tables: locks for a long time
DELETE FROM logs WHERE created_at < '2023-01-01';

-- ✅ Better: delete in batches
DELETE FROM logs
WHERE id IN (
  SELECT id FROM logs
  WHERE created_at < '2023-01-01'
  LIMIT 10000
);
-- Run this in a loop from application code until 0 rows affected
```

## Summary

| Command | Key Rule |
|---------|---------|
| `INSERT` | Always list column names; use batch inserts for multiple rows |
| `UPDATE` | ALWAYS include WHERE - no WHERE = updates every row |
| `DELETE` | ALWAYS include WHERE - no WHERE = deletes every row |
| Upsert | Use `ON CONFLICT DO UPDATE` in PostgreSQL |
| Safety | SELECT first to preview; use transactions for multi-step ops |
| Scale | Batch large deletes to avoid long table locks |
