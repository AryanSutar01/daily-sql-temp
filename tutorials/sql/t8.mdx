## DISTINCT: The Physical Cost of Duplicate Elimination

Adding `DISTINCT` to a query changes the entire execution plan. The database must physically identify and eliminate duplicates, which requires either significant memory (hashing) or significant CPU/disk I/O (sorting).

### How the Database Eliminates Duplicates

When the optimizer sees `DISTINCT`, it chooses one of two physical operators:

```
Strategy 1: HashAggregate (Memory Intensive)
  - Read each row and hash the selected columns.
  - Check the hash table: if the hash exists, discard the row.
  - If it doesn't exist, add it and emit the row.
  - Pros: O(N) time complexity, very fast if hash table fits in memory.
  - Cons: Fails or spills to disk if the number of unique combinations is massive.

Strategy 2: Sort / Unique (CPU & I/O Intensive)
  - Sort the entire result set by the selected columns (O(N log N)).
  - Scan the sorted list sequentially.
  - If the current row is identical to the previous row, discard it.
  - Pros: Works gracefully for datasets larger than memory.
  - Cons: Sorting is computationally expensive and slow.
```

If you apply `DISTINCT` on an already-indexed column (e.g., `SELECT DISTINCT category_id`), the optimizer can perform an **Index Only Scan**, reading the unique values directly from the B-tree structure without hitting the table at all — an incredibly fast optimization.

### The "DISTINCT to Fix a JOIN" Anti-Pattern

A common mistake is using `DISTINCT` to fix a query that returns unexpected duplicate rows due to a fan-out JOIN (e.g., joining a user to their orders and getting the user multiple times). 

```sql
-- The Anti-Pattern:
SELECT DISTINCT u.id, u.name 
FROM users u JOIN orders o ON u.id = o.customer_id;

-- What happens physically:
-- 1. The database computes the FULL join (creating millions of intermediate rows).
-- 2. It then performs an expensive HashAggregate or Sort to throw away 99% of those rows.
-- Extremely inefficient!

-- The Architectural Fix (EXISTS / Semi-Join):
SELECT u.id, u.name 
FROM users u 
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = u.id);

-- What happens physically (Semi-Join):
-- 1. The database scans users.
-- 2. For each user, it looks up the orders index.
-- 3. AS SOON AS it finds ONE order, it emits the user and moves to the next user.
-- No intermediate duplication, no expensive sorting or hashing required!
```

## DISTINCT

`DISTINCT` removes duplicate rows from query results. It applies to the entire selected row - not just one column.

### Basic Usage

```sql
-- All cities where users live (no duplicates)
SELECT DISTINCT city FROM users;

-- Without DISTINCT - repeated for every user in that city
SELECT city FROM users;
-- Mumbai, Mumbai, Mumbai, Delhi, Delhi, Pune ...

-- With DISTINCT - each city appears once
SELECT DISTINCT city FROM users;
-- Mumbai, Delhi, Pune, Bangalore
```

### DISTINCT on Multiple Columns

DISTINCT applies to the combination of all selected columns:

```sql
-- Unique (city, status) pairs
SELECT DISTINCT city, status FROM users;
-- Mumbai + active
-- Mumbai + inactive
-- Delhi + active
-- These are all different combinations
```

### COUNT DISTINCT

```sql
-- How many unique cities do our users come from?
SELECT COUNT(DISTINCT city) AS unique_cities FROM users;

-- How many unique customers placed orders?
SELECT COUNT(DISTINCT customer_id) AS unique_customers FROM orders;

-- How many unique products were sold last month?
SELECT COUNT(DISTINCT product_id) AS products_sold
FROM order_items oi
JOIN orders o ON oi.order_id = o.id
WHERE o.created_at >= NOW() - INTERVAL '30 days';
```

### DISTINCT vs GROUP BY

Both can deduplicate - they often produce the same result but work differently:

```sql
-- These produce the same result:
SELECT DISTINCT city FROM users ORDER BY city;

SELECT city FROM users GROUP BY city ORDER BY city;

-- Use DISTINCT when you just want unique values
-- Use GROUP BY when you also want to aggregate (COUNT, SUM, etc.)
SELECT city, COUNT(*) FROM users GROUP BY city;  -- can't do this with DISTINCT alone
```

### Performance Note

`DISTINCT` requires sorting and deduplication internally - it can be slow on large result sets. If you find yourself using DISTINCT to fix duplicate rows from a JOIN, that usually means there's a problem with the JOIN logic itself.

```sql
-- ❌ DISTINCT hiding a problem - why are there duplicates?
SELECT DISTINCT u.name FROM users u JOIN orders o ON u.id = o.customer_id;

-- ✅ Better: understand why duplicates exist
-- A user appears once per order → use COUNT or fix the query logic
SELECT u.name, COUNT(o.id) AS order_count
FROM users u
LEFT JOIN orders o ON u.id = o.customer_id
GROUP BY u.name;
```

## Aliases

Aliases give temporary names to columns or tables. They make queries more readable without changing the actual data.

### Column Aliases

```sql
-- Rename a column in the output
SELECT name AS customer_name FROM users;
SELECT email AS contact_email FROM users;

-- Alias a calculated expression
SELECT
  name,
  price * 1.18          AS price_with_gst,
  price * 0.9           AS discounted_price,
  stock * price         AS inventory_value
FROM products;

-- AS keyword is optional
SELECT name customer_name, email contact FROM users;
-- (AS is more readable - always include it)
```

### Where Aliases Can and Cannot Be Used

```sql
-- ✅ ORDER BY (runs after SELECT - alias is available)
SELECT salary * 12 AS annual_salary FROM employees
ORDER BY annual_salary DESC;

-- ✅ GROUP BY in some databases (PostgreSQL allows it)
SELECT city, COUNT(*) AS total FROM users
GROUP BY city ORDER BY total DESC;

-- ❌ WHERE (runs before SELECT - alias not yet defined)
SELECT salary * 12 AS annual_salary FROM employees
WHERE annual_salary > 600000;
-- ERROR: column "annual_salary" does not exist

-- ✅ Fix: repeat the expression
WHERE salary * 12 > 600000;

-- ✅ Or use a subquery / CTE
WITH base AS (SELECT *, salary * 12 AS annual_salary FROM employees)
SELECT * FROM base WHERE annual_salary > 600000;

-- ❌ HAVING (if referencing a SELECT alias - depends on database)
-- Safe approach: repeat the expression
HAVING COUNT(*) > 5        -- ✅ works everywhere
HAVING total_count > 5     -- may not work in all databases
```

### Table Aliases

Table aliases (also called correlation names) shorten table references in queries:

```sql
-- Without aliases - verbose
SELECT users.name, users.email, orders.total, orders.created_at
FROM users
JOIN orders ON users.id = orders.customer_id;

-- With aliases - much cleaner
SELECT u.name, u.email, o.total, o.created_at
FROM users u
JOIN orders o ON u.id = o.customer_id;

-- AS is optional for table aliases
FROM users AS u  -- same as FROM users u
```

### When Table Aliases Are Required

Self-joins require aliases to distinguish the two instances of the same table:

```sql
-- Employee and their manager - same table, two aliases
SELECT
  e.name  AS employee,
  m.name  AS manager
FROM employees e
JOIN employees m ON e.manager_id = m.id;
```

### Naming Conventions for Aliases

```sql
-- Common single-letter abbreviations
FROM users u
FROM orders o
FROM products p
FROM order_items oi
FROM categories c

-- Or meaningful short names
FROM users usr
FROM orders ord
FROM customer_stats cs
```

## Combining DISTINCT and Aliases

```sql
SELECT DISTINCT
  u.city                        AS customer_city,
  u.status                      AS account_status,
  COUNT(*) OVER ()              AS total_combinations
FROM users u
ORDER BY customer_city, account_status;
```

## Summary

- `DISTINCT` removes duplicate rows from results - applies to all selected columns together
- `COUNT(DISTINCT col)` counts unique values in a column
- If you need DISTINCT because of duplicates from a JOIN, the JOIN is probably wrong
- Column aliases (`AS`) rename output columns - required for expressions, optional for columns
- Table aliases shorten table names in queries - especially useful with JOINs and self-joins
- Aliases in SELECT are available in ORDER BY but NOT in WHERE or HAVING (in standard SQL)
