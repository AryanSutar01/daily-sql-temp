## Subquery Internals: Unnesting and Lateral Execution

Writing a subquery makes a SQL statement conceptually easier for a human to read. However, the database engine hates executing subqueries exactly as written.

### Subquery Flattening (Unnesting)

When you write a subquery in the `WHERE` clause or `FROM` clause, modern query optimizers will immediately attempt to **flatten** or **unnest** it into a standard `JOIN`.

```sql
-- You write a subquery:
SELECT name FROM users 
WHERE id IN (SELECT customer_id FROM orders WHERE total > 5000);

-- The optimizer rewrites the AST internally to a physical Semi-Join:
SELECT users.name 
FROM users 
SEMI JOIN orders ON users.id = orders.customer_id 
WHERE orders.total > 5000;
```

Why does the optimizer do this? Because executing a subquery independently creates a rigid execution pipeline. By flattening the query into a JOIN graph, the optimizer gains the freedom to reorder operations, choose between Hash/Merge/Nested Loop joins, and push down predicates.

If a subquery is too complex to flatten (e.g., it contains `LIMIT`, `OFFSET`, or certain `GROUP BY` combinations), the optimizer is forced to materialize it. It executes the inner query completely, writes the result to a temporary in-memory table, and then executes the outer query against that temp table. This is called an **Opaque Subquery** and is usually terrible for performance.

### The Physics of Correlated Subqueries

A correlated subquery references columns from the outer query. Historically, this forced the database into a row-by-row execution model (a massive nested loop):

```sql
SELECT u.name,
  (SELECT MAX(created_at) FROM orders o WHERE o.customer_id = u.id)
FROM users u;
```

**Physical Execution (The Naive Way):**
1. Read `users` row 1 (Alice, id=1).
2. Execute `SELECT MAX(created_at) FROM orders WHERE customer_id = 1`.
3. Read `users` row 2 (Bob, id=2).
4. Execute `SELECT MAX(created_at) FROM orders WHERE customer_id = 2`.

If `users` has 1 million rows, the database executes the inner query 1 million times. This is $O(N \times M)$ scaling and will bring the database to its knees.

Modern optimizers (like PostgreSQL 10+) try to rewrite correlated subqueries into a `LATERAL JOIN` or a `HashAggregate` on the whole table, computing the max for all users at once and joining the result. When writing production code, you should manually convert correlated subqueries into `JOIN`s or Window Functions to guarantee you don't accidentally trigger a row-by-row execution plan.

## What is a Subquery?

A subquery (also called an inner query or nested query) is a SELECT statement written inside another SQL statement. The inner query runs first, and its result is used by the outer query.

```sql
-- Find users who have placed at least one order
SELECT name FROM users
WHERE id IN (
  SELECT DISTINCT customer_id FROM orders  -- inner query runs first
);
```

## Types of Subqueries

### 1. Scalar Subquery (Returns One Value)

Returns exactly one row and one column. Can be used anywhere a single value is expected.

```sql
-- Products priced above average
SELECT name, price FROM products
WHERE price > (SELECT AVG(price) FROM products);
--             ↑ returns one number e.g. 2500

-- Show each product's price and the overall average side by side
SELECT
  name,
  price,
  (SELECT ROUND(AVG(price), 2) FROM products) AS avg_price,
  price - (SELECT AVG(price) FROM products)   AS diff_from_avg
FROM products;
```

### 2. Row Subquery (Returns One Row, Multiple Columns)

```sql
-- Find the product with the highest price
SELECT * FROM products
WHERE (category_id, price) = (
  SELECT category_id, MAX(price) FROM products GROUP BY category_id LIMIT 1
);
```

### 3. Table Subquery (Returns Multiple Rows - Used in FROM)

Used in the FROM clause as a derived table. Must be given an alias.

```sql
-- Average of per-customer spending totals
SELECT AVG(customer_total) AS avg_customer_ltv
FROM (
  SELECT customer_id, SUM(total) AS customer_total
  FROM orders
  WHERE status = 'completed'
  GROUP BY customer_id
) AS customer_summary;
-- ↑ the alias is required
```

### 4. Column Subquery (Returns Multiple Rows - Used in IN/NOT IN)

```sql
-- Users from cities where we have more than 10 orders
SELECT name, city FROM users
WHERE city IN (
  SELECT city FROM users u
  JOIN orders o ON u.id = o.customer_id
  GROUP BY city
  HAVING COUNT(*) > 10
);
```

## Non-Correlated vs Correlated Subqueries

### Non-Correlated
Runs **once**, completely independent of the outer query.

```sql
-- Inner query runs ONCE, result reused for every outer row
SELECT name FROM products
WHERE price > (SELECT AVG(price) FROM products);
--             ↑ calculated once = e.g. 2500
--             then: WHERE price > 2500 for every row
```

### Correlated
References a column from the outer query - runs **once per row** of the outer query.

```sql
-- For EACH product, compare to its own category average
SELECT name, price FROM products p
WHERE price > (
  SELECT AVG(price) FROM products
  WHERE category_id = p.category_id  -- ← references outer row p
);
-- Runs once per product row - potentially slow on large tables
```

**Interview question:** What's wrong with correlated subqueries at scale?
They execute once per outer row. On a 1M-row table, the inner query runs 1M times. Rewrite as a window function or JOIN for performance.

```sql
-- Correlated subquery → rewritten as window function (much faster)
SELECT name, price FROM (
  SELECT *,
    AVG(price) OVER (PARTITION BY category_id) AS cat_avg
  FROM products
) t
WHERE price > cat_avg;
```

## Subquery in SELECT (Scalar)

```sql
-- Count orders per user shown alongside each user
SELECT
  u.id,
  u.name,
  (SELECT COUNT(*) FROM orders WHERE customer_id = u.id) AS order_count,
  (SELECT MAX(total) FROM orders WHERE customer_id = u.id) AS biggest_order
FROM users u;
-- This is a correlated subquery - runs twice per user row
-- Better: use LEFT JOIN + GROUP BY for performance
```

## Subquery in WHERE

```sql
-- Users who spent above the average customer spending
SELECT name FROM users
WHERE id IN (
  SELECT customer_id FROM orders
  GROUP BY customer_id
  HAVING SUM(total) > (SELECT AVG(total_spent) FROM (
    SELECT SUM(total) AS total_spent FROM orders GROUP BY customer_id
  ) t)
);
```

## Subquery Best Practices

```sql
-- ✅ Use CTE instead of deeply nested subqueries (more readable)
WITH customer_totals AS (
  SELECT customer_id, SUM(total) AS total_spent
  FROM orders GROUP BY customer_id
),
avg_spending AS (
  SELECT AVG(total_spent) AS avg FROM customer_totals
)
SELECT u.name
FROM users u
JOIN customer_totals ct ON u.id = ct.customer_id
CROSS JOIN avg_spending a
WHERE ct.total_spent > a.avg;

-- ✅ Replace correlated subqueries with window functions when possible
-- ✅ Replace IN (subquery) with EXISTS for large datasets - EXISTS short-circuits
```

## Summary

- Scalar subquery: returns one value, used in SELECT or WHERE
- Table subquery (derived table): used in FROM, must have an alias
- Column subquery: returns many rows, used with IN / NOT IN
- Non-correlated: runs once - fast
- Correlated: runs once per outer row - can be slow, consider rewriting as JOIN or window function
- CTEs are subqueries that are named and defined at the top - same execution, much more readable
