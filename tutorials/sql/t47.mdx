## The Architecture of Pivoting: Database vs Application

Pivoting transforms row-based data into column-based reports. While technically possible in SQL, doing this in the database engine violates a core architectural principle: **The database should return raw sets; the application should format the presentation.**

### The Physical Cost of Row Reassembly

When you write a manual Pivot using `CASE WHEN` aggregations, the database engine must:
1. Scan the raw rows.
2. Build an in-memory Hash Table for the `GROUP BY` keys.
3. For *every single column*, evaluate the `CASE` condition and update a running accumulator.

If you pivot sales data into 365 daily columns, the engine must evaluate 365 `CASE` statements for *every single row* before aggregating. This causes massive CPU spikes and inflates the network payload size because the database must dynamically assemble extremely wide, sparse rows.

**Architectural Rule**: Use SQL to calculate the raw, normalized aggregations (e.g., `month, category, revenue`). Send this dense, lightweight dataset over the wire. Let the frontend (JavaScript) or the BI tool (Tableau/PowerBI) pivot the data into a visual grid. Their memory models are designed for UI rendering; the database's memory model is designed for set theory.

## What is Pivoting?

Pivoting transforms row values into column headers - turning a "tall" (normalized) table into a "wide" (report-style) table.

```
Before (tall):              After (pivot):
month | category | revenue  category | Jan   | Feb   | Mar
Jan   | Mobile   | 50000    Mobile   | 50000 | 62000 | 71000
Jan   | Laptop   | 80000    Laptop   | 80000 | 95000 | 88000
Feb   | Mobile   | 62000
Feb   | Laptop   | 95000
Mar   | Mobile   | 71000
Mar   | Laptop   | 88000
```

## Manual Pivot with CASE WHEN (Works in All Databases)

The most universally compatible way to pivot data is using conditional aggregation. By wrapping a `CASE WHEN` statement inside a `SUM()` function, you force the database to only add the revenue if the row matches that specific column's criteria (e.g., `month_num = 1` for January). This approach is highly performant because it scans the dataset exactly once, applying the conditions inline. It works in PostgreSQL, MySQL, SQL Server, and SQLite without any special extensions.

```sql
SELECT
  category,
  SUM(CASE WHEN month_num = 1  THEN revenue ELSE 0 END) AS jan,
  SUM(CASE WHEN month_num = 2  THEN revenue ELSE 0 END) AS feb,
  SUM(CASE WHEN month_num = 3  THEN revenue ELSE 0 END) AS mar,
  SUM(CASE WHEN month_num = 4  THEN revenue ELSE 0 END) AS apr,
  SUM(CASE WHEN month_num = 5  THEN revenue ELSE 0 END) AS may,
  SUM(CASE WHEN month_num = 6  THEN revenue ELSE 0 END) AS jun,
  SUM(CASE WHEN month_num = 7  THEN revenue ELSE 0 END) AS jul,
  SUM(CASE WHEN month_num = 8  THEN revenue ELSE 0 END) AS aug,
  SUM(CASE WHEN month_num = 9  THEN revenue ELSE 0 END) AS sep,
  SUM(CASE WHEN month_num = 10 THEN revenue ELSE 0 END) AS oct,
  SUM(CASE WHEN month_num = 11 THEN revenue ELSE 0 END) AS nov,
  SUM(CASE WHEN month_num = 12 THEN revenue ELSE 0 END) AS dec,
  SUM(revenue) AS annual_total
FROM (
  SELECT
    c.name AS category,
    EXTRACT(MONTH FROM o.created_at)::INT AS month_num,
    SUM(oi.quantity * oi.unit_price) AS revenue
  FROM order_items oi
  JOIN orders    o  ON oi.order_id   = o.id
  JOIN products  p  ON oi.product_id = p.id
  JOIN categories c ON p.category_id = c.id
  WHERE o.status = 'completed'
    AND EXTRACT(YEAR FROM o.created_at) = 2024
  GROUP BY c.name, EXTRACT(MONTH FROM o.created_at)
) monthly
GROUP BY category
ORDER BY annual_total DESC;
```

## Pivot with FILTER (PostgreSQL 9.4+)

Cleaner syntax for conditional aggregation:

PostgreSQL introduced the ANSI-standard `FILTER (WHERE ...)` clause specifically to make conditional aggregation more readable. Instead of burying the logic inside the aggregate function, `FILTER` acts as an inline `WHERE` clause applied only to that specific `SUM()`. It compiles down to the exact same execution plan as the `CASE WHEN` method, but is significantly easier to read and maintain.

```sql
SELECT
  category,
  SUM(revenue) FILTER (WHERE month_num = 1)  AS jan,
  SUM(revenue) FILTER (WHERE month_num = 2)  AS feb,
  SUM(revenue) FILTER (WHERE month_num = 3)  AS mar,
  SUM(revenue) FILTER (WHERE month_num = 4)  AS apr,
  SUM(revenue) FILTER (WHERE month_num = 5)  AS may,
  SUM(revenue) FILTER (WHERE month_num = 6)  AS jun,
  SUM(revenue) AS total
FROM monthly_revenue
GROUP BY category;
```

## Pivot User Counts by Status and City

Pivoting is not exclusive to revenue data. A very common reporting requirement is a matrix of user segment sizes: how many active, inactive, and banned users exist per city? This uses the same `FILTER` conditional aggregation technique, applied to `COUNT(*)` instead of `SUM()`. The result is a dense crosstab that can be rendered directly in any dashboard tool as a heatmap or comparison table.

```sql
SELECT
  city,
  COUNT(*) FILTER (WHERE status = 'active')   AS active,
  COUNT(*) FILTER (WHERE status = 'inactive') AS inactive,
  COUNT(*) FILTER (WHERE status = 'banned')   AS banned,
  COUNT(*) AS total
FROM users
GROUP BY city
ORDER BY total DESC;
```

## CROSSTAB (PostgreSQL tablefunc Extension)

For dynamic pivots, PostgreSQL has `crosstab`:

```sql
-- Enable the extension
CREATE EXTENSION IF NOT EXISTS tablefunc;

-- Use crosstab for dynamic column headers
SELECT * FROM crosstab(
  'SELECT category, month_name, revenue
   FROM monthly_sales
   ORDER BY 1, 2',
  'SELECT DISTINCT month_name FROM monthly_sales ORDER BY 1'
) AS pivot_table (
  category TEXT,
  jan NUMERIC, feb NUMERIC, mar NUMERIC,
  apr NUMERIC, may NUMERIC, jun NUMERIC
);
```

## PIVOT in SQL Server

SQL Server provides a native `PIVOT` keyword that is more declarative than the `CASE WHEN` approach. You define the aggregate function, the column whose values become new column headers (`FOR month_name IN (...)`), and the database handles the conditional aggregation automatically. The limitation is that the column list must be hardcoded — SQL Server's native `PIVOT` does not support dynamic column lists without using dynamic SQL.

```sql
-- SQL Server has native PIVOT syntax
SELECT *
FROM (
  SELECT category, month_name, revenue FROM monthly_sales
) source
PIVOT (
  SUM(revenue) FOR month_name IN ([Jan], [Feb], [Mar], [Apr], [May], [Jun])
) AS pivot_result;
```

## Unpivot - Columns to Rows

Unpivoting does the reverse - turns column headers into row values. This is often necessary when importing poorly structured Excel spreadsheets into a normalized relational format. The most compatible way to unpivot is using `UNION ALL`, where you query the same table multiple times, each time extracting a different column as a standardized row value. While this approach forces the database to scan the source table multiple times (once for each unioned segment), it is completely database-agnostic.

```sql
-- Wide format (pivot table):
-- category | jan   | feb   | mar
-- Mobile   | 50000 | 62000 | 71000

-- Unpivot using UNION ALL (works everywhere)
SELECT 'Mobile' AS category, 'Jan' AS month, 50000 AS revenue
UNION ALL SELECT 'Mobile', 'Feb', 62000
UNION ALL SELECT 'Mobile', 'Mar', 71000;

-- Better: from an actual wide table
SELECT category, 'Jan' AS month, jan AS revenue FROM pivot_table WHERE jan IS NOT NULL
UNION ALL
SELECT category, 'Feb', feb FROM pivot_table WHERE feb IS NOT NULL
UNION ALL
SELECT category, 'Mar', mar FROM pivot_table WHERE mar IS NOT NULL
ORDER BY category, month;
```

## SQL Server UNPIVOT

SQL Server also provides a native `UNPIVOT` operator that is the mirror image of `PIVOT`. Instead of a `UNION ALL` chain, you define the output value column (`revenue`), the output name column (`month`), and the list of source columns to rotate into rows (`jan, feb, mar...`). This is syntactically cleaner than `UNION ALL` for wide tables but is limited to a fixed, known set of source columns.

```sql
SELECT category, month, revenue
FROM pivot_table
UNPIVOT (
  revenue FOR month IN (jan, feb, mar, apr, may, jun)
) AS unpivoted;
```

## Real-World Example: Survey Results Pivot

Survey data is classically stored in "long" (tall) format: one row per response, with a `question_id` and `answer` column. To analyze results in a spreadsheet-style view, you pivot it so that each question becomes a column and each user occupies a single row. `MAX(CASE WHEN ...)` is used here instead of `SUM` because each user can only have one answer per question — `MAX` simply picks that single value out of the group (since the other cells are NULL).

```sql
-- responses: user_id, question_id, answer
-- Pivot: one row per user, one column per question

SELECT
  user_id,
  MAX(CASE WHEN question_id = 1 THEN answer END) AS q1_satisfaction,
  MAX(CASE WHEN question_id = 2 THEN answer END) AS q2_recommend,
  MAX(CASE WHEN question_id = 3 THEN answer END) AS q3_ease_of_use,
  MAX(CASE WHEN question_id = 4 THEN answer END) AS q4_support
FROM survey_responses
GROUP BY user_id
ORDER BY user_id;
```

## Summary

- Pivot: rows → columns - use CASE WHEN + SUM/COUNT/MAX for the aggregate
- `FILTER (WHERE ...)` is cleaner PostgreSQL syntax for conditional aggregation
- Use UNION ALL to unpivot (columns → rows)
- SQL Server has native `PIVOT` and `UNPIVOT` syntax
- PostgreSQL `crosstab()` handles dynamic pivots but requires tablefunc extension
- In practice, most pivoting is done in the BI tool (Tableau, Power BI, Metabase) - SQL pivots are for when you need the data already shaped
