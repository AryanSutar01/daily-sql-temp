## Trigger Architecture: Transactional Hooks and Penalties

A Trigger is essentially an event-driven **Transactional Hook** embedded deep within the database engine's storage manager. While powerful for maintaining data integrity, triggers are infamous for silently destroying database write throughput.

### The Context Switch Penalty

When an application sends a batch `UPDATE` affecting 10,000 rows, a standard SQL engine executes this efficiently via vectorized updates on disk blocks.

If you attach a `FOR EACH ROW` trigger to the table, you completely break this batch optimization. For every single row, the database must halt the storage engine, perform a **Context Switch** to load the PL/pgSQL procedural engine, execute the trigger logic, context-switch back, and process the next row. This can turn a 50ms batch update into a 5,000ms crawl.

### FOR EACH ROW vs FOR EACH STATEMENT

Database architects strongly differentiate between row-level and statement-level triggers:

1. **`FOR EACH ROW`**: Executes once per modified tuple. Essential if you need access to the `NEW` and `OLD` variables (e.g., updating an `updated_at` timestamp on specific rows). Extremely CPU-intensive for bulk operations.
2. **`FOR EACH STATEMENT`**: Executes exactly *once* per SQL command, regardless of whether the command updated 1 row or 1 million rows. Used for table-level validation or auditing (e.g., "Do not allow DELETEs on Sundays"). It incurs almost zero performance overhead.

### Implicit Lock Escalation

Because triggers run synchronously inside the same transaction boundary as the triggering event, if your trigger performs a secondary action (e.g., updating a parent row's aggregate total), it takes an `ExclusiveLock` on that parent row. 
If 50 concurrent transactions update different child rows that all trigger an update to the *same* parent row, the database will serialize all 50 transactions, creating a catastrophic locking bottleneck.

**Architectural Rule**: Keep triggers microscopic in complexity. Never perform complex business logic or cross-table aggregations inside a synchronous row-level trigger unless absolutely necessary.

## What is a Trigger?

A trigger is a function that automatically executes when a specified event (INSERT, UPDATE, DELETE) occurs on a table. Triggers are used for automation - you don't call them directly.

## When to Use Triggers

- Auto-populate derived columns (`updated_at`, `slug`, `full_name`)
- Audit logging - record who changed what and when
- Enforce complex constraints that CHECK can't handle
- Maintain denormalized summary data
- Cascade custom business rules

## Creating a Trigger (Two Steps)

### Step 1: Create the trigger function

```sql
CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = NOW();  -- modify the row being inserted/updated
  RETURN NEW;              -- return modified row
END;
$$ LANGUAGE plpgsql;
```

### Step 2: Attach the trigger to a table

```sql
CREATE TRIGGER trg_users_updated_at
BEFORE UPDATE ON users
FOR EACH ROW
EXECUTE FUNCTION set_updated_at();

-- Now every UPDATE on users automatically sets updated_at = NOW()
UPDATE users SET name = 'Alice New' WHERE id = 1;
-- updated_at is automatically set - no application code needed
```

## Trigger Timing

| Timing | When | Can modify NEW? | Use for |
|--------|------|----------------|---------|
| `BEFORE` | Before the operation | ✅ Yes | Modify/validate data, cancel the operation |
| `AFTER` | After the operation | ❌ No | Audit logging, cascading to other tables |
| `INSTEAD OF` | Replace the operation | ✅ Yes | Making views updatable |

## Common Trigger Patterns

### Audit Log Trigger

An audit log trigger is the definitive use case for `AFTER` triggers. It fires after every `INSERT`, `UPDATE`, or `DELETE`, recording the before/after state of each changed row into an `audit_log` table. PostgreSQL's `TG_TABLE_NAME` and `TG_OP` special variables allow a single generic trigger function to be attached to any table. `row_to_json(OLD)::JSONB` serializes the old row state to JSONB, enabling you to reconstruct exactly what a row looked like at any point in history. This is the basis of compliance auditing and point-in-time data recovery.

```sql
CREATE TABLE audit_log (
  id         BIGSERIAL PRIMARY KEY,
  table_name TEXT,
  operation  TEXT,
  old_data   JSONB,
  new_data   JSONB,
  changed_by TEXT DEFAULT current_user,
  changed_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE OR REPLACE FUNCTION log_changes()
RETURNS TRIGGER AS $$
BEGIN
  INSERT INTO audit_log (table_name, operation, old_data, new_data)
  VALUES (
    TG_TABLE_NAME,
    TG_OP,
    CASE WHEN TG_OP = 'DELETE' THEN row_to_json(OLD)::JSONB ELSE NULL END,
    CASE WHEN TG_OP != 'DELETE' THEN row_to_json(NEW)::JSONB ELSE NULL END
  );
  RETURN COALESCE(NEW, OLD);
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER audit_users
AFTER INSERT OR UPDATE OR DELETE ON users
FOR EACH ROW EXECUTE FUNCTION log_changes();
```

### Auto-generate Slug

A `BEFORE INSERT` trigger can automatically derive computed columns from other columns at write time, centralizing the computation in the database layer rather than trusting every application client to perform it correctly. Here, a URL slug is generated from the article title using a regex to replace non-alphanumeric characters with hyphens. Since this is a `BEFORE` trigger, `NEW` can be modified before it's written to disk — `NEW.slug = ...` overwrites any value the application passed, ensuring the slug is always consistent.

```sql
CREATE OR REPLACE FUNCTION generate_slug()
RETURNS TRIGGER AS $$
BEGIN
  NEW.slug = LOWER(REGEXP_REPLACE(NEW.title, '[^a-zA-Z0-9]+', '-', 'g'));
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_articles_slug
BEFORE INSERT ON articles
FOR EACH ROW EXECUTE FUNCTION generate_slug();
```

### Maintain Summary Table

This trigger demonstrates the summary table synchronization pattern: after every `INSERT` into the `orders` table, the corresponding row in `customer_stats` is immediately updated. The `ON CONFLICT (customer_id) DO UPDATE` is the upsert mechanism — if the customer already has a stats row, it increments the counts. If this is their first order, it creates the stats row. The trade-off is real-time accuracy (stats are always current) vs. write overhead (every order insert now also triggers an upsert into `customer_stats`, adding latency to the write path).

```sql
CREATE OR REPLACE FUNCTION sync_customer_stats()
RETURNS TRIGGER AS $$
BEGIN
  INSERT INTO customer_stats (customer_id, order_count, total_spent)
  VALUES (NEW.customer_id, 1, NEW.total)
  ON CONFLICT (customer_id) DO UPDATE SET
    order_count = customer_stats.order_count + 1,
    total_spent = customer_stats.total_spent + NEW.total,
    updated_at  = NOW();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_orders_sync_stats
AFTER INSERT ON orders
FOR EACH ROW EXECUTE FUNCTION sync_customer_stats();
```

## Special Trigger Variables

PostgreSQL provides a set of special variables automatically available inside every trigger function. `TG_TABLE_NAME` contains the table name, enabling a single generic function to be attached to multiple tables. `TG_OP` contains the triggering operation (`'INSERT'`, `'UPDATE'`, `'DELETE'`, `'TRUNCATE'`). `NEW` is a record variable holding the row being inserted or updated — mutations to `NEW` in a `BEFORE` trigger are reflected in the final written row. `OLD` holds the pre-update row state and is only available in `UPDATE` and `DELETE` triggers.

```sql
-- Available inside trigger functions:
TG_TABLE_NAME  -- name of the table ('users', 'orders')
TG_OP          -- operation: 'INSERT', 'UPDATE', 'DELETE'
NEW            -- the new row (INSERT/UPDATE only)
OLD            -- the old row (UPDATE/DELETE only)
```

## Managing Triggers

Triggers are stored as database objects and can be listed, disabled, enabled, and dropped. `DISABLE TRIGGER` is extremely useful in data migration scenarios: when bulk-loading millions of rows into a table, disabling its audit triggers eliminates the overhead of millions of extra inserts into the audit log. After the migration, re-enable them with `ENABLE TRIGGER`. Always document which triggers are disabled during a migration window to avoid accidentally leaving audit coverage gaps in production.

```sql
-- List triggers
SELECT trigger_name, event_manipulation, event_object_table
FROM information_schema.triggers WHERE trigger_schema = 'public';

-- Disable/enable
ALTER TABLE users DISABLE TRIGGER trg_users_updated_at;
ALTER TABLE users ENABLE  TRIGGER trg_users_updated_at;

-- Drop
DROP TRIGGER IF EXISTS trg_users_updated_at ON users;
```

## Summary

- Triggers fire automatically on INSERT, UPDATE, or DELETE - you never call them directly
- Two steps: create a trigger function (returns TRIGGER), then attach it with CREATE TRIGGER
- BEFORE triggers can modify or cancel the operation; AFTER triggers are for side effects
- Common uses: `updated_at` automation, audit logs, slug generation, summary table maintenance
- Triggers add hidden behavior - always document them and use them sparingly
