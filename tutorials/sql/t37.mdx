## Physical Architecture: The Clustered Index and Page Fragmentation

A Primary Key is not just a logical constraint; it dictates the physical layout of the table on disk in many databases (e.g., MySQL InnoDB, SQL Server) via a **Clustered Index**.

### The Clustered Index (Sequential Disk I/O)

In a clustered architecture, the table *is* the B-Tree index. The rows are physically sorted on the disk pages according to the Primary Key. 
If your primary key is an auto-incrementing integer (`BIGSERIAL`), every new `INSERT` goes to the very end of the file. This creates perfect **Sequential I/O**. The disk head simply appends data, and B-Tree pages are filled to 100% capacity sequentially.

### The UUID Fragmentation Penalty

Many modern applications use UUIDs (Universally Unique Identifiers) like `123e4567-e89b-12d3-a456-426614174000` as the Primary Key. 

Because standard UUIDs are entirely random (UUIDv4), an `INSERT` cannot be appended sequentially. The database must traverse the B-Tree, locate a random 8KB disk page somewhere in the middle of the table, and squeeze the new row into it. 
If that page is full, the database must perform a **Page Split**: it allocates a new page, moves half the rows over, and updates the parent nodes. This causes massive **Random I/O**, disk fragmentation, and drastically degrades write throughput on high-volume systems.

**Architectural Standard**: If you must use a UUID for a clustered primary key, you must use a **Time-Sorted UUID** (like UUIDv7 or ULID), which monotonically increases over time, restoring the sequential disk insertion pattern.

## Primary Key

A primary key uniquely identifies each row in a table. Rules:
- Must be unique across all rows
- Cannot be NULL
- A table can have only one primary key (but it can span multiple columns)

```sql
-- Single column PK
CREATE TABLE users (
  id    BIGSERIAL PRIMARY KEY,
  email VARCHAR(255) NOT NULL
);

-- Named PK constraint
CREATE TABLE users (
  id    BIGSERIAL,
  email VARCHAR(255),
  CONSTRAINT pk_users PRIMARY KEY (id)
);

-- Add PK to existing table
ALTER TABLE users ADD PRIMARY KEY (id);
```

## Natural vs Surrogate Keys

**Surrogate key:** An artificial ID with no business meaning (SERIAL, UUID)

```sql
id BIGSERIAL PRIMARY KEY   -- purely for identification, no meaning
```

**Natural key:** A real-world attribute that happens to be unique

```sql
email VARCHAR(255) PRIMARY KEY   -- naturally unique
tax_id CHAR(15)    PRIMARY KEY   -- unique business identifier
```

**Which to use?**
- Surrogate keys are almost always better in practice
- Natural keys change (email addresses, tax IDs can be reassigned or updated)
- Surrogate keys are stable, short, and fast to index

## Foreign Key

A foreign key links a column to the primary key of another table. Enforces **referential integrity** - you can't reference a row that doesn't exist.

```sql
CREATE TABLE orders (
  id          BIGSERIAL PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES users(id),
  total       DECIMAL(10,2)
);

-- Explicit syntax with named constraint
CREATE TABLE orders (
  id          BIGSERIAL PRIMARY KEY,
  customer_id BIGINT NOT NULL,
  CONSTRAINT fk_orders_customer
    FOREIGN KEY (customer_id) REFERENCES users(id)
    ON DELETE CASCADE
    ON UPDATE CASCADE
);
```

### ON DELETE Behaviors

The `ON DELETE` clause defines what happens to child rows when a parent row is deleted. The choice has profound operational impact. `CASCADE` is convenient but dangerous: deleting a user cascades to delete all their orders, then all order items, potentially removing millions of rows in a chain reaction triggered by a single `DELETE` statement. `RESTRICT` / `NO ACTION` are safer defaults — they prevent accidental data destruction by requiring you to manually clean up children before deleting the parent. `SET NULL` is the right choice when the child-parent relationship is optional (e.g., deleting an employee who was a sales rep on some orders doesn't mean those orders should disappear).

```sql
ON DELETE CASCADE      -- delete child rows when parent is deleted
ON DELETE RESTRICT     -- prevent deletion if child rows exist (default, strictest)
ON DELETE SET NULL     -- set FK column to NULL when parent deleted
ON DELETE SET DEFAULT  -- set FK column to default value
ON DELETE NO ACTION    -- same as RESTRICT but checked at end of transaction
```

**Choosing the right behavior:**
- `CASCADE` - for dependent records that shouldn't exist without the parent (order_items → orders)
- `RESTRICT` - when deletion should be blocked (delete a user who has orders → error)
- `SET NULL` - for optional relationships (orders.sales_rep_id → employees: rep can leave, order stays)

## Composite Primary Key

A primary key across multiple columns - uniqueness is enforced on the combination.

```sql
-- Order items: one product per order (combination is unique, neither column alone is)
CREATE TABLE order_items (
  order_id   BIGINT REFERENCES orders(id),
  product_id BIGINT REFERENCES products(id),
  quantity   INT NOT NULL CHECK (quantity > 0),
  unit_price DECIMAL(10,2) NOT NULL,

  PRIMARY KEY (order_id, product_id)   -- composite PK
);

-- Cannot add the same product twice to the same order:
INSERT INTO order_items VALUES (1, 5, 2, 999);
INSERT INTO order_items VALUES (1, 5, 1, 999);  -- ❌ ERROR: duplicate key
```

## Composite Foreign Key

When referencing a table with a composite primary key, the foreign key must also be composite, referencing all columns of the target's primary key. This is most common in many-to-many junction tables and audit/discount tables that extend a composite-keyed entity. The columns in the `FOREIGN KEY (...)` list must match the *order* of the columns in the referenced `REFERENCES (...) (...)` list exactly.

```sql
-- Reference a composite PK
CREATE TABLE order_item_discounts (
  order_id    BIGINT,
  product_id  BIGINT,
  discount    DECIMAL(5,2),

  FOREIGN KEY (order_id, product_id) REFERENCES order_items(order_id, product_id)
);
```

## Unique Constraints vs Primary Keys

Both PRIMARY KEY and UNIQUE enforce uniqueness at the storage level, but they have key differences. A table can only have one PRIMARY KEY — it is the canonical row identifier, cannot be NULL, and is used as the default target for FOREIGN KEY references from other tables. A table can have many UNIQUE constraints — they enforce uniqueness on alternate columns (like `email` or `username`) and allow one NULL (since NULL is not equal to NULL, two NULL values do not violate uniqueness in most databases). Architecturally, always use surrogate integer keys as your PRIMARY KEY; reserve UNIQUE for natural key enforcement.

```sql
-- PRIMARY KEY: one per table, cannot be NULL, clustered index (usually)
id BIGSERIAL PRIMARY KEY

-- UNIQUE: multiple allowed per table, can be NULL (one NULL allowed per column in most DBs)
email VARCHAR(255) UNIQUE

-- Composite UNIQUE
UNIQUE (user_id, provider)   -- a user can have one account per OAuth provider
```

## Checking Constraints

`CHECK` constraints are the last line of defense at the database layer against invalid data. They execute on every `INSERT` and `UPDATE`, and the row is rejected if the constraint evaluates to FALSE. An important nuance: if a `CHECK` constraint evaluates to NULL (because it references a NULLable column and that column is NULL), the constraint *passes* — SQL's three-valued logic means NULL-producing conditions are treated as "we don't know it's false, so allow it". Always test your CHECK constraints with NULL inputs to ensure they behave as intended.

```sql
CREATE TABLE products (
  id       BIGSERIAL PRIMARY KEY,
  price    DECIMAL(10,2) CHECK (price >= 0),
  discount DECIMAL(5,2)  CHECK (discount BETWEEN 0 AND 100),
  stock    INT           CHECK (stock >= 0),
  status   VARCHAR(20)   CHECK (status IN ('active', 'inactive', 'discontinued'))
);

-- Named check constraint
CONSTRAINT chk_price_positive CHECK (price >= 0)
```

## Indexing Foreign Keys

Foreign key columns are frequently used in JOINs - always index them:

```sql
-- FK columns are not automatically indexed (in PostgreSQL)
-- Always add an index manually:
CREATE INDEX idx_orders_customer ON orders(customer_id);
CREATE INDEX idx_order_items_order ON order_items(order_id);
CREATE INDEX idx_order_items_product ON order_items(product_id);
```

## Summary

- Primary key: unique + not null identifier for each row; one per table
- Surrogate keys (BIGSERIAL, UUID) are preferred over natural keys - they don't change
- Foreign key: links to another table's PK, enforces referential integrity
- `ON DELETE CASCADE` for dependent records; `RESTRICT` to block deletion; `SET NULL` for optional relationships
- Composite PK: uniqueness enforced on the combination of multiple columns
- Always index foreign key columns - they're used in JOINs constantly
