## CTEs and Query Optimization: Materialization vs. Inlining

CTEs (`WITH` clauses) drastically improve the readability of complex SQL code. However, historically, they came with a massive hidden performance penalty due to how the query optimizer handled them.

### The Optimizer Boundary Problem

In older databases (e.g., PostgreSQL before version 12), a CTE acted as an **Optimizer Boundary**. The query planner was forced to **materialize** the CTE.

Materialization means the database executes the CTE completely, writes the result to a temporary, unindexed physical table in memory (or disk), and then executes the outer query against that temporary table.

**The hazard:** If your CTE generates 10 million rows, but your outer query has a `LIMIT 5` or a strict `WHERE` clause, the database still wastes time generating and buffering all 10 million rows because the outer query's filters cannot be pushed down into the CTE.

### CTE Inlining (Flattening)

Modern databases (PostgreSQL 12+, SQL Server, Snowflake) solve this via **CTE Inlining**. The query parser treats the CTE exactly like an inline subquery. During the AST generation phase, the planner "unpacks" the CTE and merges it into the main query graph.

This removes the optimizer boundary. The planner can now push outer `WHERE` conditions deep into the CTE logic, heavily utilizing indexes on the base tables and avoiding temporary materialization entirely.

### Forcing Materialization

Sometimes, you actually *want* materialization. If a CTE performs a very expensive computation (e.g., heavily aggregating millions of rows) and you reference that CTE 4 different times in your outer query, inlining is disastrous: the database will re-execute the expensive computation 4 separate times!

To prevent this, you can explicitly force materialization:
```sql
-- Force the database to execute this ONCE and cache it in memory
WITH expensive_cte AS MATERIALIZED (
  SELECT customer_id, SUM(total) FROM orders GROUP BY customer_id
)
SELECT ...
```

**Architectural Rule**: Treat CTEs as syntactic sugar that gets flattened by the engine. However, if a CTE is heavily reused in the main query, manually verify the execution plan (`EXPLAIN`) to ensure the database isn't redundantly recalculating it.

## What is a CTE?

A CTE (Common Table Expression) is a named temporary result set defined at the top of a query using `WITH`. It can be referenced like a table in the main query.

```sql
WITH cte_name AS (
  SELECT ...  -- your subquery
)
SELECT * FROM cte_name;
```

CTEs don't store data - they're just named subqueries. But they make complex queries dramatically more readable.

## Why Use CTEs Instead of Subqueries?

```sql
-- ❌ Nested subqueries: hard to read and debug
SELECT name FROM users
WHERE id IN (
  SELECT customer_id FROM orders
  WHERE total > (
    SELECT AVG(total) FROM orders
  )
);

-- ✅ CTE version: read top to bottom like a story
WITH avg_order AS (
  SELECT AVG(total) AS avg FROM orders
),
high_value_customers AS (
  SELECT customer_id FROM orders, avg_order
  WHERE total > avg_order.avg
)
SELECT name FROM users
WHERE id IN (SELECT customer_id FROM high_value_customers);
```

## Basic CTE

A CTE is syntactic sugar around a subquery, but with a crucial structural benefit: it is defined *before* the main `SELECT`, named at the point of definition, and referenced by that name in the query body. This "top-to-bottom" reading order matches how humans naturally reason about a problem: define your building blocks first, then compose them. Each CTE acts like a temporary named result that exists only for the duration of the query.

```sql
WITH active_users AS (
  SELECT id, name, email FROM users WHERE status = 'active'
)
SELECT * FROM active_users WHERE city = 'Mumbai';
```

## Multiple CTEs - Chain Them Together

Multiple CTEs allow you to decompose a complex query into named, sequential processing steps. Each CTE can reference the CTEs defined before it. This chained structure transforms a deeply nested, unreadable subquery pyramid into a series of clearly labeled transformation stages — identical in concept to defining intermediate variables in application code. From a performance perspective, most modern optimizers (PostgreSQL 12+, SQL Server, BigQuery) can inline non-recursive CTEs into the main query and optimize them as a unit.

```sql
WITH
-- Step 1: Get completed orders
completed_orders AS (
  SELECT customer_id, total, created_at
  FROM orders
  WHERE status = 'completed'
),
-- Step 2: Aggregate per customer
customer_totals AS (
  SELECT
    customer_id,
    COUNT(*)   AS order_count,
    SUM(total) AS total_spent
  FROM completed_orders
  GROUP BY customer_id
),
-- Step 3: Assign tiers
customer_tiers AS (
  SELECT *,
    CASE
      WHEN total_spent >= 100000 THEN 'Platinum'
      WHEN total_spent >= 50000  THEN 'Gold'
      WHEN total_spent >= 10000  THEN 'Silver'
      ELSE 'Bronze'
    END AS tier
  FROM customer_totals
)
-- Final: join back to get names
SELECT u.name, u.email, ct.order_count, ct.total_spent, ct.tier
FROM users u
JOIN customer_tiers ct ON u.id = ct.customer_id
ORDER BY ct.total_spent DESC;
```

## CTE vs Subquery - When to Use Which

| | Subquery | CTE |
|-|----------|-----|
| Readability | Gets messy when nested | Clean, linear flow |
| Reuse in same query | ❌ Must repeat | ✅ Reference by name |
| Recursive | ❌ No | ✅ Yes |
| Debugging | Hard to isolate | Easy to test each step |

**Rule of thumb:** Use a subquery for simple, one-off inline references. Use a CTE when:
- The logic is complex (more than one level of nesting)
- You need to reference the result multiple times
- You want to make the query readable and maintainable

## Recursive CTEs

A recursive CTE references itself - useful for hierarchical data like org charts, categories, and paths.

```sql
WITH RECURSIVE org_chart AS (
  -- Base case: top-level employees (no manager)
  SELECT id, name, manager_id, 1 AS level
  FROM employees
  WHERE manager_id IS NULL

  UNION ALL

  -- Recursive case: employees whose manager is already in the CTE
  SELECT e.id, e.name, e.manager_id, oc.level + 1
  FROM employees e
  JOIN org_chart oc ON e.manager_id = oc.id
)
SELECT
  REPEAT('  ', level - 1) || name AS indented_name,
  level
FROM org_chart
ORDER BY level, name;
```

### Number Series with Recursive CTE

Recursive CTEs can generate synthetic sequences of numbers or dates without any source table. The pattern is always the same: a base case providing the starting value, and a recursive case incrementing the value and re-querying the CTE with a termination condition. In PostgreSQL, `generate_series()` is the preferred tool for number and date sequences, but the recursive CTE is the ANSI-standard equivalent that works in all databases (SQL Server, MySQL 8+, SQLite).

```sql
-- Generate numbers 1 to 10
WITH RECURSIVE nums AS (
  SELECT 1 AS n
  UNION ALL
  SELECT n + 1 FROM nums WHERE n < 10
)
SELECT n FROM nums;
```

### Date Series (Alternative to generate_series)

Generating a complete date spine is critical for analytics queries that need to report metrics for every day, even days with no data. Without a date spine, a `GROUP BY DATE(created_at)` query silently omits days with zero events. The recursive date series CTE builds this spine portably across all databases that support recursive CTEs, making it the standard pattern in SQL Server, MySQL 8+, and environments where PostgreSQL's `generate_series()` is unavailable.

```sql
WITH RECURSIVE dates AS (
  SELECT '2024-01-01'::DATE AS d
  UNION ALL
  SELECT d + 1 FROM dates WHERE d < '2024-01-31'
)
SELECT d FROM dates;
```

## CTE for Readability in Reports

For complex analytical reports, CTEs serve as a form of inline documentation. The CTE names (`rep_sales`, `team_avg`, `ranked_reps`) communicate what each processing stage does before you even read the SQL. This makes the query self-documenting and dramatically reduces the onboarding time for new engineers who need to understand or modify the query. Always prefer descriptive CTE names over anonymous subqueries when the query will be maintained by a team.

```sql
/*
  Sales performance report
  Shows each rep's performance vs team average
*/
WITH
rep_sales AS (
  SELECT
    sales_rep_id,
    COUNT(*)   AS deals_closed,
    SUM(value) AS total_revenue
  FROM deals
  WHERE status = 'won'
    AND closed_at >= DATE_TRUNC('month', NOW())
  GROUP BY sales_rep_id
),
team_avg AS (
  SELECT
    AVG(total_revenue) AS avg_revenue,
    SUM(total_revenue) AS team_total
  FROM rep_sales
)
SELECT
  u.name              AS rep_name,
  rs.deals_closed,
  rs.total_revenue,
  ta.avg_revenue      AS team_avg,
  rs.total_revenue - ta.avg_revenue AS vs_avg,
  ROUND(rs.total_revenue * 100.0 / ta.team_total, 1) AS pct_of_team
FROM rep_sales rs
JOIN users u     ON rs.sales_rep_id = u.id
CROSS JOIN team_avg ta
ORDER BY rs.total_revenue DESC;
```

## Summary

- CTE = named temporary result set, defined with `WITH cte_name AS (...)`
- Makes complex queries readable by breaking them into named, logical steps
- Multiple CTEs are separated by commas, can reference previous CTEs
- Recursive CTEs reference themselves - used for hierarchies, number/date series
- CTEs don't persist after the query - they're just named subqueries
- Prefer CTEs over deeply nested subqueries for maintainability
