## Comments and Query Processing Internals

Comments in SQL are often thought of purely as documentation for humans, but understanding how the database engine handles them reveals how query parsing and optimization actually work.

### The Lexer and Abstract Syntax Tree (AST)

When you send a SQL string to the database, it doesn't execute the string directly. It goes through the **Lexer** and **Parser**:

1. **Lexer (Tokenizer)**: Scans the raw string character by character. When it encounters `--` or `/*`, it transitions into a "comment state" and simply discards all subsequent characters until the newline or `*/` is found. 
2. **Parser**: Takes the tokens (keywords, identifiers) produced by the Lexer and builds an **Abstract Syntax Tree (AST)**. 

Because the Lexer strips comments *before* the AST is built, comments have **zero performance impact** on execution time. The query planner never even knows they existed.

```sql
-- Query A:
SELECT * FROM users WHERE id = 1;

-- Query B:
/* 
   Author: DBA Team
   Purpose: Get user by ID for login flow
   Note: Do not remove this query
*/
SELECT * FROM users WHERE id = 1;

-- The database hashes the parsed AST (not the raw text) to check the plan cache.
-- Therefore, Query A and Query B resolve to the EXACT same cached execution plan instantly.
```

### Optimizer Hints: When Comments Aren't Ignored

There is one critical exception to the "comments are ignored" rule. Many databases (like MySQL and Oracle) use a special comment syntax to inject **Optimizer Hints**. 

Optimizer hints bypass the cost-based query planner and force the database to use a specific physical execution strategy.

```sql
-- MySQL / Oracle Optimizer Hint Syntax: /*+ ... */
-- The '+' tells the Lexer NOT to discard this comment, but pass it to the Optimizer.

-- Force the database to use a specific index (even if the optimizer thinks a full scan is better):
SELECT /*+ INDEX(users idx_users_email) */ name, email 
FROM users 
WHERE email = 'alice@example.com';

-- Force a Hash Join instead of a Nested Loop Join:
SELECT /*+ HASH_JOIN(u o) */ u.name, o.total
FROM users u
JOIN orders o ON u.id = o.customer_id;
```

**Interview insight** 🎯: Hints are considered an anti-pattern in modern database engineering (PostgreSQL actively refuses to support them natively). If you have to use a hint, it usually means your table statistics are out of date (`ANALYZE` hasn't run) or your query is written poorly. You should fix the underlying statistics rather than forcing a physical plan that might become terrible as the data grows.

## SQL Comments

Comments are ignored by the database engine - they exist to explain the code to humans.

### Single-Line Comments

```sql
-- This is a single-line comment
SELECT * FROM users; -- returns all users

-- Useful for quick notes
SELECT
  id,
  name,       -- customer's full name
  email,      -- primary contact
  -- phone,   -- temporarily excluded
  city
FROM users;
```

### Multi-Line Comments

```sql
/* This is a
   multi-line comment */

SELECT *
/*
  TODO: add pagination
  Author: Alice
  Date: 2024-06-15
*/
FROM orders;
```

## SQL Formatting Conventions

Well-formatted SQL is much easier to read, debug, and maintain. These conventions are widely used in professional settings.

### Capitalization

```sql
-- SQL keywords in UPPERCASE (common convention)
SELECT name, email
FROM users
WHERE status = 'active'
ORDER BY name;

-- Some teams prefer lowercase keywords (also valid)
select name, email
from users
where status = 'active'
order by name;
```

Most teams use UPPERCASE for SQL keywords. Be consistent within a project.

### One Clause Per Line

```sql
-- ❌ Hard to read
SELECT name, email, city FROM users WHERE status = 'active' AND age > 18 ORDER BY name LIMIT 10;

-- ✅ Easy to read
SELECT name, email, city
FROM users
WHERE status = 'active'
  AND age > 18
ORDER BY name
LIMIT 10;
```

### Indent Column Lists

```sql
-- ✅ Aligned columns - easy to add/remove/comment out
SELECT
  id,
  name,
  email,
  city,
  created_at
FROM users;

-- ✅ Align aliases for readability
SELECT
  u.id                AS user_id,
  u.name              AS customer_name,
  u.email             AS contact_email,
  COUNT(o.id)         AS order_count,
  SUM(o.total)        AS lifetime_value,
  MAX(o.created_at)   AS last_order_date
FROM users u
LEFT JOIN orders o ON u.id = o.customer_id
GROUP BY u.id, u.name, u.email;
```

### Subqueries and CTEs: Visual Execution Blocks

When you indent a subquery or a CTE, you are not just making it "look pretty". You are visually mapping the **Execution Blocks** that the Query Optimizer will construct. 

Just as the database parser builds an Abstract Syntax Tree (AST), the human brain builds a mental AST when reviewing a Pull Request. Proper indentation visually isolates optimizer boundaries (like CTE materialization steps), allowing the reviewer to instantly understand the query's dependency graph.

```sql
-- ✅ Clearly nested structure
SELECT *
FROM (
  SELECT
    customer_id,
    SUM(total) AS total_spent
  FROM orders
  WHERE status = 'completed'
  GROUP BY customer_id
) AS spending
WHERE total_spent > 10000;

-- ✅ CTEs - each one clearly separated
WITH active_users AS (
  SELECT id, name
  FROM users
  WHERE status = 'active'
),
user_orders AS (
  SELECT customer_id, COUNT(*) AS order_count
  FROM orders
  GROUP BY customer_id
)
SELECT
  u.name,
  COALESCE(uo.order_count, 0) AS orders
FROM active_users u
LEFT JOIN user_orders uo ON u.id = uo.customer_id;
```

### Trailing vs Leading Commas: The Version Control Impact

In data engineering, the debate between trailing and leading commas is not about aesthetics — it is entirely about **Version Control (Git) efficiency** and `git blame` accuracy.

```sql
-- Trailing commas (The standard)
SELECT
  name,
  email,
  city
FROM users;

-- Leading commas (easier to comment out a line)
SELECT
   name
  ,email
  ,city
FROM users;
```

**The Engineering Impact:**
If you use trailing commas and add a new column to the end of the `SELECT` list, you must modify the previous line to add a comma. Git registers this as a **2-line diff** (one modification, one addition). This corrupts `git blame` because the previous line's author appears to have modified the query, when they only added a comma.

If you use leading commas, adding a new column to the end of the list is a **1-line diff**. `git blame` perfectly preserves the author history of every column. However, leading commas break standard language tooling and are often rejected by automated formatters (like `sqlfluff`). Most modern data teams accept the trailing comma standard and rely on advanced IDEs to resolve `git blame` nuances.

### JOIN Formatting

```sql
-- ✅ Each JOIN on its own line, condition indented
SELECT
  u.name,
  p.name AS product,
  o.total,
  o.created_at
FROM orders o
  JOIN users    u  ON o.customer_id = u.id
  JOIN products p  ON o.product_id  = p.id
WHERE o.status = 'completed'
  AND o.created_at >= '2024-01-01';
```

### WHERE Conditions

```sql
-- ✅ Each condition on its own line, AND/OR at the start
SELECT *
FROM users
WHERE status = 'active'
  AND age BETWEEN 18 AND 35
  AND city IN ('Mumbai', 'Delhi')
  AND email IS NOT NULL;
```

## A Well-Formatted Real Query

```sql
/*
  Monthly revenue report
  - Only completed orders
  - Grouped by month
  - Last 12 months only
*/
SELECT
  DATE_TRUNC('month', o.created_at)::DATE   AS month,
  COUNT(DISTINCT o.id)                       AS total_orders,
  COUNT(DISTINCT o.customer_id)              AS unique_customers,
  SUM(o.total)                               AS revenue,
  ROUND(AVG(o.total), 2)                     AS avg_order_value,
  SUM(o.total) - LAG(SUM(o.total)) OVER (
    ORDER BY DATE_TRUNC('month', o.created_at)
  )                                          AS revenue_change
FROM orders o
WHERE
  o.status = 'completed'
  AND o.created_at >= NOW() - INTERVAL '12 months'
GROUP BY DATE_TRUNC('month', o.created_at)
ORDER BY month DESC;
```

## Summary

- Use `--` for single-line comments and `/* */` for multi-line
- Comment the WHY, not the WHAT - SQL is self-documenting for the what
- Put each SQL clause on its own line
- Indent column lists and subqueries
- Use UPPERCASE for SQL keywords (standard convention)
- Align column aliases for long SELECT lists
- Consistent formatting makes SQL easier to review, debug, and maintain
