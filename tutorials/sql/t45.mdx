## Architecture: Why Partitioning is Mandatory at Scale

Partitioning is a physical storage strategy designed to overcome the memory limits of **B-Tree Indexes**.

### The B-Tree Memory Bound

When a table reaches 100 million rows, its B-Tree index becomes massive (e.g., 10GB+). If the database's available RAM (`shared_buffers`) is only 8GB, the index no longer fits in memory. 
Every `INSERT` or `SELECT` forces the database to evict a page from RAM and read a new B-Tree page from the physical disk (Cache Thrashing). Performance falls off a cliff. 

By partitioning the table by month, you break the single 10GB B-Tree into twelve 800MB B-Trees. The active month's index stays permanently cached in RAM, restoring $O(\log N)$ memory-speed lookups.

### Partition Pruning (Planning vs Execution)

The Query Optimizer uses **Partition Pruning** to eliminate partitions. 
- **Static Pruning (Planning Time):** If you write `WHERE created_at = '2024-01-05'`, the planner immediately excludes 11 partitions before execution even begins.
- **Dynamic Pruning (Execution Time):** If you join a partitioned table (`orders.created_at = events.created_at`), the planner cannot know the dates in advance. Modern executors evaluate the join dynamically, pruning partitions on the fly as rows stream in.

### The Sharding Abstraction (Consistent Hashing)

While partitioning happens on one machine, **Sharding** distributes data across multiple independent database servers (horizontal scaling). 
To distribute data evenly without a centralized bottleneck, distributed databases (like Citus, Vitess, or Cassandra) use **Consistent Hashing**. They hash the Shard Key (e.g., `hash(user_id)`) to map it to a logical ring, which is then mapped to physical nodes. This ensures that when you add a new database node, only a fraction of the data needs to be rebalanced across the network.

## Partitioning

Partitioning splits a single large table into smaller physical pieces (partitions) while presenting them as one logical table. Queries that filter by the partition key only scan relevant partitions - dramatically reducing I/O.

```
orders table (logical - one table to query)
├── orders_2022  (physical partition - Jan-Dec 2022)
├── orders_2023  (physical partition - Jan-Dec 2023)
├── orders_2024  (physical partition - Jan-Dec 2024)
└── orders_default (catch-all)

Query: SELECT * FROM orders WHERE created_at >= '2024-01-01'
→ Scans only orders_2024 - skips 3 years of data!
```

## Range Partitioning (Most Common)

Range partitioning is the most widely deployed strategy for time-series data. In PostgreSQL, you define the parent table with `PARTITION BY RANGE (column)` and then create child tables, each responsible for a specific value range (e.g., one year per partition). The parent table is a logical routing layer — it contains no rows itself. When you `INSERT` a row, the database automatically routes it to the correct child partition based on the `created_at` value. You must create partitions in advance; rows that don't fit any partition are rejected with an error unless you define a default partition.

```sql
CREATE TABLE orders (
  id          BIGSERIAL,
  customer_id BIGINT,
  total       DECIMAL(10,2),
  created_at  TIMESTAMPTZ NOT NULL
) PARTITION BY RANGE (created_at);

-- Create partitions (one per year)
CREATE TABLE orders_2023 PARTITION OF orders
  FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');

CREATE TABLE orders_2024 PARTITION OF orders
  FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');

CREATE TABLE orders_2025 PARTITION OF orders
  FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');

-- Indexes on each partition
CREATE INDEX ON orders_2024 (customer_id);
CREATE INDEX ON orders_2025 (customer_id);
```

## List Partitioning

Partition by a discrete set of values:

```sql
CREATE TABLE users (
  id     BIGSERIAL,
  name   VARCHAR(100),
  region VARCHAR(50) NOT NULL
) PARTITION BY LIST (region);

CREATE TABLE users_india PARTITION OF users
  FOR VALUES IN ('Mumbai', 'Delhi', 'Bangalore', 'Pune');

CREATE TABLE users_us PARTITION OF users
  FOR VALUES IN ('New York', 'San Francisco', 'Chicago');

CREATE TABLE users_eu PARTITION OF users
  FOR VALUES IN ('London', 'Berlin', 'Paris');
```

## Hash Partitioning

Distributes rows evenly across N partitions using a hash function - useful when there's no natural range:

```sql
CREATE TABLE events (
  id      BIGSERIAL,
  user_id BIGINT,
  type    VARCHAR(50),
  created_at TIMESTAMPTZ
) PARTITION BY HASH (user_id);

CREATE TABLE events_0 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE events_1 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 1);
CREATE TABLE events_2 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 2);
CREATE TABLE events_3 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 3);
```

## Partition Management

One of the most operationally powerful features of partitioned tables is how they change the cost of data lifecycle management. To archive or delete an old year's worth of orders, instead of running `DELETE FROM orders WHERE created_at < '2022-01-01'` (which locks rows one-by-one and generates massive WAL), you `DROP TABLE orders_2021` — an instantaneous metadata operation. `DETACH PARTITION` is even better for archiving: it converts the partition back into a standalone table, keeping the data accessible without it being part of the main partitioned table anymore.

```sql
-- Add a new year's partition
CREATE TABLE orders_2026 PARTITION OF orders
  FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');

-- Archive: detach old partition (instant - no data moved)
ALTER TABLE orders DETACH PARTITION orders_2021;
-- orders_2021 still exists as a standalone table

-- Drop old partition (instant vs slow DELETE)
DROP TABLE orders_2021;
-- Much faster than: DELETE FROM orders WHERE created_at < '2022-01-01';

-- Check partition sizes
SELECT
  child.relname  AS partition,
  pg_size_pretty(pg_relation_size(child.oid)) AS size
FROM pg_inherits
JOIN pg_class parent ON pg_inherits.inhparent = parent.oid
JOIN pg_class child  ON pg_inherits.inhrelid  = child.oid
WHERE parent.relname = 'orders'
ORDER BY pg_relation_size(child.oid) DESC;
```

## Partition Pruning - The Key Benefit

Partition pruning is the query planner's ability to determine at plan time which partitions *cannot* contain rows matching the query's `WHERE` clause, and skip reading them entirely. For pruning to work, the `WHERE` clause must filter on the **partition key**. If you query by `customer_id` but the table is partitioned by `created_at`, the planner has no choice but to scan every partition. Always design your partition key to match your most frequent query pattern. Verify pruning is working with `EXPLAIN` and look for `"Partitions:"` in the output showing only a subset of partitions.

```sql
-- Always include the partition key in WHERE for pruning to work:
SELECT * FROM orders WHERE created_at >= '2024-01-01';
-- ✅ Scans only relevant partitions

SELECT * FROM orders WHERE customer_id = 101;
-- ❌ Scans ALL partitions (customer_id is not the partition key)

-- Verify pruning with EXPLAIN
EXPLAIN SELECT * FROM orders WHERE created_at = '2024-06-15';
-- Should show: "Partitions: orders_2024" (not all partitions)
```

## Sharding

Sharding splits data across multiple database servers (horizontal scaling). Unlike partitioning (one server, multiple files), sharding means multiple independent databases.

```
Shard 1 (DB Server 1): users with id 1 to 1,000,000
Shard 2 (DB Server 2): users with id 1,000,001 to 2,000,000
Shard 3 (DB Server 3): users with id 2,000,001 to 3,000,000
```

**Shard key selection:**
- High cardinality (many distinct values)
- Avoid hot spots (don't shard by date - all writes go to today's shard)
- Common choices: user_id, tenant_id, geographic region

**Trade-offs:**
- Cross-shard queries are expensive or impossible
- Transactions across shards require distributed transaction protocols
- Schema changes must be applied to every shard

## Partitioning vs Sharding

| | Partitioning | Sharding |
|-|-------------|---------|
| Servers | One database server | Multiple database servers |
| Transparency | Fully transparent | Application must route queries |
| Cross-partition queries | ✅ Possible (planner handles) | ❌ Complex, expensive |
| Scale type | Vertical (bigger server) | Horizontal (more servers) |
| Complexity | Low | High |
| Use when | Table > 100M rows | Single server maxed out |

## Summary

- Partitioning splits one large table into smaller physical pieces on one server
- Range: by date ranges - best for time-series data
- List: by discrete values - best for regions, categories
- Hash: even distribution - best when no natural range or list exists
- Always include the partition key in WHERE for partition pruning
- Drop old partitions instantly instead of slow DELETE
- Sharding = multiple database servers - much more complex, use only when one server isn't enough
