## The Physical B-Tree: Depth and the Write Penalty

When you create an index, the database allocates a completely separate data structure on disk, almost always a **B-Tree (Balanced Tree)**. Understanding the physical structure of the B-Tree is crucial for understanding its performance limits.

### Node Architecture and Logarithmic Depth

A B-Tree consists of 8KB disk pages organized hierarchically:
1. **Root Node:** The top page, cached permanently in RAM.
2. **Branch Nodes:** Internal routing pages that narrow down the search space.
3. **Leaf Nodes:** The bottom pages containing the actual indexed values and a physical pointer (Row ID or Heap TID) to the exact disk location of the row in the main table.

Because B-Trees have a massive branching factor (hundreds of keys per node), they are incredibly shallow. Even a table with 1 billion rows typically has a B-Tree depth of only 4 or 5 levels. 
**Lookup Time**: $O(\log_b N)$. To find a row in a 1-billion-row table, the engine only reads 4 or 5 disk pages. It is near-instantaneous.

### The Write Penalty (Index Amplification)

The devastating trade-off of indexes is the **Write Penalty**. 
If a table has 5 indexes, every single `INSERT` or `DELETE` statement must physically modify 6 different locations on disk (the main table + the 5 index structures). 
Worse, if you update an indexed column (e.g., `UPDATE users SET status = 'active'`), the database must delete the old entry from the `status` B-Tree and insert the new entry into a different leaf node, potentially triggering cascading B-Tree rebalancing operations.

**Architectural Rule**: Every index accelerates reads but exponentially penalizes writes. Heavily indexed tables will destroy database throughput during bulk inserts. In OLTP systems, audit and delete unused indexes relentlessly.

## What is an Index?

An index is a separate data structure that the database maintains alongside a table. It allows the database to find rows without scanning every row (a full table scan).

```
Without index: Scan all 10,000,000 rows → O(n)
With index:    Jump directly to matching rows → O(log n)
```

## Creating and Dropping Indexes

Creating an index in PostgreSQL does not block reads by default, but a standard `CREATE INDEX` takes a full table lock that blocks writes for the duration of the build. For production tables with millions of rows, use `CREATE INDEX CONCURRENTLY` — it takes significantly longer but builds the index without blocking inserts or updates. Indexes created with `UNIQUE` enforce uniqueness as a constraint at the storage level, equivalent to a `UNIQUE` constraint on the column.

```sql
-- Basic index
CREATE INDEX idx_users_email ON users(email);

-- Unique index (also enforces uniqueness)
CREATE UNIQUE INDEX idx_users_email ON users(email);

-- Composite index (multiple columns)
CREATE INDEX idx_orders_customer_date ON orders(customer_id, created_at DESC);

-- Drop
DROP INDEX idx_users_email;           -- PostgreSQL
DROP INDEX idx_users_email ON users;  -- MySQL
```

## B-Tree Index (Default)

B-Tree (Balanced Tree) is the default index type. It supports:
- Equality: `WHERE email = 'alice@email.com'`
- Range: `WHERE age BETWEEN 20 AND 30`
- Sorting: `ORDER BY created_at DESC`
- Prefix matching: `WHERE name LIKE 'Alice%'`

```sql
-- All of these use a B-Tree index efficiently:
WHERE email = 'x'
WHERE salary > 50000
WHERE created_at BETWEEN '2024-01-01' AND '2024-12-31'
WHERE name LIKE 'Ali%'     -- ✅ trailing wildcard only
WHERE name LIKE '%Ali'     -- ❌ leading wildcard cannot use index
```

## Hash Index

Only supports equality (`=`). Slightly faster than B-Tree for exact lookups, but cannot support range queries or sorting.

```sql
CREATE INDEX idx_sessions_token ON sessions USING HASH (token);
-- Only useful for: WHERE token = 'abc123'
-- Cannot use for: WHERE token > 'abc' or ORDER BY token
```

In practice, B-Tree is usually preferred even for equality - it's versatile and PostgreSQL optimizes it well.

## Composite Index - Column Order Matters

A composite index on `(customer_id, created_at)` physically sorts the B-Tree first by `customer_id`, then by `created_at` within each customer. This means the leftmost columns act as a prefix — queries filtering only on `customer_id` can use the index perfectly. Queries filtering only on `created_at` cannot, because the tree is not sorted by `created_at` at the top level. Always design composite indexes to match the access pattern of your most frequent queries, and put the column with the highest filter selectivity first to maximize rows eliminated per node traversal.

```sql
CREATE INDEX idx_orders_customer_date ON orders(customer_id, created_at);
```

A composite index can be used when the query filters on the **leftmost** columns:

```sql
WHERE customer_id = 101                              -- ✅ uses index (leftmost col)
WHERE customer_id = 101 AND created_at > '2024-01'  -- ✅ uses both columns
WHERE created_at > '2024-01'                         -- ❌ skips leftmost col
```

**Rule:** Design composite indexes to match your most common query patterns - most selective column first.

## Partial Index - Index a Subset of Rows

A partial index includes a `WHERE` clause that filters which rows are indexed. This is one of the most powerful and underused index types. If 90% of your users are `'inactive'`, a standard index on `email` wastes storage on those rows and forces the query planner to read them. A partial index with `WHERE status = 'active'` is dramatically smaller (only 10% of the rows), fits more of itself in RAM, and is faster to traverse. The planner will use it automatically when the query's `WHERE` clause is compatible with the index predicate.

```sql
-- Only index active users (if 90% are inactive, don't waste space on them)
CREATE INDEX idx_active_users ON users(email) WHERE status = 'active';

-- Query that benefits from this index:
SELECT * FROM users WHERE status = 'active' AND email = 'alice@email.com';

-- Pending orders index (only a small fraction of orders)
CREATE INDEX idx_pending_orders ON orders(created_at) WHERE status = 'pending';
```

Partial indexes are smaller and faster because they contain fewer rows.

## Covering Index (Include)

A covering index stores extra columns so the query can be answered from the index alone - no need to touch the main table.

```sql
-- Query: SELECT amount, order_date FROM orders WHERE customer_id = 101
-- Without covering index: index lookup → then fetch row from table for amount and order_date
-- With covering index: everything needed is in the index

CREATE INDEX idx_orders_covering
ON orders(customer_id)
INCLUDE (amount, created_at);   -- PostgreSQL 11+ INCLUDE syntax
-- Now: Index Only Scan - never touches the main table
```

## GIN Index - Full-Text Search, Arrays, JSONB

A B-Tree can only index simple scalar values (integers, strings, dates). A GIN (Generalized Inverted Index) index is designed for **composite values** — full-text documents, JSONB objects, and arrays — where a single row can contain multiple indexable elements. GIN shreds each value into individual lexemes (for text) or key-value pairs (for JSONB) and builds an inverted map from each element to the list of rows containing it, identical in structure to a search engine's index. This makes containment queries (`@>`) and full-text match queries (`@@`) extremely fast on large datasets.

```sql
-- Full-text search
CREATE INDEX idx_articles_fts ON articles USING GIN (to_tsvector('english', content));
SELECT * FROM articles WHERE to_tsvector('english', content) @@ to_tsquery('database');

-- JSONB fields
CREATE INDEX idx_users_metadata ON users USING GIN (metadata);
SELECT * FROM users WHERE metadata @> '{"city": "Mumbai"}';

-- Array contains
CREATE INDEX idx_products_tags ON products USING GIN (tags);
SELECT * FROM products WHERE tags @> ARRAY['wireless'];
```

## When to Add an Index

**Good candidates:**
- Columns used in `WHERE` clauses frequently
- Columns used in `JOIN` conditions (`ON u.id = o.customer_id`)
- Columns used in `ORDER BY` with a matching filter
- Foreign key columns (not auto-indexed in PostgreSQL)

**Bad candidates:**
- Low-cardinality columns (e.g., `status` with only 2 values - full scan may be faster)
- Very small tables (less than a few thousand rows - full scan is negligible)
- Columns that are rarely queried
- Tables with extremely high write rates (every write must update all indexes)

## Index Anti-Patterns

```sql
-- ❌ Function on column: index cannot be used
WHERE UPPER(email) = 'ALICE@EMAIL.COM'
-- ✅ Fix: store lowercase, or create a functional index
CREATE INDEX idx_users_email_lower ON users (LOWER(email));

-- ❌ Leading wildcard: index cannot be used
WHERE name LIKE '%Kumar'
-- ✅ Fix: reverse the string and index, or use full-text search

-- ❌ Implicit type conversion: prevents index use
WHERE customer_id = '101'   -- customer_id is INT, '101' is string
-- ✅ Fix: match the data type
WHERE customer_id = 101
```

## EXPLAIN - Verify Index Usage

After creating an index, always run `EXPLAIN ANALYZE` to verify the planner actually uses it. The planner may choose a sequential scan over an index scan if the table is small, if statistics are stale, or if it estimates that the index scan would actually read more disk pages than a sequential scan (this can happen for low-selectivity queries). If the index is being ignored, check: (1) whether the predicate is sargable, (2) whether statistics are fresh (`ANALYZE table_name`), and (3) whether `random_page_cost` is configured correctly for SSD vs HDD.

```sql
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'alice@email.com';

-- Good: "Index Scan using idx_users_email"
-- Bad: "Seq Scan on users (cost=0..180000 rows=1000000)"
```

## Summary

- B-Tree (default): equality, range, sorting, prefix LIKE - use for almost everything
- Hash: equality only - rarely needed, B-Tree usually better
- Composite: column order matters - put leftmost filter column first
- Partial: index subset of rows - great for status = 'pending' or similar
- Covering: include extra columns to enable Index Only Scans
- GIN: full-text search, arrays, JSONB containment queries
- Too many indexes slow down INSERT/UPDATE/DELETE - index strategically
