## Self Joins: Physical Execution and Recursion

A `SELF JOIN` is not a special physical operator in the database engine. It is simply a standard Nested Loop, Hash, or Merge Join where both the inner and outer relations happen to point to the same physical table on disk. 

### The Double Scan Penalty

When you perform a self join, the database is often forced to read the same table from disk twice simultaneously:

```sql
SELECT a.name, b.name 
FROM employees a JOIN employees b ON a.manager_id = b.id;
```

**Physical Execution:**
1. Scan `employees` to populate the build phase of a Hash Table (using `id` as the key).
2. Scan `employees` *again* to probe the hash table (using `manager_id`).

If the `employees` table is 10GB, this query requires reading 20GB of data from disk into the buffer pool.

**The Index Covering Optimization:**
To mitigate the double-scan penalty, you need a **Covering Index**. If you have an index on `(manager_id, name)` and `(id, name)`, the database can perform an *Index Only Scan* for both sides of the join. The engine reads the slim B-trees in memory rather than touching the massive physical heap pages, drastically reducing I/O.

### The Limits of Self Joins vs. Recursive CTEs

A self join hardcodes the depth of a hierarchy. `A JOIN B JOIN C` traverses exactly 3 levels. What if the hierarchy depth is unknown? 

To solve this, modern databases implement **Recursive CTEs** (Common Table Expressions). Under the hood, a recursive CTE uses a temporary memory spool (a working table):

```
WITH RECURSIVE org_chart AS (
  -- 1. ANCHOR MEMBER
  -- Executed exactly once. Result goes into the "Working Table" and "Result Table".
  SELECT id, manager_id FROM employees WHERE manager_id IS NULL
  
  UNION ALL
  
  -- 2. RECURSIVE MEMBER
  -- Executed repeatedly. Joins the base table against the CURRENT contents of the "Working Table".
  SELECT e.id, e.manager_id 
  FROM employees e JOIN org_chart w ON e.manager_id = w.id
)
```

**Physical execution of the Recursive Step:**
1. Join `employees` to the `Working Table`.
2. Take the output rows of that join and put them into an `Intermediate Table`.
3. Append the `Intermediate Table` to the final `Result Table`.
4. *Replace* the `Working Table` with the `Intermediate Table` (the new bottom layer of the tree).
5. Repeat until the join produces zero new rows.

Recursive CTEs are incredibly powerful but dangerous. If your hierarchy contains a circular reference (A manages B, B manages A), the working table will never empty, and the query will loop infinitely until it OOMs (Out Of Memory) or hits a statement timeout.

## What is a SELF JOIN?

A SELF JOIN joins a table with itself. The table appears twice in the query under different aliases - it's just a regular JOIN where both sides reference the same table.

**When do you need it?**
- Hierarchical data (employee-manager, category-parent)
- Comparing rows within the same table
- Finding pairs or relationships within one dataset

## Employee-Manager Hierarchy

The classic use case - an `employees` table where each employee has a `manager_id` pointing to another employee in the same table:

```
employees:
id | name     | manager_id
1  | CEO      | NULL
2  | Alice    | 1
3  | Bob      | 1
4  | Charlie  | 2
5  | Diana    | 2
```

```sql
-- Each employee with their manager's name
SELECT
  e.name  AS employee,
  m.name  AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;

-- Result:
-- CEO      | NULL    (no manager)
-- Alice    | CEO
-- Bob      | CEO
-- Charlie  | Alice
-- Diana    | Alice
```

We use `LEFT JOIN` (not INNER) so the CEO (whose `manager_id` is NULL) still appears.

## Three Levels Deep

A SELF JOIN can be chained to traverse multiple hierarchy levels: one alias for the employee, one for their direct manager, one for the manager's manager. Each additional level requires one more `LEFT JOIN` against the same table. This approach scales linearly with the number of levels you want to display but fails for unknown or arbitrary depth — you'd need to write a different query for an org chart that is 3 levels deep vs. 7 levels deep. This is exactly the limitation that recursive CTEs solve.

```sql
-- Employee, their manager, and their manager's manager
SELECT
  e.name   AS employee,
  m.name   AS manager,
  gm.name  AS grand_manager
FROM employees e
LEFT JOIN employees m  ON e.manager_id  = m.id
LEFT JOIN employees gm ON m.manager_id  = gm.id;
```

## Finding Pairs Within the Same Table

Self-joining a table with `a.id < b.id` is the canonical technique for generating **unordered pairs** — every combination of two rows in a group without duplicates. Without the `a.id < b.id` condition, the join would produce every ordered pair (A→B and B→A) plus every row paired with itself (A→A), resulting in N² rows instead of N*(N-1)/2. This pattern is used in similarity analysis ("which products are most alike?"), fraud detection ("which accounts share an IP?"), and recommender systems.

```sql
-- Find all pairs of products in the same category
SELECT
  a.name AS product_1,
  b.name AS product_2,
  a.category_id
FROM products a
JOIN products b
  ON  a.category_id = b.category_id
  AND a.id < b.id      -- prevents (A,B) and (B,A) duplicates and (A,A) self-pairs
ORDER BY a.category_id;
```

The `a.id < b.id` condition is crucial - without it you'd get every pair twice plus each product paired with itself.

## Comparing Rows - Orders Placed on the Same Day

This pattern extends the self-join pair-finding to time-windowed analysis: finding orders placed by the same customer on the same day. The `DATE(a.created_at) = DATE(b.created_at)` condition truncates the timestamp to date precision before comparing. The `a.id < b.id` guard again ensures each pair is returned exactly once. In fraud detection, this same pattern identifies suspicious duplicate transactions: same customer, same amount, same day.

```sql
-- Find pairs of orders by the same customer on the same day
SELECT
  a.id      AS order_1,
  b.id      AS order_2,
  a.customer_id,
  DATE(a.created_at) AS order_date
FROM orders a
JOIN orders b
  ON  a.customer_id = b.customer_id
  AND DATE(a.created_at) = DATE(b.created_at)
  AND a.id < b.id;
```

## Finding Consecutive Events

Detecting consecutive-day streaks requires joining each user's daily activity set with itself, offset by one day. The `b.order_date = a.order_date + INTERVAL '1 day'` condition acts as a date-adjacency predicate. A user appears in the result if and only if there exists at least one pair of consecutive dates in their order history. This produces the list of customers who placed orders on back-to-back days — a common input for streak-based loyalty programs and engagement scoring.

```sql
-- Find users who placed orders on consecutive days
WITH daily_orders AS (
  SELECT DISTINCT customer_id, DATE(created_at) AS order_date
  FROM orders
)
SELECT DISTINCT a.customer_id
FROM daily_orders a
JOIN daily_orders b
  ON  a.customer_id = b.customer_id
  AND b.order_date  = a.order_date + INTERVAL '1 day';
```

## Interview Question: How do you query a hierarchical table?

**Answer:** Use a SELF JOIN for shallow hierarchies (2-3 levels) or a recursive CTE for unlimited depth.

```sql
-- Shallow (2 levels): SELF JOIN
SELECT e.name AS employee, m.name AS manager
FROM employees e LEFT JOIN employees m ON e.manager_id = m.id;

-- Deep (unlimited levels): Recursive CTE
WITH RECURSIVE org AS (
  SELECT id, name, manager_id, 0 AS level
  FROM employees WHERE manager_id IS NULL  -- root

  UNION ALL

  SELECT e.id, e.name, e.manager_id, o.level + 1
  FROM employees e
  JOIN org o ON e.manager_id = o.id        -- recursive step
)
SELECT * FROM org ORDER BY level, name;
```

## Summary

- A SELF JOIN joins a table to itself using two different aliases
- Required for hierarchical data (employee-manager, category tree)
- Use `a.id < b.id` when finding pairs to avoid duplicates
- Use LEFT JOIN when some rows have no parent (root of hierarchy)
- For unlimited-depth hierarchies, use a recursive CTE instead
