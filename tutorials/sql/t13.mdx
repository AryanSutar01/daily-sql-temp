## How JOINs Actually Execute: Physical Join Algorithms

When you write an `INNER JOIN`, you are describing the *logical* result you want. The database optimizer translates this into a *physical* execution plan. Understanding the three physical join algorithms is mandatory for senior engineering interviews and database performance tuning.

### 1. Nested Loop Join (NLJ)
The simplest algorithm. For every row in Table A, the database scans Table B to find matches.
```
FOREACH row_a IN table_a:
  FOREACH row_b IN table_b:
    IF row_a.id == row_b.customer_id THEN EMIT

Cost: O(N * M) 
```
**When is it used?** 
NLJ is terrible for large tables, but it is **extremely fast if the inner table is indexed**. If `table_b.customer_id` has an index, the inner loop becomes an O(log M) B-tree lookup instead of a full scan. The optimizer chooses NLJ when joining a small table to a large indexed table.

### 2. Hash Join
The go-to algorithm for joining large, unindexed datasets.
```
Phase 1: Build Phase
  Scan the smaller table (Table A)
  Build an in-memory Hash Table using the join key (row_a.id)

Phase 2: Probe Phase
  Scan the larger table (Table B)
  For each row, hash row_b.customer_id and look it up in the Hash Table
  IF match found THEN EMIT

Cost: O(N + M) reads, plus O(N) memory for the hash table.
```
**When is it used?**
When both tables are large and neither has a usable index on the join key. 
**The danger:** If the Hash Table exceeds `work_mem`, it spills to disk (Grace Hash Join), causing massive I/O bottlenecks.

### 3. Sort-Merge Join
Used when both tables are already sorted by the join key (or if sorting them in memory is cheaper than building a hash table).
```
Phase 1: Sort
  Sort Table A by join key
  Sort Table B by join key (Skip if an index already provides sorted order!)

Phase 2: Merge
  Iterate through both sorted lists simultaneously (like zipping a zipper)
  IF row_a.id == row_b.customer_id THEN EMIT

Cost: O(N log N + M log M) for sorting, plus O(N + M) for merging.
```
**When is it used?**
When joining massive tables that don't fit in memory (so Hash Join would spill to disk), or when the optimizer needs the final output to be sorted anyway (e.g., you have an `ORDER BY` on the join key).

### The Optimizer's Job
The query planner uses table statistics (row counts, histograms) to estimate the cost of all three algorithms and picks the cheapest one. **Missing indexes or outdated statistics will cause the optimizer to choose the wrong algorithm**, leading to queries that take hours instead of milliseconds.

## What is an INNER JOIN?

An INNER JOIN returns rows that have **matching values in both tables**. If a row in either table has no match in the other, it is excluded from the result.

```sql
SELECT columns
FROM table_a
INNER JOIN table_b ON table_a.key = table_b.key;

-- JOIN = INNER JOIN (shorthand, most common)
SELECT columns
FROM table_a
JOIN table_b ON table_a.key = table_b.key;
```

## Basic Example

```
users:                    orders:
id | name                 id | customer_id | total
1  | Alice                1  | 1           | 500
2  | Bob                  2  | 1           | 300
3  | Charlie              3  | 2           | 750
                          4  | 99          | 200  ← customer 99 doesn't exist
```

```sql
SELECT u.name, o.total
FROM users u
JOIN orders o ON u.id = o.customer_id;

-- Result:
-- Alice  | 500
-- Alice  | 300
-- Bob    | 750
-- Charlie is excluded (no orders)
-- order #4 is excluded (customer 99 doesn't exist in users)
```

## Table Aliases - Always Use Them

```sql
-- Without aliases: verbose and error-prone
SELECT users.name, users.email, orders.total, orders.created_at
FROM users
JOIN orders ON users.id = orders.customer_id;

-- With aliases: clean and readable
SELECT u.name, u.email, o.total, o.created_at
FROM users u
JOIN orders o ON u.id = o.customer_id;
```

## JOIN on Multiple Conditions

```sql
-- Join on multiple columns
SELECT *
FROM order_items oi
JOIN orders o ON oi.order_id = o.id
             AND o.status = 'completed';  -- additional condition in ON

-- Alternative: put extra condition in WHERE
SELECT *
FROM order_items oi
JOIN orders o ON oi.order_id = o.id
WHERE o.status = 'completed';
```

**ON vs WHERE for JOIN conditions:**
- Conditions in `ON` are evaluated during the join
- Conditions in `WHERE` are evaluated after the join
- For INNER JOIN they produce the same result - for OUTER JOINs they behave differently

## Joining Three or More Tables

```sql
SELECT
  u.name        AS customer,
  p.name        AS product,
  oi.quantity,
  oi.unit_price,
  o.created_at  AS order_date
FROM orders o
JOIN users      u  ON o.customer_id  = u.id
JOIN order_items oi ON o.id          = oi.order_id
JOIN products   p  ON oi.product_id  = p.id
WHERE o.status = 'completed'
  AND o.created_at >= '2024-01-01'
ORDER BY o.created_at DESC;
```

**Join order tip:** Start from the most central table (often the fact table like `orders`) and JOIN outward to dimension tables.

## JOIN with Aggregation

```sql
-- Total revenue per customer with their name
SELECT
  u.id,
  u.name,
  u.email,
  COUNT(o.id)        AS order_count,
  SUM(o.total)       AS total_spent,
  MAX(o.created_at)  AS last_order
FROM users u
JOIN orders o ON u.id = o.customer_id
WHERE o.status = 'completed'
GROUP BY u.id, u.name, u.email
ORDER BY total_spent DESC;
```

## Common Interview Question: ON vs WHERE

```sql
-- For INNER JOIN, these two produce the same result:

-- Filter in ON:
SELECT u.name, o.total
FROM users u
JOIN orders o ON u.id = o.customer_id AND o.status = 'completed';

-- Filter in WHERE:
SELECT u.name, o.total
FROM users u
JOIN orders o ON u.id = o.customer_id
WHERE o.status = 'completed';
```

But for LEFT JOIN they behave completely differently (covered in the LEFT JOIN tutorial).

## Avoiding Duplicate Rows

A common pitfall: joining to a one-to-many table multiplies rows.

```sql
-- users has 1 row per user
-- orders has N rows per user
-- This produces one output row per order, not per user
SELECT u.name, o.total
FROM users u
JOIN orders o ON u.id = o.customer_id;
-- If Alice has 5 orders → Alice appears 5 times

-- To get one row per user, aggregate:
SELECT u.name, COUNT(o.id) AS orders, SUM(o.total) AS spent
FROM users u
JOIN orders o ON u.id = o.customer_id
GROUP BY u.name;
```

## Summary

- INNER JOIN (or just JOIN) returns only rows with matches in both tables
- Rows with no matching row in the other table are excluded
- Always use table aliases (u, o, p) for readability
- Start joins from the central table and join outward
- INNER JOIN + WHERE = same result as INNER JOIN + ON for the filter condition
- Watch out for row multiplication when joining one-to-many tables
