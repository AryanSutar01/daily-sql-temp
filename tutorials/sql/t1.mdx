## How a SQL Query Engine Actually Works

Before writing a single query, understanding what happens inside the database engine when you hit "Execute" gives you an enormous advantage — both for writing efficient SQL and for answering architecture questions in interviews.

### The 5-Phase Query Processing Pipeline

```
Your SQL text:
  SELECT name FROM users WHERE city = 'Mumbai';

Phase 1: LEXER + PARSER
  Input text → Token stream → Abstract Syntax Tree (AST)
  "SELECT" → keyword token
  "name"   → identifier token
  "FROM"   → keyword token
  "users"  → identifier token
  Parser checks SQL grammar: is the syntax valid?
  If not: SyntaxError (before any data is touched)

Phase 2: SEMANTIC ANALYSIS (Binder / Analyzer)
  AST + Schema Catalog → Annotated AST
  - Does table "users" exist? → lookup system catalog
  - Does column "name" exist in "users"? → resolve type: VARCHAR(100)
  - Does column "city" exist? → resolve type: VARCHAR(100)
  - Check data type compatibility: 'Mumbai' (string) vs VARCHAR → OK
  If not: "column does not exist" error

Phase 3: QUERY OPTIMIZER
  Annotated AST → Logical Plan → Physical Plan
  The most important phase for performance!
  
  Rule-based optimizations (always applied):
    - Predicate pushdown: apply WHERE as early as possible
    - Column pruning: only read needed columns
    - Constant folding: evaluate WHERE 1=1 → remove condition
  
  Cost-based optimizations (uses table statistics):
    - Choose: Sequential Scan vs Index Scan
    - For JOINs: Nested Loop vs Hash Join vs Merge Join
    - JOIN ordering: which table to probe first?
  
  Statistics used: row count, column cardinality, histogram of values
  Updated by: ANALYZE (PostgreSQL), ANALYZE TABLE (MySQL)

Phase 4: PHYSICAL PLAN GENERATION
  Logical Plan → Executable Physical Plan
  A tree of physical operators:
    IndexScan(users, idx_city, city='Mumbai')
      → Filter(city = 'Mumbai')
        → Project(name)

Phase 5: EXECUTION ENGINE
  Physical Plan → Result rows
  Operators execute in a pipeline (pull model):
    - IndexScan reads rows from storage via buffer pool
    - Filter evaluates each row's WHERE condition
    - Project selects only the "name" column
    - Returns rows to client
```

### The Query Optimizer: Why It Changes Everything

The optimizer is why two equivalent SQL statements can have **1000x different performance**:

```sql
-- Both return the same result, but very different execution:

-- Query A: may use an index (fast for small result set)
SELECT * FROM orders WHERE customer_id = 42;

-- Query B: function on column prevents index use!
SELECT * FROM orders WHERE YEAR(created_at) = 2024;
-- Optimizer cannot use an index on created_at for this
-- Must read EVERY row and apply the function → full table scan

-- Query B rewritten to allow index use:
SELECT * FROM orders
WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01';
```

**Interview insight** 🎯: Never wrap an indexed column in a function in WHERE. The optimizer cannot use the index — it must evaluate the function for every row (full table scan).

### Codd's Rules: The Theoretical Foundation

In 1970, E.F. Codd at IBM defined the **relational model**. His 12 rules (actually 13, numbered 0-12) define what it truly means to be a relational database:

- **Rule 1**: All data must be representable as tables (the **information rule**)
- **Rule 4**: Active catalog (data dictionary) accessible via SQL — you can query `information_schema.tables` like a regular table
- **Rule 6**: All views that are theoretically updatable must be updatable by the system
- **Rule 8**: Physical data independence — how data is stored should be invisible to queries
- **Rule 9**: Logical data independence — adding columns shouldn't break existing queries

Understanding Codd's rules explains why SQL is designed the way it is — and why certain NoSQL systems technically aren't "relational" even if they support SQL-like syntax.

## What is SQL?

SQL - pronounced "S-Q-L" or "sequel" - stands for **Structured Query Language**. It is the standard language used to communicate with relational databases. With SQL you can:

- **Create** tables and databases
- **Insert** new data
- **Query** (read) data
- **Update** existing data
- **Delete** data
- **Control** who has access to what

SQL was developed at IBM in the early 1970s, became an ANSI standard in 1986, and today powers nearly every application that stores structured data - from banking systems to e-commerce platforms to analytics dashboards.

## What is a Database?

A **database** is an organized collection of structured data stored electronically. Think of it as a digital filing cabinet where everything is indexed and retrievable.

```
Without a database:                With a database:
- Files scattered everywhere       - Centralized storage
- No easy search                   - Query in milliseconds
- No relationships                 - Relationships between data
- No concurrent access             - Multiple users simultaneously
- Data duplication everywhere      - Data stored once, referenced everywhere
```

## What is a RDBMS?

A **Relational Database Management System (RDBMS)** is the software that:
1. Stores your data in structured tables
2. Manages how that data is accessed and modified
3. Enforces rules (constraints) on the data
4. Handles multiple users accessing data simultaneously
5. Ensures data is not lost or corrupted

## The Relational Model

"Relational" means data is organized into **tables** that can be **related** to each other through shared values.

### Tables

A table stores data about one type of thing (users, products, orders). It has:
- **Columns** (also called fields or attributes) - define what data is stored
- **Rows** (also called records or tuples) - individual data entries

```
users table:
+----+----------+---------------------+--------+
| id | name     | email               | city   |
+----+----------+---------------------+--------+
| 1  | Alice    | alice@email.com     | Mumbai |
| 2  | Bob      | bob@email.com       | Delhi  |
| 3  | Charlie  | charlie@email.com   | Pune   |
+----+----------+---------------------+--------+
```

### Relationships Between Tables

Tables relate to each other through **keys**:

```
users table          orders table
+---------+          +----+-------------+--------+
| id (PK) |←----+    | id | customer_id | amount |
| name    |     +----| 1  | 1           | 500    |
| email   |          | 2  | 1           | 300    |
+---------+          | 3  | 2           | 750    |
                     +----+-------------+--------+
                              ↑
                         Foreign Key → references users.id
```

## Key Concepts

### Primary Key (PK)
A column (or combination of columns) that **uniquely identifies each row**. No two rows can have the same primary key. Cannot be NULL.

```sql
CREATE TABLE users (
  id    INT PRIMARY KEY,    -- unique, not null
  name  VARCHAR(100),
  email VARCHAR(255)
);
```

### Foreign Key (FK)
A column that **references the primary key of another table**. Creates the "relationship" in relational database.

```sql
CREATE TABLE orders (
  id          INT PRIMARY KEY,
  customer_id INT REFERENCES users(id),  -- FK → users.id
  amount      DECIMAL(10,2)
);
```

### Schema
The **structure** of a database - all its tables, columns, data types, and relationships. It's like the blueprint of the database.

## How SQL Works with RDBMS

When you write a SQL query, here's what happens:

```
1. You write SQL:
   SELECT name FROM users WHERE city = 'Mumbai';

2. SQL Parser checks syntax

3. Query Planner figures out the most efficient way to fetch the data

4. Query Executor accesses the data files on disk

5. Results returned to you
       ↓
   +----------+
   | name     |
   +----------+
   | Alice    |
   +----------+
```

## SQL vs NoSQL

A common interview question: *"When would you use SQL vs NoSQL?"*

| Feature | SQL (Relational) | NoSQL |
|---------|-----------------|-------|
| Data structure | Tables (rows & columns) | Documents, Key-Value, Graph |
| Schema | Fixed, defined upfront | Flexible, dynamic |
| Relationships | Strong, enforced by FKs | Application handles relationships |
| Consistency | ACID compliant | Often eventual consistency |
| Query language | Standardized SQL | Varies (MongoDB query, Redis commands) |
| Best for | Structured data, complex queries, transactions | Unstructured data, massive scale, rapid iteration |
| Examples | PostgreSQL, MySQL, SQLite | MongoDB, Redis, DynamoDB, Cassandra |

**Use SQL when:** data is structured, relationships matter, consistency is critical (banking, e-commerce, user accounts)

**Use NoSQL when:** schema changes frequently, data is unstructured (logs, social media), you need massive horizontal scale

## Summary

- SQL is the standard language for interacting with relational databases
- An RDBMS stores data in tables with rows and columns
- Tables relate to each other through primary and foreign keys
- The most popular RDBMS are PostgreSQL, MySQL, and SQLite
- SQL is used everywhere - from small apps to systems handling billions of rows
