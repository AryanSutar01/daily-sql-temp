## Physical Storage: JSONB, GIN, and TOAST

Storing unstructured data in a relational database requires specialized physical storage mechanisms to maintain performance.

### Binary Parsing (JSON vs JSONB)

If you use the standard `JSON` data type, the database stores the exact raw text you inserted (including whitespace). When you query `attributes->'color'`, the engine must physically parse the entire JSON string at runtime. For millions of rows, this CPU overhead is crippling.

**JSONB (JSON Binary)** completely eliminates this overhead. During `INSERT`, the database pre-parses the JSON string, strips whitespace, and converts it into a custom binary format. Keys are hashed and stored in a binary tree structure inside the column. When you query `attributes->'color'`, the engine does a $O(1)$ binary lookup, bypassing the parser entirely.

### GIN Indexes and Containment

You cannot build a standard B-Tree index on a JSONB column because B-Trees sort single values, not nested graphs. Instead, databases use a **GIN (Generalized Inverted Index)**.
Similar to how a search engine indexes the web, a GIN index shreds the JSON document into individual key-value pairs (e.g., `"color": "red"`) and maps each pair to a list of Row IDs that contain it. This is why GIN indexes excel at the `@>` (containment) operator.

### TOAST: Out-of-Line Storage

A standard PostgreSQL disk page is 8KB. What happens if you insert a 5MB JSON API response into a column? 
The database uses a system called **TOAST (The Oversized-Attribute Storage Technique)**. It compresses the 5MB JSON object, chops it into 2KB chunks, and stores those chunks in a completely separate, hidden TOAST table. The main table row simply stores a tiny pointer to the TOAST chunks. 

**Architectural Rule**: Because of TOAST, `SELECT id FROM table` is lightning fast even if the table has massive JSON columns. However, `SELECT *` forces the database to follow the TOAST pointers, decompress the chunks, and reassemble the JSON for every row, triggering massive I/O amplification.

## Why JSON in SQL?

Sometimes data doesn't fit neatly into columns - user preferences, product attributes, API responses, event metadata. JSON columns let you store flexible data alongside structured relational data.

```sql
-- Instead of 10 nullable columns for rarely-used attributes:
ALTER TABLE products ADD COLUMN attributes JSONB;
-- Now store any attributes: {"color": "red", "weight": "2kg", "warranty": "1year"}
```

## JSONB vs JSON (PostgreSQL)

| | JSON | JSONB |
|-|------|-------|
| Storage | Text (as-is) | Binary (parsed, compressed) |
| Indexing | ❌ No | ✅ Yes (GIN index) |
| Query speed | Slower (re-parse each time) | Faster |
| Key order preserved | ✅ Yes | ❌ No |
| Duplicate keys | ✅ Kept | ❌ Last wins |

**Always use JSONB.** JSON is rarely the right choice.

## Inserting JSON Data

When inserting JSON into a JSONB column, PostgreSQL expects a well-formed JSON string. The engine will parse the string, compress it into the binary format, and sort the keys. Alternatively, you can use `jsonb_build_object()` to construct the JSON programmatically from relational columns or variables. This function is extremely useful when converting relational rows into JSON APIs directly inside the database layer, bypassing the need for ORM serialization.

```sql
-- Insert a JSONB column
INSERT INTO users (name, settings) VALUES
('Alice', '{"theme": "dark", "lang": "en", "notifications": true}'),
('Bob',   '{"theme": "light", "lang": "hi", "notifications": false, "timezone": "Asia/Kolkata"}');

-- Or use jsonb_build_object
INSERT INTO products (name, attributes) VALUES (
  'Laptop',
  jsonb_build_object(
    'brand', 'Dell',
    'ram_gb', 16,
    'storage_gb', 512,
    'color', 'silver',
    'tags', ARRAY['laptop', 'electronics']
  )
);
```

## Querying JSON Fields

Accessing JSON data requires understanding the difference between the `->` and `->>` operators. The `->` operator returns a JSONB object — useful when the target value is a nested JSON object or array that you intend to drill further into. The `->>` operator extracts the target value and casts it to native SQL `TEXT`. You must use `->>` when comparing against string literals in a `WHERE` clause, otherwise you will get a type mismatch error between `jsonb` and `text`.

```sql
-- -> returns JSON value (keeps JSON type)
SELECT settings -> 'theme' FROM users;           -- "dark" (with quotes - JSON string)

-- ->> returns text value (extracts as text)
SELECT settings ->> 'theme' FROM users;          -- dark (no quotes - plain text)

-- Nested access
SELECT settings -> 'address' ->> 'city' FROM users;

-- In WHERE clause
SELECT * FROM users WHERE settings ->> 'theme' = 'dark';
SELECT * FROM users WHERE settings -> 'notifications' = 'true';

-- Existence operator: does key exist?
SELECT * FROM users WHERE settings ? 'timezone';

-- Contains operator: does JSON contain this subset?
SELECT * FROM users WHERE settings @> '{"theme": "dark"}';
SELECT * FROM products WHERE attributes @> '{"brand": "Dell"}';
```

## JSON Array Operations

JSONB columns can store arrays of objects, which is tempting for representing one-to-many relationships (e.g., an order's line items). PostgreSQL provides several functions for working with these arrays: `jsonb_array_length()` counts elements, and `jsonb_array_elements()` is a set-returning function that "unnests" the array, producing one row per array element. Used with a `LATERAL` join, this transforms a single row containing a JSON array into a properly normalized set of rows — effectively joining structured and semi-structured data in a single query.

```sql
-- Array of objects stored in JSONB
INSERT INTO orders (customer_id, items) VALUES (
  1,
  '[{"product_id": 5, "qty": 2}, {"product_id": 8, "qty": 1}]'::JSONB
);

-- Get array element by index (0-based)
SELECT items -> 0 FROM orders;                      -- {"product_id": 5, "qty": 2}
SELECT items -> 0 ->> 'product_id' FROM orders;    -- "5"

-- Array length
SELECT jsonb_array_length(items) AS item_count FROM orders;

-- Expand array to rows
SELECT
  order_id,
  item ->> 'product_id' AS product_id,
  item ->> 'qty' AS qty
FROM orders,
LATERAL jsonb_array_elements(items) AS item;
```

## Modifying JSON Data

JSONB values are immutable in PostgreSQL — you cannot mutate a specific key in place at the storage level. Instead, `jsonb_set(target, path, new_value)` returns a *new* JSONB value with the modification applied. When used in an `UPDATE SET` clause, the database writes the new complete value back to the row. The `||` (concatenation/merge) operator is the fast shortcut for adding or overriding top-level keys, while the `-` operator removes a key. For deeply nested modifications, `jsonb_set` is the correct tool as it accepts a path array like `'{address, city}'`.

```sql
-- Set a key (returns new JSONB - doesn't modify in place)
SELECT settings || '{"theme": "blue"}' FROM users;    -- merge/override
SELECT jsonb_set(settings, '{theme}', '"blue"') FROM users;

-- Update in place
UPDATE users
SET settings = jsonb_set(settings, '{theme}', '"blue"')
WHERE id = 1;

-- Add a new key
UPDATE users
SET settings = settings || '{"premium": true}'::JSONB
WHERE id = 1;

-- Remove a key
UPDATE users
SET settings = settings - 'old_key'
WHERE id = 1;
```

## Indexing JSON (GIN Index)

Without an index, any query filtering on a JSONB field (`WHERE settings->>'theme' = 'dark'`) forces a full sequential scan, evaluating every row's JSONB binary tree. A `GIN` (Generalized Inverted Index) indexes the entire JSONB document — it extracts every key-value pair from every row and builds a lookup structure. This makes `@>` (containment) and `?` (key existence) queries very fast. For simple equality checks on a known key path, an expression index (`(settings->>'theme')`) is even more efficient as it builds a standard B-Tree over that single extracted value.

```sql
-- GIN index enables fast containment queries
CREATE INDEX idx_users_settings ON users USING GIN (settings);

-- These queries now use the index:
SELECT * FROM users WHERE settings @> '{"theme": "dark"}';
SELECT * FROM users WHERE settings ? 'timezone';

-- Index a specific JSON path (for equality queries)
CREATE INDEX idx_users_theme ON users ((settings ->> 'theme'));
SELECT * FROM users WHERE settings ->> 'theme' = 'dark';  -- uses index
```

## Aggregating JSON

SQL's `jsonb_agg()` is a powerful aggregation function that collects a set of rows into a JSON array — perfect for building nested API responses directly in SQL, eliminating the need for application-layer data shaping. `jsonb_object_agg(key, value)` constructs a key-value JSON object from rows. These functions are especially useful in reporting APIs and GraphQL backends where you need to send a single structured JSON object, not dozens of flat rows, to the client.

```sql
-- Aggregate rows into a JSON array
SELECT jsonb_agg(jsonb_build_object('name', name, 'email', email))
FROM users WHERE city = 'Mumbai';

-- Aggregate rows into a JSON object (key-value pairs)
SELECT jsonb_object_agg(id, name) FROM users;
-- {"1": "Alice", "2": "Bob", ...}

-- Build a nested JSON report
SELECT jsonb_build_object(
  'total_orders', COUNT(*),
  'total_revenue', SUM(total),
  'avg_order', ROUND(AVG(total), 2),
  'by_status', jsonb_object_agg(status, status_count)
) AS report
FROM (
  SELECT status, COUNT(*) AS status_count, SUM(total), AVG(total)
  FROM orders GROUP BY status
) t;
```

## MySQL JSON

MySQL 5.7+ added JSON support, but it uses a completely different syntax from PostgreSQL. Instead of the `->` and `->>` operators, MySQL uses the `JSON_EXTRACT(column, '$.path')` function syntax, where `$` represents the document root. The `->>`shorthand is available in MySQL 5.7.13+ as equivalent to `JSON_UNQUOTE(JSON_EXTRACT(...))`. MySQL's JSON type stores data as a validated, binary-optimized format (similar to JSONB), but it lacks PostgreSQL's GIN index support — use generated virtual columns with standard indexes as a workaround.

```sql
-- MySQL 5.7+ has JSON support
CREATE TABLE users (
  id       INT AUTO_INCREMENT PRIMARY KEY,
  name     VARCHAR(100),
  settings JSON
);

-- Extract values
SELECT JSON_EXTRACT(settings, '$.theme') FROM users;
SELECT settings->>'$.theme' FROM users;   -- shorthand

-- Modify
UPDATE users SET settings = JSON_SET(settings, '$.theme', 'dark') WHERE id = 1;

-- Check key existence
SELECT * FROM users WHERE JSON_CONTAINS_PATH(settings, 'one', '$.timezone');
```

## When to Use JSON Columns

**Good use cases:**
- User preferences (rarely queried by specific keys, frequently read as whole object)
- Product attributes (highly variable: electronics vs clothing)
- API request/response logging
- Event metadata (different fields per event type)
- Feature flags

**Bad use cases:**
- Data you filter/sort by frequently (use a real column instead)
- Data with strict schema requirements (use proper columns)
- Relationships between entities (use a foreign key, not a JSON array of IDs)

## Summary

- Always use `JSONB` in PostgreSQL, not `JSON`
- `->` extracts as JSON; `->>` extracts as text
- `@>` containment: `settings @> '{"theme": "dark"}'`
- `?` key existence: `settings ? 'timezone'`
- GIN index on the entire column for containment queries; expression index on extracted field for equality
- `jsonb_array_elements` expands a JSON array into rows
- `jsonb_agg` and `jsonb_object_agg` aggregate rows into JSON
