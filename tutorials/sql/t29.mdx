## Recursive CTEs: The Physical Graph Traversal Engine

Relational databases are designed for Set Theory (tables and joins), not Graph Theory (nodes and edges). However, standard business domains are full of graphs: organization charts, network routing, and bill-of-materials.

To solve this, SQL engines implement **Recursive CTEs**, which act as a Turing-complete physical graph traversal engine.

### The Working Spool (Cyclic Buffers)

A standard query flows in one direction: Table $\rightarrow$ Filter $\rightarrow$ Output. A Recursive CTE introduces a feedback loop. The database maintains two hidden memory structures: the **Result Table** and the **Working Table** (Spool).

1. **Initialization:** The Engine executes the Base Case. The rows are placed into *both* the Result Table and the Working Table.
2. **Iteration (BFS):** The Engine executes the Recursive Case. Crucially, any reference to the CTE name inside the recursive block *only queries the current contents of the Working Table*, not the entire Result Table.
3. **Replacement:** The rows generated by the Iteration are appended to the Result Table, and then they *completely replace* the contents of the Working Table.
4. **Termination:** If an iteration produces zero rows, the Working Table becomes empty, the loop terminates, and the Result Table is emitted to the client.

This iterative replacement forces the database to execute a **Breadth-First Search (BFS)** through the hierarchy.

### Memory Overhead and Graph Cycles

Because Recursive CTEs buffer arbitrary graphs in RAM, they are highly susceptible to memory explosion. If a hierarchy is 1,000 levels deep, the engine must perform 1,000 sequential join-and-buffer cycles.

More dangerously, if your graph contains a **Cycle** (e.g., A manages B, B manages A), the Working Table will never become empty. The engine will join infinitely, consuming 100% of CPU and RAM until the process OOMs (Out of Memory) or the transaction timeout kills it. 

**Architectural Rule**: Whenever writing a Recursive CTE on untrusted data, you must inject a cycle-detection mechanism (array tracing) or a hard depth-limit (`WHERE depth < 100`) to prevent infrastructure-killing infinite loops.

## What is a Recursive CTE?

A recursive CTE is one that references itself. It keeps running until no new rows are produced. It has two parts:

```sql
WITH RECURSIVE cte_name AS (
  -- 1. Base case: starting rows (runs once)
  SELECT ...

  UNION ALL

  -- 2. Recursive case: references cte_name, runs repeatedly
  SELECT ... FROM source JOIN cte_name ON condition
)
SELECT * FROM cte_name;
```

The database:
1. Runs the base case → produces initial rows
2. Runs the recursive case on those rows → produces more rows
3. Runs recursive case on those new rows → produces more rows
4. Stops when the recursive case produces zero rows

## Org Chart - Hierarchy Traversal

One of the most common real-world applications of recursive CTEs is traversing an organizational hierarchy. An org chart is a classic tree structure: the CEO has no manager, and each employee's `manager_id` points to their direct boss. The base case starts at the root (the CEO), and each recursive step finds all direct reports of nodes already in the result set.

The `depth` column tracks how many levels down from the root each employee is, and the `path` column concatenates names to produce a human-readable trail — both are computed incrementally on each recursive pass.

```sql
-- employees table
-- id | name    | manager_id
-- 1  | CEO     | NULL
-- 2  | Alice   | 1
-- 3  | Bob     | 1
-- 4  | Charlie | 2
-- 5  | Diana   | 2

WITH RECURSIVE org AS (
  -- Base case: start from the CEO (no manager)
  SELECT id, name, manager_id, 0 AS depth, name AS path
  FROM employees
  WHERE manager_id IS NULL

  UNION ALL

  -- Recursive: find direct reports of people already in the result
  SELECT
    e.id,
    e.name,
    e.manager_id,
    org.depth + 1,
    org.path || ' > ' || e.name
  FROM employees e
  JOIN org ON e.manager_id = org.id
)
SELECT
  REPEAT('    ', depth) || name AS indented_org_chart,
  depth AS level,
  path
FROM org
ORDER BY path;

-- Output:
-- CEO
--     Alice
--         Charlie
--         Diana
--     Bob
```

## Find All Descendants of a Node

Sometimes you don't need the entire tree — you need all nodes reachable *downward* from a specific node. This is called finding all **descendants**. The base case anchors on the specific target person (Alice), and each recursive step adds her direct reports. The recursive case then adds *their* direct reports, and so on, until no new employees are found.

This pattern is used in e-commerce for product sub-categories, in security systems for permission inheritance, and in project management for task dependencies.

```sql
-- Find everyone who reports to Alice (directly or indirectly)
WITH RECURSIVE reports_to_alice AS (
  -- Base: Alice herself
  SELECT id, name FROM employees WHERE name = 'Alice'

  UNION ALL

  -- Recursive: their reports
  SELECT e.id, e.name
  FROM employees e
  JOIN reports_to_alice r ON e.manager_id = r.id
)
SELECT name FROM reports_to_alice WHERE name != 'Alice';
```

## Category Tree (Breadcrumbs)

The inverse of finding descendants is **walking upward** toward the root — used in breadcrumb navigation (e.g., `Electronics > Mobile > Smartphones`). Here, the base case starts at a specific leaf node (category ID 42), and each recursive step finds the *parent* of the current node by joining on `parent_id`. The `breadcrumb` string is built by prepending the parent's name to the child's breadcrumb on every iteration, producing a complete path when the recursion terminates at the root (`parent_id IS NULL`).

```sql
-- categories: id | name | parent_id

WITH RECURSIVE breadcrumb AS (
  -- Start from a specific category
  SELECT id, name, parent_id, name AS breadcrumb
  FROM categories
  WHERE id = 42

  UNION ALL

  -- Walk up to parent
  SELECT c.id, c.name, c.parent_id, c.name || ' > ' || b.breadcrumb
  FROM categories c
  JOIN breadcrumb b ON c.id = b.parent_id
)
SELECT breadcrumb FROM breadcrumb WHERE parent_id IS NULL;
-- Output: 'Electronics > Mobile > Smartphones'
```

## Generate a Number or Date Series

Recursive CTEs are not limited to tree traversal. They can generate synthetic sequences — sequences of numbers or dates — which are invaluable for populating test data, filling calendar gaps in reporting, or generating all dates in a date range even when no orders exist. PostgreSQL provides `generate_series()` as a built-in shortcut, but the recursive CTE approach works in any SQL database that supports the `WITH RECURSIVE` syntax (MySQL 8+, SQL Server, SQLite 3.35+).

```sql
-- Generate numbers 1 to 100
WITH RECURSIVE numbers AS (
  SELECT 1 AS n
  UNION ALL
  SELECT n + 1 FROM numbers WHERE n < 100
)
SELECT n FROM numbers;

-- Generate dates for all of 2024
WITH RECURSIVE calendar AS (
  SELECT '2024-01-01'::DATE AS d
  UNION ALL
  SELECT d + INTERVAL '1 day' FROM calendar WHERE d < '2024-12-31'
)
SELECT d AS date, TO_CHAR(d, 'Day') AS day_name FROM calendar;
```

## Preventing Infinite Loops

A recursive CTE with a bug can loop forever. Always include a termination condition and optionally a depth limit:

```sql
WITH RECURSIVE safe_traversal AS (
  SELECT id, parent_id, 1 AS depth
  FROM nodes WHERE id = 1

  UNION ALL

  SELECT n.id, n.parent_id, st.depth + 1
  FROM nodes n
  JOIN safe_traversal st ON n.parent_id = st.id
  WHERE st.depth < 100   -- ← depth limit prevents infinite loop
)
SELECT * FROM safe_traversal;
```

## Detecting Cycles

In graph data with cycles, you need to track visited nodes:

```sql
WITH RECURSIVE path AS (
  SELECT id, ARRAY[id] AS visited, FALSE AS cycle
  FROM nodes WHERE id = 1

  UNION ALL

  SELECT n.id, p.visited || n.id, n.id = ANY(p.visited)
  FROM nodes n
  JOIN path p ON n.parent_id = p.id
  WHERE NOT p.cycle
)
SELECT id, visited, cycle FROM path;
```

## Summary

- Recursive CTEs have two parts: a base case and a recursive case connected by UNION ALL
- They run until the recursive case produces zero rows
- Essential for: org charts, category trees, path finding, number/date series generation
- Always include a termination condition or depth limit to prevent infinite loops
- PostgreSQL supports recursive CTEs natively; MySQL 8+, SQL Server also support them
